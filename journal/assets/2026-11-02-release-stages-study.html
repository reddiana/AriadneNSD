M47 MVP 다음의 단계

문서에는 "MVP"(지금)와 "웹 베타"와 "출시"라는 말이 있지만, 셋 사이의 경계는 적혀 있지 않습니다. 후원 버튼, 비공개 문제 알리기 채널, 상표 검색은 "베타 무렵" · "공개 출시 전"으로만 적혀 있습니다. 이 페이지는 MVP 다음의 단계를 다섯 물음으로 나눠 묻습니다. 정한 것은 DR-0018에 적습니다.

추천을 모두 고르면

MVP 베타 1.0과 그 뒤 Obsidian 베타 파일 형식이 바뀔 수 있음 저장한 파일은 뒤의 모든 판이 엶

가로축은 순서일 뿐 날짜가 아닙니다. 점선은 단계의 문턱입니다. 데스크톱은 이 순서(DR-0002) 그대로 Obsidian 다음입니다.

MVP (지금)

  • 링크를 아는 사람이 써 봅니다. 널리 알리지 않습니다.
  • 파일 형식은 바뀔 수 있습니다. 버전(v1)을 올리지 않고 고칩니다.

웹 베타의 문턱

  • 메인테이너가 MVP를 실제 일에 써 보고, 데이터를 잃는 결함이 없음
  • 파일에 남는 것을 확정: 글꼴 이름 "AriadneNSD Block", 저장할 때 고정 문구의 언어
  • 주소를 정함: ariadnensd.com으로 옮길지 (알린 뒤에 바꾸면 링크가 깨짐)
  • 상표 검색 (KIPRIS · USPTO · EUIPO)
  • 사용법 /manual/ (지금은 빈 주소)
  • 비공개 문제 알리기 채널 (R-REP-01), README의 후원 버튼 (R-ALL-01)
  • Firefox · Safari · 휴대폰에서 써 봄

웹 1.0의 문턱

  • MVP에서 미룬 편집 기능 (S4)
  • 키 표를 굳힘. 1.0 뒤에 키를 바꾸면 알림
  • 사용법이 모든 기능을 다룸
  • Obsidian 베타가 웹과 같은 파일을 읽고 써 봄
S1

단계를 몇 개로 나눌까요?

웹에만 해당합니다. Obsidian과 데스크톱은 S3에서 봅니다.

1

MVP → 베타 → 1.0

★ 추천
베타
널리 알리기 시작하는 때. 지금 "베타 무렵"으로 흩어진 일이 이 문턱에 모입니다
1.0
기능과 키가 굳는 때
단점
문턱이 둘이라 정할 것이 하나 더 있습니다
2

MVP → 1.0

장점
가장 단순합니다. MVP가 베타의 몫을 합니다
단점
알리는 때와 굳는 때가 하나라, 1.0 전에는 알릴 수 없거나 굳지 않은 것을 1.0이라 부르게 됩니다
3

MVP → 알파 → 베타 → RC → 1.0

장점
회사 제품에서 흔한 나눔이라 익숙합니다
단점
혼자 만드는 제품에는 문턱이 너무 많습니다. MVP와 알파가 하는 일이 겹칩니다
S2

저장한 파일이 뒤의 판에서도 열린다고 언제부터 약속할까요?

약속한 뒤에는 형식을 바꿀 때마다 버전을 올리고 옛 파일을 새 형식으로 옮기는 코드(마이그레이션)를 둡니다. 약속하기 전에는 버전을 올리지 않고 고칩니다. 지금 파일 형식 명세는 "첫 출시 전까지는 버전을 올리지 않고 고칠 수 있다"고 적고 있는데, "첫 출시"가 MVP인지 아닌지 분명하지 않습니다.

1

지금(MVP)부터

장점
MVP로 저장한 사람의 파일도 지킵니다. MVP는 README에 링크가 있어 누구나 열 수 있습니다
단점
outbox에 남은 글꼴 이름 · 고정 문구의 언어를 바꾸는 것도 마이그레이션이 됩니다
2

웹 베타부터

★ 추천
장점
널리 알린 뒤부터 지킵니다. MVP에서 써 보며 나온 것을 형식에 마음껏 고칩니다
단점
MVP로 저장한 파일은 뒤에 열리지 않을 수 있습니다. MVP 화면과 README에 그렇다고 적습니다
3

웹 1.0부터

장점
미룬 기능(접기, 펴 보기)을 넣으며 형식을 고칠 여유가 가장 깁니다
단점
베타를 알린 뒤 많은 사람이 저장한 파일이 열리지 않을 수 있습니다. 모델은 이미 미룬 기능까지 담도록 설계해 여유가 그렇게 필요하지 않습니다
S3

Obsidian 플러그인은 언제 시작할까요?

개발 순서(웹 → Obsidian → 데스크톱)는 DR-0002가 정했고, 웹의 어느 단계에서 다음으로 넘어갈지는 정하지 않았습니다. Obsidian은 커뮤니티 플러그인 목록에 오르기 전에도, BRAT 플러그인으로 GitHub 저장소에서 바로 설치해 베타로 써 볼 수 있습니다.

1

웹 베타 전 (MVP 바로 다음)

장점
메인테이너가 주로 쓰는 곳에서 가장 빨리 씁니다
단점
웹 베타의 문턱(매뉴얼, 주소, 상표)과 Obsidian 셸을 동시에 하게 되어 둘 다 늦어집니다
2

웹 베타 동안 (BRAT로 Obsidian 베타)

★ 추천
장점
웹 1.0으로 굳히기 전에 두 곳이 같은 파일을 읽고 써 봅니다. 노트에 넣은 그림이 어떻게 보이는지도 형식을 굳히기 전에 확인합니다
단점
베타 동안 두 셸을 함께 고칩니다. 편집기와 코어는 같은 코드라 고칠 곳은 대개 한 곳입니다
3

웹 1.0 뒤

장점
형식과 키가 굳은 뒤라 셸만 만들면 됩니다
단점
메인테이너가 Obsidian에서 쓰는 날이 가장 늦습니다. Obsidian에서만 드러나는 문제가 1.0 뒤에 나옵니다
S4

웹 1.0에는 어떤 기능까지 넣을까요?

채운 칸이 1.0에 드는 기능입니다. 다른 문서의 Method를 부르는 호출(P2)은 어느 안에서도 1.0 뒤입니다.

1

MVP 기능 그대로 굳히기

장점
1.0이 가장 빨리 옵니다
단점
프로토타입에서 아끼던 접기와 펴 보기가 1.0에 없습니다
2

MVP에서 미룬 편집 기능까지

★ 추천
장점
DR-0015가 "MVP 다음 판들"로 미룬 목록 그대로입니다. 이 제품을 다른 NS 편집기와 가르는 기능들입니다
단점
펴 보기의 성능(아키텍처의 위험)과 접기가 듣는 곳(Q20)을 베타 동안 풀어야 합니다
3

웹의 P1 모두

장점
1.0에 빠진 것이 가장 적습니다
단점
1.0이 가장 늦습니다. 공유 URL · PDF는 편집과 따로 더할 수 있는 기능이라 1.0 뒤에 더해도 파일에 영향이 없습니다
S5

버전 번호는 어떻게 붙일까요?

앱의 버전이고, 파일 형식의 버전(v1)과는 따로 갑니다. 지금 코드의 버전은 모두 0.0.0이고 화면에는 보이지 않습니다.

1

SemVer: 0.x에서 1.0으로

★ 추천
규칙
MVP는 0.1.0, 판을 낼 때마다 0.y를 올리고, 웹 1.0은 1.0.0. 단계는 번호가 아니라 이름(베타)으로 알립니다
장점
npm · Obsidian 플러그인(manifest의 version)이 쓰는 방식이라 따로 맞출 것이 없습니다
단점
베타가 몇 번부터인지 번호만 보고는 모릅니다
2

날짜 (CalVer)

장점
언제 낸 판인지 바로 보입니다
단점
1.0이라는 약속이 번호에 드러나지 않습니다. Obsidian 플러그인 목록은 SemVer 꼴을 바랍니다
3

번호 없이 단계 이름만

장점
지금과 같아 할 일이 없습니다
단점
결함을 알릴 때 어느 판인지 커밋 해시로만 말할 수 있습니다. Obsidian 플러그인에는 번호가 꼭 있어야 합니다
