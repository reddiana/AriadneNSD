M40 · 시험과 빌드 도구

결정함 (2026-10-25): T1 1번 소스 옆 · T2 1번 ESLint + Prettier · T3 1번 Vite + esbuild → ADR-0038.

테스트 전략을 쓰기 전에 정할 것 셋입니다. 시험의 종류와 도구 후보는 품질 속성 시나리오에서 이미 정했고(아래 표), 여기서는 시험 파일을 어디에 둘지(T1), 코드 모양을 검사하고 맞추는 도구(T2), 빌드 도구(T3)를 고릅니다. 백엔드(Java)에 빗댄 말을 붙였습니다. 각 물음의 1번이 Claude의 추천입니다.

이미 정한 것 (품질 속성 시나리오 3장)

시험도구Java에 빗대면
단위 시험, 성능 벤치마크VitestJUnit, JMH
속성 기반 시험, 퍼징fast-checkjqwik
골든 파일(저장되는 SVG를 바이트로 비교)저장소의 기대 파일approval test
브라우저 E2E, 시각 회귀PlaywrightSelenium
의존 방향 검사dependency-cruiserArchUnit
T1

T1. 시험 파일을 어디에 둘까

코드는 src/packages/core 같은 패키지에 둡니다(ADR-0036). 그 안에서 시험 파일의 자리입니다. 노란 칠이 시험 파일입니다.

T1 · 1번

소스 바로 옆 (*.test.ts)

Claude의 추천
src/packages/core/
  src/
    layout/
      measure.ts
      measure.test.ts
      place.ts
      place.test.ts
    model/
      commands.ts
      commands.test.ts
  golden/            ← 골든 SVG와 그 문서
    if-nested.ns.svg
  • TypeScript · Vitest의 흔한 관례입니다. 코드를 열면 그 시험이 바로 옆에 있어 함께 고치기 쉽습니다.
  • 파일을 옮기거나 지울 때 시험도 함께 움직입니다.
  • 골든 파일처럼 여러 모듈에 걸친 시험만 패키지의 golden/에 따로 둡니다.
  • 폴더 안 파일 수가 두 배가 됩니다.
T1 · 2번

패키지마다 test/ 폴더

src/packages/core/
  src/
    layout/
      measure.ts
      place.ts
    model/
      commands.ts
  test/
    layout/
      measure.test.ts
      place.test.ts
    model/
      commands.test.ts
    golden/
      if-nested.ns.svg
  • Maven · Gradle의 src/main · src/test와 같아 백엔드 개발자에게 익숙합니다.
  • 제품 코드 폴더가 깔끔합니다.
  • 폴더 나무를 두 벌 똑같이 맞춰야 하고, 파일을 옮기면 시험도 따로 옮겨야 합니다. TypeScript 쪽에서는 덜 흔합니다.
T2

T2. 코드 모양을 검사하고 맞추는 도구

린터(실수를 찾음, Java의 Checkstyle · SpotBugs)와 포매터(들여쓰기와 줄 바꿈을 맞춤, Java의 Spotless · google-java-format)입니다. 컨트리뷰터의 코딩 스타일을 사람 대신 도구가 지키게 합니다. 품질 속성 QA-13(화면 글자를 코드에 박지 않기)도 린터 규칙으로 검사할 생각입니다.

T2 · 1번

ESLint + Prettier

Claude의 추천
// 저장소 맨 위
eslint.config.js      ← 실수 검사 (typescript-eslint)
.prettierrc           ← 모양 맞추기

$ pnpm lint           ← 둘 다 돌림
  • 가장 널리 쓰는 짝이라 컨트리뷰터 대부분이 이미 압니다. 편집기(VSCode 등)의 지원도 가장 넓습니다.
  • 규칙을 직접 만들 수 있어 QA-13 같은 우리만의 검사를 넣기 쉽습니다.
  • 도구가 둘이고 설정 파일도 둘입니다. Biome보다 느립니다(이 크기의 저장소에서는 몇 초).
T2 · 2번

Biome 하나

// 저장소 맨 위
biome.json            ← 검사와 모양 맞추기 둘 다

$ pnpm lint
  • 도구 하나, 설정 하나입니다. Rust로 만들어 아주 빠릅니다.
  • ESLint보다 새롭고 규칙과 플러그인이 적습니다. 우리만의 규칙(QA-13)을 만드는 길이 좁습니다.
T3

T3. 빌드 도구

TypeScript를 브라우저와 Obsidian이 읽는 JavaScript 파일로 묶는 도구입니다(Java의 Gradle 빌드와 jar 묶기). 웹은 개발 중에 고치면 바로 보이는 개발 서버도 필요합니다.

T3 · 1번

웹은 Vite, Obsidian은 esbuild

Claude의 추천
src/apps/web/vite.config.ts        ← 개발 서버, 빌드
src/apps/obsidian/esbuild.config.mjs ← main.js 하나로
  • Vite는 React 웹 앱의 표준이고, Vitest가 같은 설정을 씁니다.
  • Obsidian은 공식 견본 플러그인이 esbuild로 main.js 하나를 만듭니다. 견본을 그대로 따르면 문서와 예제가 맞습니다.
  • 빌드 도구가 둘입니다(다만 Vite도 안에서 esbuild를 씀).
T3 · 2번

모두 Vite

src/apps/web/vite.config.ts
src/apps/obsidian/vite.config.ts   ← 라이브러리 모드
  • 도구가 하나입니다.
  • Obsidian 플러그인을 Vite로 묶는 것은 견본과 달라, 문제가 생기면 참고할 자료가 적습니다.

답하실 것

  1. T1, T2, T3 하나씩, 번호 또는 고칠 점.
  2. 정하면 테스트 전략 문서(docs/04-design/07-testing.md)를 쓰고, 도구는 ADR 하나로 남깁니다.
