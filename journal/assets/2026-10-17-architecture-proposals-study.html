M20 · 아키텍처 제안 확인

아키텍처 문서 03-architecture를 다시 쓰며(2026-10-13) Claude가 정해 적은 일곱 가지입니다. 각 단락에 1번(Claude의 제안, 문서에 적힌 것)과 2번(대안)을 나란히 그렸습니다. "1번 그대로"면 ADR이나 설계 문서로 옮기고, 아니면 고칩니다. A6은 이 페이지를 만들며 고친 제안입니다(2026-10-17에 정한 "다른 문서의 Method 부르기"와 사용자 설정 때문).

A1

A1. 글꼴에 관한 것을 따로 된 패키지(packages/fonts)에 모은다

편집기는 글꼴 파일(187~762 KB)과 글꼴을 추리는 wasm(652 KB)을 싣습니다. 그런데 레이아웃을 셈하는 데는 글자마다의 폭을 적은 표만 있으면 됩니다.

A1 · 1번

따로 된 패키지 fonts

Claude의 제안
  • 큰 파일이 한 곳에 모여, 어디에 싣는지 한눈에 보입니다.
  • core의 시험이 가볍습니다. 레이아웃만 쓰는 도구(예: Claude skill)도 wasm 없이 씁니다.
  • 패키지가 하나 늘어납니다.
A1 · 2번

core 안의 폴더로 둔다

  • 패키지가 셋(core · editor · 셸)으로 단순합니다.
  • 레이아웃만 필요한 곳도 1.5 MB쯤을 함께 받습니다. 나누려면 나중에 옮겨야 합니다.
A2

A2. 호출 블록은 부르는 Method를 id로 가리킨다

ADR-0022는 "호출 블록은 이름을 글자로 갖지 않고 Method를 가리킨다"까지 정했습니다. 무엇으로 가리킬지가 남았습니다. 예: Method partition의 이름을 split으로 고칠 때.

A2 · 1번

id로 가리킨다

Claude의 제안
// 파일 안의 모델
{ "id": "d7", "head": { "name": "split" } }
{ "call": "d7", "args": "nums, 0, n - 1" }
  • 머리의 이름을 고쳐도 호출 블록은 그대로 d7을 가리키고, 글자는 모두 split으로 바뀌어 보입니다.
  • 같은 이름의 Method가 둘이어도 헷갈리지 않습니다.
  • 다른 문서의 Method(#P2)는 "파일 + 그 파일 안의 id"로 가리킵니다. 그 파일에서 이름을 고쳐도 끊기지 않습니다.
  • 파일을 글자로 열어 보면 d7이 무엇인지 바로 알 수 없습니다.
A2 · 2번

이름으로 가리킨다

// 파일 안의 모델
{ "id": "d7", "head": { "name": "split" } }
{ "call": "partition", "args": "nums, 0, n - 1" }
// → 이름을 고치는 순간 끊김. 편집기가 모든
//   호출 블록을 찾아 함께 고쳐야 함
  • 파일을 글자로 읽기 쉽습니다.
  • 이름을 고치면 편집기가 호출 블록을 모두 찾아 고쳐야 합니다. 다른 문서에서 부르던 것은 고칠 수 없어 끊깁니다.
  • 같은 이름의 Method가 둘이면 어느 것인지 모릅니다.
A3

A3. 접기 영역은 블록이 아니라 줄에 붙은 표시다

본문 줄 A B C D에서 B C를 접기 영역 "입력 검사"로 만들었을 때, 모델의 트리가 어떻게 되는가입니다. 화면의 모습은 둘 다 같습니다.

A3 · 1번

줄에 붙은 범위 표시

Claude의 제안
  • 고르기 · 옮기기 · 감싸기 · j k는 블록 넷만 압니다. 접기 영역을 몰라도 됩니다.
  • 접기 영역을 만들고 풀어도 블록의 자리(부모)가 바뀌지 않습니다.
  • B를 줄 밖으로 옮기면 범위를 고쳐야 합니다. 그 규칙(범위가 줄어듦, 비면 사라짐)을 따로 정해야 합니다.
A3 · 2번

블록을 품는 블록

  • 접기 영역이 트리에 그대로 보여 저장 형식이 단순해 보입니다.
  • 접기 영역을 만들면 블록의 부모가 바뀝니다. 고르기, j k, 옮기기, 감싸기, 실행 취소가 모두 이 블록을 알아야 합니다.
A4

A4. 문서는 고치지 않고 새로 만들고(불변), 실행 취소는 앞의 문서로 돌아가기다

"B C를 If로 감싸기"를 한 뒤 u를 누를 때, 편집기가 무엇을 하는가입니다.

A4 · 1번

앞의 문서로 돌아간다

Claude의 제안
  • 명령마다 "되돌리는 명령"을 따로 짜지 않습니다. 명령이 30개를 넘어도 실행 취소의 코드는 하나입니다.
  • 되돌린 결과가 앞의 문서와 늘 똑같습니다(어긋날 수 없음).
  • 판을 몇 개까지 기억할지 정해야 합니다(예: 200번).
A4 · 2번

명령마다 되돌리는 명령을 짠다

감싸기(B..C, If)    ↔ 풀기(그 If)
지우기(B)          ↔ 넣기(B, 그 자리)
옮기기(B, 아래로)    ↔ 옮기기(B, 위로)
접기 영역 만들기     ↔ 접기 영역 풀기
… 명령마다 하나씩, 짝이 맞아야 함
  • 기억 공간이 가장 적게 듭니다.
  • 짝이 조금만 어긋나도 되돌린 문서가 앞과 달라집니다. 명령을 더할 때마다 짝도 짜고 시험해야 합니다.
A5

A5. 화면의 그림도 렌더러가 만든 SVG를 그대로 쓴다

저장되는 그림은 렌더러가 만듭니다(core). 편집 화면의 그림을 무엇으로 그릴지입니다. 이것이 정해지면 UI 프레임워크(ADR-0010)가 맡을 일의 크기가 정해집니다.

A5 · 1번

같은 렌더러 + 위에 편집 층

Claude의 제안
  • 화면에서 본 그림과 저장된 그림이 어긋날 수 없습니다.
  • UI 프레임워크는 도구 모음 · 메뉴 · 설정 창에만 쓰입니다. 그래서 ADR-0010의 고민이 작아집니다.
  • 한 글자를 고쳐도 그림 전체를 다시 만듭니다. 블록 500개에서 100ms 안에 드는지는 만들며 잽니다.
A5 · 2번

화면은 UI 프레임워크로 따로 그린다

  • 고친 블록 하나만 다시 그리기 쉽습니다(빠를 수 있음).
  • 그리는 코드가 두 벌이라, 화면과 저장된 그림의 1px 차이를 늘 맞춰야 합니다.
A6

A6. 셸(Obsidian · 데스크톱 · 웹)이 넣어 주는 것

처음 제안은 "셸의 인터페이스는 파일 입출력 하나(이 문서를 읽기 · 쓰기 · 다른 이름으로 쓰기)"였습니다. 다시 보니 둘이 빠져 있었습니다. 다른 문서의 Method 부르기(2026-10-17, #P2)는 다른 파일을 읽어야 하고, 사용자의 설정(화면 언어, 화면 색)은 어딘가에 보관해야 합니다.

A6 · 1번

두 가지: 파일 입출력 + 설정 보관

Claude의 제안고친 제안
  • Obsidian은 볼트에서, 데스크톱은 디스크에서 다른 문서를 읽습니다. 웹은 사용자가 고른 파일이나 폴더만 읽을 수 있어서, 읽지 못하면 그 호출 블록은 "이어진 곳 없음"으로 보입니다.
  • 설정 보관: Obsidian은 플러그인 설정, 데스크톱은 설정 파일, 웹은 그 브라우저.
  • 문서의 상태는 여전히 파일 안에만 둡니다(편집기 상태 저장소는 그대로 없음).
A6 · 2번

처음 제안 그대로: 파일 입출력 하나

  • 인터페이스가 가장 작습니다.
  • 셸마다 인터페이스 밖에서 같은 일을 따로 짜게 됩니다. 새 셸(Confluence, IDE)을 붙일 때 무엇을 짜야 하는지 문서에 드러나지 않습니다.
A7

A7. 블록 글자의 종류마다 낱말 가르는 함수 하나로 구문 강조한다

블록 글자의 종류(C · Java · Python · Bash …)를 문서마다 고르면 그 종류로 색을 입힙니다. 블록 하나의 글자는 문장 한 토막이라 문법상 완전하지 않습니다(예: While 블록의 i < n).

A7 · 1번

낱말만 가른다

Claude의 제안
if (count > 0)   // 양수일 때
printf("%d\n", count)
i < n
  • 예약어 · 글자열 · 주석 · 숫자 넷만 가립니다. 토막 글자에도 늘 됩니다.
  • 종류 하나에 짧은 함수 하나라 작고 빠릅니다. 종류를 더하기 쉽습니다.
  • 변수 이름과 함수 이름은 구별하지 않습니다(같은 색).
A7 · 2번

언어의 문법을 모두 읽는다 (예: tree-sitter)

if (count > 0)   // 양수일 때
printf("%d\n", count)
i < n   ← 문장이 아니라 읽다 막힘
  • 함수 이름 · 형 이름까지 색을 나눌 수 있습니다.
  • 언어마다 수백 KB의 문법 파일이 실리고, 토막 글자에서 자주 틀립니다.

답하실 것

  1. A1 ~ A7 하나씩, "1번 그대로" 또는 다른 번호나 고칠 점.
  2. "1번 그대로"를 받은 것은 ADR(제안 ADR이 이미 있으면 거기)이나 설계 문서로 옮기고, 아키텍처 문서의 "8. 확인받지 못한 제안"에서 지웁니다.
