M32 · 코드의 자리

inbox 요청: "MVP 직전입니다. src/ 구조를 어떻게 할 것인지 결정해야 합니다. 배포 대상이 다양한 것을 고려합시다." 큰 틀은 이미 정해져 있습니다. 공통 패키지 packages/fonts · core · editor와 대상마다의 셸 apps/*를 한 저장소에 두는 모노레포입니다(ADR-0002, 아키텍처 3.1). 그래서 여기서는 그 틀을 저장소의 어디에, 얼마나 잘게, 무엇과 함께 둘지를 묻습니다. 각 물음의 1번이 Claude의 추천입니다. 노랗게 칠한 곳이 안마다 다릅니다. 흐린 글자는 나중에 만들 대상이 들어갈 자리입니다(지금은 폴더를 만들지 않습니다).

빌드 결과(dist/)는 저장소에 넣지 않습니다(.gitignore). GitHub Actions가 빌드해 위 "내보내는 곳"으로 보냅니다. 패키지 이름은 2026-10-25에 잡아 둔 npm 조직으로 @ariadne-nsd/core처럼 씁니다.

S1

S1. 코드 폴더를 저장소의 어디에 둘까

지금 저장소 맨 위에는 문서 폴더(docs/ atelier/ journal/ til/ site/)가 있습니다. 여기에 코드가 들어옵니다.

S1 · 1번

맨 위에 apps/ 와 packages/

Claude의 추천
AriadneNSD/
├─ apps/
│  ├─ web/            웹 → /app/
│  ├─ obsidian/       Obsidian 플러그인
│  ├─ desktop/        데스크톱
│  └─ vscode/ intellij/ confluence/
├─ packages/
│  ├─ fonts/          D2Coding, 폭 표, 서브세팅
│  ├─ core/           DOM 없음
│  └─ editor/         React 편집 화면
├─ skills/ariadne-nsd/
├─ docs/ atelier/ journal/ til/
├─ site/              문서 사이트 빌드
├─ package.json       작업 공간의 뿌리
├─ pnpm-workspace.yaml
├─ tsconfig.base.json
└─ .github/workflows/ pages · release
  • ADR-0002와 아키텍처 문서의 이름(packages/core, apps/web)이 경로와 그대로 맞습니다. 문서를 고칠 곳이 없습니다.
  • TypeScript 모노레포의 흔한 모양입니다(Vite, Vue, Babel 등). 새로 오는 기여자에게 익숙합니다.
  • 맨 위의 폴더가 아홉 개로 늘어 문서와 코드가 섞여 보입니다.

  • 명령은 늘 src/에서 실행해야 하고, 도구와 GitHub의 안내 대부분이 맨 위의 package.json을 기대합니다.

  • 저장소 이름이 둘이 되고, 펴낸 사이트(/app/)에 앱을 함께 올리려면 저장소를 건너 빌드해야 합니다.
S2

S2. core를 몇 개의 패키지로 나눌까

core에는 모듈이 여섯 있습니다(아키텍처 3.1: 모델, 편집 명령, 텍스트, 레이아웃, 렌더러, 파일 형식). 의존은 한 방향(모델 ← 명령, 텍스트 ← 레이아웃 ← 렌더러)이어야 합니다.

S2 · 1번

패키지 하나, 안을 폴더로

Claude의 추천
packages/core/
├─ package.json       @ariadne-nsd/core
└─ src/
   ├─ model/          불변 객체, 불변식
   ├─ commands/       편집 명령
   ├─ text/           폭, 토크나이저, 문구
   ├─ layout/         순수 함수
   ├─ render/         씬 빌드 → SVG
   ├─ format/         직렬화, 마이그레이션
   └─ index.ts        밖에 내놓는 것만
+ 폴더 사이의 import 방향을 검사 도구로 막음
  • 빌드 · 판 번호 · 설정이 하나라 단순합니다. MVP 단계에서 패키지 수를 늘리면 관리할 것만 늡니다.
  • 의존 방향은 검사 도구(예: dependency-cruiser)를 CI에 넣어 지킵니다. 어기면 빌드가 실패합니다.
  • 나중에 따로 내놓을 필요가 생기면(예: 레이아웃만 쓰는 CLI) 그때 폴더 하나를 패키지로 떼어 냅니다.

  • 경계를 아직 써 보지 않았는데 굳힙니다. 모듈 사이를 옮기는 리팩터링이 패키지를 건너는 일이 됩니다.
S3

S3. Obsidian이 요구하는 manifest.json을 어디에 둘까

Obsidian 커뮤니티 플러그인 목록은 등록한 저장소의 맨 위에 있는 manifest.json을 읽어 플러그인의 이름과 판을 알아냅니다. 플러그인 파일(main.js 등)은 GitHub Release에서 받아 갑니다. 그래서 모노레포라도 이 파일 하나는 저장소 맨 위에 있어야 합니다.

S3 · 1번

맨 위에 사본, 스크립트가 맞춤

Claude의 추천
AriadneNSD/
├─ manifest.json      Obsidian이 읽는 사본
├─ versions.json      판 ↔ 최소 Obsidian 판
└─ apps/obsidian/
   └─ manifest.json   원본

판을 올리는 스크립트가 원본을 맨 위로 복사.
CI는 둘이 다르면 실패.
  • 저장소 하나, 이슈 하나. 플러그인 화면의 "저장소" 링크가 이 저장소로 옵니다.
  • 많은 모노레포 플러그인이 쓰는 방법입니다.
  • 맨 위에 파일 두 개가 더 생기고, 처음 보는 사람은 "왜 여기에?" 하고 볼 수 있습니다(README에 한 줄 적음).
S3 · 2번

플러그인만 다른 저장소로 내보냄

AriadneNSD/
└─ apps/obsidian/manifest.json

AriadneNSD-obsidian/  CI가 빌드 결과만 밀어 넣음
├─ manifest.json
├─ versions.json
└─ README.md
  • 이 저장소의 맨 위가 깔끔합니다.
  • 저장소가 둘이 되고, Obsidian 사용자의 이슈는 저쪽에 쌓입니다.
  • CI가 다른 저장소에 쓸 권한(토큰)을 가져야 합니다.
묻지 않고 따르는 것

이미 정했거나, 뒤의 결정을 따라가는 것

  • pnpm 워크스페이스로 묶습니다(ADR-0002의 후속 작업에 적힌 후보). 웹 · 편집기는 Vite, Obsidian은 esbuild로 빌드합니다(Obsidian 플러그인 견본이 쓰는 도구).
  • apps/desktop의 안쪽 모양은 ADR-0009(Electron 또는 Tauri)를 정할 때 따라 정해집니다. Tauri면 그 안에 Rust 폴더(src-tauri/)가 생깁니다.
  • 시험 코드를 어디에 둘지(소스 옆 *.test.ts 또는 test/ 폴더, 그림 비교용 기준 SVG의 자리)는 다음 일인 테스트 전략에서 정합니다.
  • 프로토타입(journal/assets/2026-10-10-ns-prototype.html)은 버리는 것이라 코드 폴더로 옮기지 않습니다.
  • 정한 것은 새 ADR(코드의 배치)로 남기고, ADR-0002에 "이후 변경"을 답니다.
