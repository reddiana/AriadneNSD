# 브라우저 저장소와 API 키: 서버 없는 페이지에서 AI를 부르는 법

2026-10-14에 "웹 버전에 Claude나 ChatGPT를 쓰는 대화창을 달 수 있나", "키를 브라우저 스토리지에 저장할 수 있지 않을까"라는 물음에 답한 것을 정리한다. → [[01-requirements#^web-ai-chat]]

## 한 줄 요약

서버가 없는 페이지에서는 **사용자가 자기 API 키를 넣고**, 페이지가 그 키로 AI 회사의 서버를 직접 부른다. 키는 브라우저 저장소에 둘 수 있다. 다만 그 저장소는 **같은 페이지에서 도는 모든 스크립트가 읽을 수 있다.**

## 백엔드로 비유하면

백엔드에서는 API 키를 서버의 환경 변수나 비밀 저장소에 둔다. 사용자는 그 키를 볼 수 없다. 서버가 사용자를 대신해 AI를 부르기 때문이다.

정적 페이지에는 그 "서버"가 없다. 페이지의 코드는 모두 사용자의 브라우저로 내려가고, 누구나 "소스 보기"로 읽을 수 있다. 그래서 메인테이너의 키를 페이지에 넣을 수 없다. 넣는 순간 공개된다. 길은 셋이다.

| 길 | 누구의 키 | 서버 | 치르는 값 |
| --- | --- | --- | --- |
| 사용자가 자기 키를 넣는다 (고른 것) | 사용자 | 없음 | 키가 있는 사람만 쓴다 |
| 중계 서버를 둔다 | 메인테이너 | 있음 | 사용료와 운영, 남용 막기 |
| 대화창을 달지 않는다 (Claude skill) | 사용자의 Claude | 없음 | 편집기 밖에서 묻고 결과를 가져온다 |

## 브라우저 저장소란

브라우저가 사이트마다 따로 내주는 작은 저장 공간이다. 백엔드로 치면 클라이언트마다 하나씩 있는 키-값 저장소이고, 서버는 그 안을 볼 수 없다.

| 종류 | 언제까지 남나 | 쓰임 |
| --- | --- | --- |
| `localStorage` | 사용자가 지울 때까지 | 설정, 넣어 둔 키 |
| `sessionStorage` | 그 탭을 닫을 때까지 | 잠깐 쓰는 값 |
| IndexedDB | 사용자가 지울 때까지 | 큰 것(작성 중인 문서의 임시 보관 → [[01-requirements#^web-draft]]) |

나누는 단위는 **출처(origin)**다. 주소의 앞부분(`https://` + 도메인 + 포트)이 같으면 같은 저장소를 본다. 다른 사이트는 읽지 못한다.

## 무엇이 위험한가

출처가 같으면 읽을 수 있다는 것은, **그 페이지에 실려 도는 스크립트라면 누가 쓴 것이든 읽을 수 있다**는 뜻이다.

- **남의 스크립트.** 광고, 통계, 외부에서 불러오는 라이브러리. 페이지에 `<script>`로 실으면 우리 코드와 같은 권한으로 돈다. 웹 버전에는 광고가 예정되어 있다([[01-requirements#^web-ads]]). 광고와 키가 한 페이지에 있어도 되는지는 정하지 않았다 → [[01-requirements#6. 미결정 사항]]
- **끼어든 스크립트(XSS).** 페이지가 남이 쓴 글을 그대로 화면에 넣으면 그 안의 스크립트가 돈다. AriadneNSD는 남이 준 파일과 공유 URL을 연다. 블록의 글자를 화면에 넣을 때 글자로만 다루어야 한다.
- **같은 컴퓨터를 쓰는 다른 사람.** `localStorage`의 값은 암호화되지 않고, 개발자 도구에서 그대로 보인다.

줄이는 법: 키를 `sessionStorage`에 두어 탭을 닫으면 잊게 하기, 광고를 다른 출처의 `iframe` 안에 가두기, 키를 쓰는 화면에는 남의 스크립트를 싣지 않기, 사용자에게 "쓸 수 있는 금액에 한도를 건 키를 따로 만들어 넣으라"고 안내하기.

## 브라우저에서 AI 회사의 서버를 직접 부를 수 있나

브라우저는 페이지가 다른 출처의 서버를 부르는 것을 기본으로 막는다. 그 서버가 "다른 출처에서 불러도 된다"고 답해 주어야 통한다(CORS). 백엔드에서는 겪지 않는 제약이다. 서버끼리는 누구나 누구를 부를 수 있다.

AI 회사의 API가 브라우저에서 바로 부르는 것을 받아 주는지는 회사마다, 때마다 다르다. 받아 주지 않으면 "사용자가 자기 키를 넣는다"는 길은 그 회사에 대해 닫힌다.

2026-10-14에 메인테이너가 염두에 둔 세 회사를 확인했다. 브라우저가 본 요청 앞에 보내는 물음(preflight, `OPTIONS`)과 키 없는 요청을 `curl`로 흉내 내어, 답에 `access-control-allow-origin`이 오는지 보았다. 출처는 `https://reddiana.github.io`로 적었다.

| 회사 | 주소 | 미리 묻기 | 키 없는 요청의 답 | 알아 둘 것 |
| --- | --- | --- | --- | --- |
| Claude (Anthropic) | `api.anthropic.com/v1/messages` | 200, 허용 | 401 + 허용 머리 | 요청에 `anthropic-dangerous-direct-browser-access: true`를 넣어야 한다. 빼면 미리 묻기가 400이고 허용 머리가 오지 않는다 |
| ChatGPT (OpenAI) | `api.openai.com/v1/chat/completions`, `/v1/responses` | 200, 허용 | 401 + 허용 머리 | 따로 넣을 머리가 없다 |
| Grok (xAI) | `api.x.ai/v1/chat/completions` | 200, 허용 | 400 + 허용 머리 | 요청의 모양이 OpenAI와 같다 |

셋 다 받아 준다. 다만 이것은 **문이 열려 있는지**만 본 것이다. 진짜 키로 진짜 브라우저에서 답이 오는지, 답을 조금씩 흘려 받는 것(스트리밍)이 되는지는 해 보지 않았다. Claude의 머리 이름에 "dangerous"가 든 것은 위의 "무엇이 위험한가" 때문이다. 키가 사용자의 브라우저에 있다는 것을 알고 쓰라는 뜻이다.
