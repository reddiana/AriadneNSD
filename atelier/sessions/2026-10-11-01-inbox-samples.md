# 2026-10-11 inbox 검토: 예제 둘, 문자 로고의 색, Event와 Method

3. **inbox 검토.** 다섯 가지 가운데 넷에 답을 받았다: "1: 수용 / 2: 모양을 다르게 하기 전에, 의미가 있는지 살펴봐주세요. / 4: 수용 / 5: 마무리 때". 3번(어두운 테마의 문자 로고)은 답이 없어 inbox에 남겼다.
4. **프로토타입 주소.** [[status#바로 가기]]에 칸을 만들고 inbox 맨 위에서 링크했다.
5. **예제 둘.** 프로토타입에 "퀵소트"와 "Raft" 예제 단추를 넣고 다시 게시했다(34번째 판). 화면의 이름도 `AriadneNSD`로 바꿨다.
6. **Event와 Method의 뜻.** Claude가 구분할 뜻이 있다고 검토했다 → 아래 "Event와 Method를 따로 둘지".
7. **어두운 테마의 문자 로고.** 원인을 찾는 데 Claude의 추정이 두 번 틀렸고, 메인테이너가 콘솔에서 읽어 준 값으로 원인이 잡혔다. "그냥 둡시다"로 정했다가, Obsidian에서도 같은 문제가 있다는 것을 보고 시안 둘을 실제 문서에 넣어 본 뒤 N1으로 바꿨다 → 아래 "어두운 테마에서 문자 로고가 검게 보이는 문제".
8. **Event와 Method의 시안과 결정.** 시안 페이지를 보고 메인테이너가 `H3, A1, C1, S2`를 골랐다. 프로토타입과 요구사항, ADR-0021에 반영했다 → 아래 "Event와 Method: 시안과 결정".
9. **마무리.** 고쳐 쓴 기록을 GitHub에 강제 push했다.

## Event와 Method를 따로 둘지

메인테이너의 물음: "Event와 Sub process 또는 Method를 별개로 하는게 의미있거나 더 유용할까요? 코드연동도 고려해봅시다." 그리고 "모양을 다르게 하기 전에, 의미가 있는지 살펴봐주세요."

Claude의 검토: **뜻이 있다. 모델에서 구분하기를 권한다.** 근거는 예제 둘을 만들며 나왔다.

| 견줄 점 | Event (이벤트 처리기) | Method (Sub process) |
| --- | --- | --- |
| 누가 시작하나 | 문서 밖 (인터럽트, 타이머, 받은 메시지) | 문서 안의 호출 블록 |
| 인자와 결과 | 없거나, 이벤트가 실어 온 것 | 인자를 받고 결과를 돌려준다 |
| 아무도 부르지 않으면 | 정상 | 쓰이지 않는 것 (알려 줄 만함) |
| 차트 → 코드 | 처리기 등록 (ISR, 콜백) | 함수 정의 |
| 코드 → 차트 | 힌트가 있어야 알 수 있음 | 함수는 기본으로 모두 Method |

- **읽을 때:** Raft 예제는 다이어그램 열 개가 모두 같은 모자를 쓴다. 어디서 일이 시작되는지(일곱)와 불려서만 도는 것(셋)이 한눈에 갈리지 않는다.
- **인자:** 퀵소트 예제에서는 호출 블록을 쓰지 못했다. 호출 블록은 머리 글자를 그대로 보여 주므로 `quicksort(a, lo, p - 1)`와 `quicksort(a, p + 1, hi)`가 같은 글자가 되고, `p = partition(…)`처럼 결과를 받을 수도 없다. 그래서 처리 블록으로 적었고 다이어그램 사이의 이어짐이 없다. 열린 질문 "호출 블록마다 다른 글자(인자)"의 답이 Method에서는 "필요하다"로 보인다.
- **코드 연동:** 코드를 만들려면 종류를 알아야 한다. 코드를 읽어 올 때는 함수가 모두 Method로 들어오고, 이벤트 처리기라는 것은 따로 표시해야 한다.
- **드는 값:** 개념이 하나 늘지만 사용자가 고를 일은 거의 없다. 블록을 새 다이어그램으로 빼면(`E`) Method, 머리를 달면(`M`) Event로 시작하고, 바꾸는 명령 하나를 두면 된다.

함께 정할 것: Method의 인자와 결과를 어떻게 적을지(머리와 호출 블록), 호출 블록으로 Event를 부를 수 있게 둘지(지금 요구사항은 허용), 모양.

## 어두운 테마에서 문자 로고가 검게 보이는 문제

메인테이너의 물음(inbox): "GitHub에서 다크테마를 설정했는데 문자로고의 Ariadne가 여전히 검게 나옵니다."

- **저장소 쪽은 맞다.** README의 `<picture>`와 두 그림 파일(어두운 화면용의 글자색 `#F7F1EA`)은 GitHub에 제대로 올라가 있다.
- **GitHub는 그림을 스크립트로 바꾼다.** README의 `<picture>`를 `themed-picture`라는 요소로 감싸고, 스크립트가 GitHub의 테마에 맞춰 조건을 고쳐 쓴다. 스크립트가 돌지 않으면 브라우저는 운영체제의 밝기만 본다.
- **Claude의 시험** (헤드리스 Chrome, 로그인 없음): 테마를 어둡게 고정하면 어두운 화면용이 골라졌다. "시스템과 맞춤"에 낮 테마가 어두운 경우에는 밝은 화면용이 골라졌다(GitHub의 한계. `#gh-dark-mode-only`도 같다).
- **Claude의 추정 둘은 틀렸다.** "시스템과 맞춤 + 낮 테마 어두움"과 "밝은 칸에 어두운 테마" 모두 메인테이너의 상태가 아니었다. 콘솔 값은 `dark / light / dark`였다.
- **메인테이너의 화면에서 읽은 값** (Edge, 로그인, Single theme: Dark, Windows는 밝은 모드): `2026-10-10-wordmark-light.svg ; (prefers-color-scheme: dark) ; false ; false ; /reddiana/ariadne-nsd`. 그림을 바꿔 주는 스크립트(`themed-picture`)가 켜지지 않았고, 그래서 조건이 고쳐지지 않은 채 운영체제의 밝기(밝음)를 따라 밝은 화면용이 그려졌다. 스크립트가 왜 켜지지 않았는지는 모른다.
- **고칠 길:** README 쪽에서 GitHub의 스크립트를 켤 방법은 없다. 문자 로고를 파일 하나로 두고 어느 바탕에서나 읽히게 하는 시안 다섯 가지를 그렸다 → https://claude.ai/artifact/VmPiuJk7cLMYDMA2ePKKs7, `journal/assets/2026-10-11-wordmark-*`. 메인테이너의 첫 결정은 "그냥 둡시다"였다.
- **Obsidian에서도 같았다.** 메인테이너가 "Obsidian에서도 다크테마에서 동일한 문제가 발생하는데 이건 왜죠?"라고 물었다. README의 조건은 Obsidian에서도 운영체제의 밝기를 따르고, `logo-source`와 `name-story`에는 Claude가 밝은 화면용 파일만 넣어 두었다.
- **시험과 결정.** 메인테이너가 N1과 P1을 차례로 실제 문서에 넣어 보고("N1을 테스트해봅시다", "P1 테스트") **N1으로 정했다**("N1으로 합시다"). 문자 로고는 파일 하나가 되었다.

## Event와 Method: 시안과 결정

메인테이너가 "Event와 Method를 구분 시안과 단축키 설명해주세요"라고 해서 시안 페이지를 만들었다 → https://claude.ai/artifact/AAXhC9eSan97yNw6S2HXB8, `journal/assets/2026-10-11-event-method-study.html`. 정할 것 네 가지(머리 모양, 인자와 결과, Event를 부를 수 있는지, 단축키)마다 안을 나란히 놓았고 Claude는 `H1 / A2 / C1 / S2`를 권했다.

메인테이너의 결정: **"H3, A1, C1, S2"**. 머리 모양과 인자 표기는 Claude가 권한 것과 다른 안이다. → [[0021-event-and-method|ADR-0021]]

프로토타입에 넣어 다시 게시했다(35번째 판). 넣으면서 Claude가 정한 것은 [[outbox]]에 적었다. 헤드리스 Chrome에서 키를 눌러 보는 시험 23개를 만들어 모두 통과했다(`journal/assets/2026-10-11-ns-prototype-test.mjs`). 지난 세션의 검사 177개는 임시 폴더에만 있어서 사라졌는데, 이번 시험은 저장소에 두었다.

## 발견한 위험

- **Claude의 추정이 두 번 틀렸다.** 문자 로고가 검게 보이는 까닭을 "시스템과 맞춤에 낮 테마가 어두움", "밝은 칸에 어두운 테마"로 추정했으나 둘 다 메인테이너의 상태가 아니었다. 추정을 사실처럼 적지 않고 확인을 부탁한 덕에 걸러졌다. 로그인한 화면은 Claude가 볼 수 없으므로, 그런 문제는 처음부터 그 화면의 값을 읽어 오는 편이 빠르다. → [[theme-aware-images]]
- **GitHub의 스크립트가 왜 켜지지 않았는지는 모른다.** 문자 로고를 파일 하나로 바꿔 문제는 사라졌지만 원인의 끝은 밝히지 못했다.
- **N1은 두 바탕 모두에서 대비가 약하다.** 메인테이너가 실제 문서에서 보고 골랐으나, 접근성 기준의 대비 값은 재어 보지 않았다.
- **호출 블록의 글자가 자유롭다(A1).** 머리 이름을 고치면 글자와 이어진 Method가 어긋날 수 있다. 코드를 만들 때 글자에서 인자와 결과를 가려내야 한다. ADR-0021의 "감수하는 점"에 적었다.
- **Claude가 넣으면서 정한 규칙이 여섯 가지다.** 부를 Method를 바꾸는 키 `R`, 글자가 같을 때 따라 바뀌기 등. 요구사항에 이미 적혀 있으므로, 확인받기 전까지는 [[outbox]]에서 놓치지 않게 한다.
- **Claude가 지어낸 주소를 문서에 적을 뻔했다.** 시안 페이지를 게시하는 것과 같은 때에 `status`의 바로 가기 칸을 고치면서, 아직 받지 않은 주소를 지어 적었다. 바로 다음에 실제 주소로 고쳤고 커밋 전에 확인했다. 주소는 게시 결과를 받은 뒤에 적어야 한다.
- **옛 커밋은 해시로 아직 열린다.** 강제 push 뒤에도 `github.com/…/commit/6b2fcb6`이 열렸다. 사진이 든 예전 커밋도 해시를 아는 사람에게는 한동안 보일 수 있다. 완전히 없애려면 GitHub 지원에 요청해야 한다.
- **기록이 갈라진 채로 세션을 시작했다.** 메인테이너가 기록 고쳐 쓰기를 로컬에서만 실행한 상태였다. 그 사이 Obsidian의 자동 백업이 push를 시도했다면 실패했을 것이다.
