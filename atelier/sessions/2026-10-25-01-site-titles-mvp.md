## 논의 흐름

### 1. 사이트의 문서 이름과 목록 (inbox 6)

- 메인테이너가 세션 전에 `title` 아홉 개의 말머리를 직접 뺐다(예: "AriadneNSD 요구사항 명세" → "요구사항", "보낼 편지함 (outbox)" → "Outbox"). Claude가 규칙을 읽어 냈다: 제품 이름 · 상위 폴더 이름의 말머리를 빼고, 영어 이름이 익숙하면 영어로.
- 나머지 제목은 표로 보여 고르게 했다. 처음 물을 때 표를 고르는 창 앞의 글에만 두어 메인테이너가 "표가 어디 있나요?"라고 했다. 표를 창의 미리 보기에 넣어 다시 물었고, README 둘은 한국어 이름("문서", "작업 공간")으로 정했다. 본문의 `# 제목`도 같게 맞췄다.
- 사이트: 왼쪽 목록을 파일 이름(번호)순으로(Quartz 기본은 제목순이라 번호 없는 제목이면 순서가 흐트러짐), 폴더의 README를 폴더 첫 페이지(index)로, 위쪽 제목(ArticleTitle)을 빼서 제목이 한 번만, 그래프에서 태그를 뺌. 본문에 `# 제목`이 없는 문서(inbox)는 빌드 때 넣는다.
- push 뒤 메인테이너가 "왼쪽 목록은 예전 제목"이라고 했다. 서버의 `contentIndex.json`은 새 것이었고, GitHub Pages가 10분 캐시(`max-age=600`)를 주어 브라우저가 옛 목록을 들고 있었다. Ctrl+F5로 해결.
- README의 "읽는 법"을 "1. 웹 사이트 / 2. Obsidian"으로 나눠 사이트 주소를 먼저 보이게 했다(주소는 팁 상자 안에 이미 한 줄 있었다).
- 태그 뒤 조사: `#P0`~`#P3`는 요구사항 항목의 우선순위 태그로 쓰려고 만든 것이라 태그는 살리고, 글 속에서 말할 때만 `` `P2` ``로 쓰기로 했다(25곳). `#Q9` 같은 것은 링크 안의 제목 주소라 태그가 아니었다.

### 2. MVP 전에 정할 것 (inbox 5)

- 답을 backlog의 새 절 "MVP 전에 정할 것"으로 두었다: ① 범위 ② 파일에 남아 바꾸기 어려운 것 ③ 아직 쓰지 않은 상세 설계 ④ MVP에 드는 조작 규칙.
- 고르는 창을 메인테이너가 두 번 "되묻기"로 돌려보냈다: 사이트를 아직 못 봤다(→ 그 자리에서 push), 프로토타입은 유지하나 · 프로토타입만큼 안 하면 MVP의 목적은 무엇인가(→ 프로토타입은 "맞나?", MVP는 "쓰나?"와 뼈대. 메인테이너: MVP는 "제품의 뼈대를 세우고 공개해 반응을 보는 쪽").

### 3. MVP 범위 (M28)

- 같은 흐름(메뉴를 읽고 커피 · 차 · 물)을 세 범위로 그려 견줌. S1 · 2번(`P0` + Case · For · 감싸기 · 풀기 · 복사 · 갈래)과 S2 · 1번(태그는 기능의 우선순위)을 골랐다 → [[dr-0015-mvp-scope|DR-0015]]

### 4. 번들 글꼴 (M29)

- 후보 다섯을 실제 글꼴 파일로 재고, 견본 글자만 추린 글꼴을 페이지에 넣어 같은 다이어그램을 그렸다. MVP에는 굵은 글자 · 기울임 자리가 모두 미뤄져 보통 굵기 하나면 된다.
- 메인테이너가 "사용자가 폰트를 선택하게 하는 기능은 아키텍처 변경이 큰가요?"라고 물었다. 번들한 것 가운데 문서마다 고르기는 작다(`textKind`가 이미 같은 구조), 기기의 아무 글꼴은 크다(ADR-0026을 다시 씀). 글꼴은 보는 사람이 아니라 문서의 설정이어야 한다.
- 메인테이너는 D2Coding을 골랐다(Claude의 추천은 IBM Plex Sans KR). 이어 "사용자를 한국어사용자로 국한하지 않을 것입니다"라고 해서 문자 범위를 재 보니 **IBM Plex Sans KR은 `é`도 없었다.** D2Coding은 라틴 확장 · 그리스 · 키릴 · 가나를 갖췄다. G2를 "어느 문자를 실을지"로 바꿔 다시 물어 "한자만 빼고 모두"(448 KB) → [[0034-default-block-font|ADR-0034]]

### 5. 파일 형식의 이름 (M30)

- 네임스페이스 URI 네 안(사이트 주소 · 도메인 · 저장소 주소 · URN)에서 메인테이너가 저장소 주소를 골랐다(Claude의 추천은 사이트 주소). 프로토타입의 v0 파일은 열지 않는다 → [[0035-model-namespace-and-v0|ADR-0035]]
- 모델 요소 이름과 필드 이름은 모델 설계를 굳히며 Claude가 정하고 확인받기로 했다.

### 6. 세션 중의 inbox 네 항목

- 컨트리뷰터 준비: `CONTRIBUTING.md` 첫 판(설계 단계의 기여, 영어 요약)을 쓰고, 코딩 스타일 등은 테스트 전략의 도구와 함께.
- 웹 버전의 본보기 SequenceDiagram.org와 한 페이지 사용 안내: 요구사항 참고 자료와 `^help`에.
- 웹 화면 설계의 시점: 레이아웃 설계 다음, 편집기 설계와 함께.
- 사이트의 폴더 페이지 순서: 폴더 먼저, 파일 이름순, 세션 기록만 최근 것이 위.

### 7. 파비콘, tech-notes 펴내기, 이름 잡아 두기

- 파비콘: DR-0006이 정한 작은 판(16~24px)을 둥글린 96px PNG(`site/icon.png`, `site/make-icon.mjs`).
- `tech-notes/`도 사이트에 펴냄. Mermaid 문법 검사 스크립트(`site/check-mermaid.mjs`)를 만들어 펴내는 그림 23개를 사이트와 같은 11.4.0으로 검사(모두 통과). 헤드리스 Chrome의 화면 찍기가 이 컴퓨터에서 자주 빈 결과를 내서 Node로 검사했다.
- "도메인 등 선점이 필요한 것": 배포 대상 전체로 정리. 메인테이너가 그 자리에서 `ariadnensd.com`(Cloudflare), npm 조직 `ariadne-nsd`, GitHub 조직 `AriadneNSD`를 만들었다. 상표 검색은 backlog로.

### 8. 테스트 설계는 MVP 전에?

- 네. 다만 둘로: 개발 전에는 테스트 전략(층마다의 시험, SVG 골든 파일, 인수 시험 목록, 도구 · CI), 기능마다의 세부 시험은 개발하며. 순서는 레이아웃 → 테스트 전략 → 편집기 · 웹(메인테이너: "제안 수용").

- 시안 M28 · M29를 Claude가 공개로 바꿀 수 있는지 물음: 공유 설정은 바꿀 수 없다. 메인테이너가 "공개로 바꾼 것 같은데..."라고 해서 페이지를 읽어 확인하니 M17 · M18 · M28 · M29 모두 이미 공개였다. status의 할 일과 옛 "비공개" 문장은 기록이 늦은 것이라 고쳤고, 확인하는 법을 스케치북에 적었다.

## 발견한 위험

- 추천의 전제를 대 보지 않으면 틀린다: 한국어 밖의 사용자를 보지 않고 낸 글꼴 추천이 `é`도 없는 글꼴이었다(메모리에 기준을 더함).
- MVP의 갈래 이름(`참` · `거짓`)이 명세의 "비례폭" 자리인데 글꼴이 하나라 D2Coding으로 그리기로 Claude가 정함 → [[outbox]]
- 블록이 프로토타입보다 넓어진다(같은 줄 187 → 221px). 크기 단계는 레이아웃 설계에서 다시 본다.
- Windows의 Python으로 고친 파일이 작업 폴더에서 CRLF가 되었다. 저장소에는 LF로 들어가지만 셸 스크립트가 로컬에서 깨질 수 있어 되돌렸다. 다음부터 Python으로 쓸 때는 `newline=''`을 준다.
- 로컬 미리보기 서버(node, 8080 포트)가 이 컴퓨터에 남아 있을 수 있다.
