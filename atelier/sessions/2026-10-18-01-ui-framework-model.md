# 2026-10-18 셸 · UI 프레임워크 · 모델 설계

2026-10-18의 첫 세션이다 (← [[2026-10-17-02-atelier-readme]]). 메인테이너의 첫 말은 "M20 A6 이해가 잘 안 갑니다. 설명을 다시 해주세요."였다.

## inbox 원문

세션 중에 메인테이너가 inbox에 더한 다섯 항목이다. 처리 방향에 동의를 받아(메인테이너: "네") 지웠다.

> [!quote] 3. 기능 / 프로토타입
> - if블록 브랜치 레이블도 수정할 수 있게해주세요
> - case블록의 default 레이블은 우측 정렬 해주세요.
> - if나 case 블록의 브랜치 내부에 아무 블록도 없으면 아무것 도 없다는 의미기 기호를 넣어주세요.

> [!quote] 3. 기능 / 프로토타입 / 추가/변경 요건
> - Event/Method 헤더는 원래 NSD에느 없던 것을 도입했습니다. 다음과 같은 옵션을 사용자가 선택할 수 있게 해주세요. (선택의 법위는 문서)
> 	1. 우리가 도입한 블록모양을 그대로 쓴다(현재안 대로), 
> 	2. 블록 자체는 존재하지만 아무 모양이 없고 레이블만 보여서 다이어그램의 제목처럼 보이게 한다
> - 감싸기나 폴더 관련 단축키처럼 두개의 키가 연속 조합되는 케이스는, 첫번째 키가 입력되면 두번째 키에대한 안내(선택)도 사용자에게 제시해주세요. 방법은 UI지식이 없어서 뭐가 좋을지 모르겠는데, 일단 떠오르는 것은 팝업이네요.

처리 방향(합의):

| # | 항목 | 처리 |
| --- | --- | --- |
| 1 | If 갈래 이름 고치기 | 모델에 If 갈래의 이름 칸을 두고(비면 "참" · "거짓"), 요구사항 · 조작 규칙 · 키 표 · 모델에 반영. 프로토타입은 할 일 |
| 2 | default 이름 오른쪽 정렬 | 시각 디자인 명세에 반영. 프로토타입은 할 일 |
| 3 | 빈 갈래 기호 | 시안 M24에서 기호를 고름 |
| 4 | 머리 모양을 문서마다 고르기 | 시안 M24에서 "제목처럼"의 모습과 Event · Method를 가르는 법을 고름 |
| 5 | 두 키 조합의 다음 키 안내 | 시안 M24에서 안내의 자리와 모양을 고름 |

## 논의 흐름

1. **M20 A6 다시 설명.** 셸을 백엔드의 저장소 어댑터에 견주어, 처음 제안(파일 입출력 하나)과 고친 제안(문서 파일 + 다른 문서 읽기, 설정 보관)을 Java 인터페이스 모양으로 보임. 메인테이너: **"추천 수용. 그리고 셀은 3개가 아닙니다. IDE까지 하면 더 많습니다."** → Claude가 "세 곳"이라 한 것을 바로잡고 기술 정리 [[wasm-and-shell]]도 고침 → [[0031-shell-interfaces|ADR-0031]]
2. **M20 A7.** lexer와 parser에 견주어 고르는 창으로 물음. 1번(낱말만 가름) → [[0032-token-highlighting|ADR-0032]]. M20의 일곱 가지가 모두 정해짐
3. **UI 프레임워크(ADR-0010).** 같은 도구 모음을 프레임워크 없음 · Svelte 5 · React 19 · Preact로 짜서 빌드하고 크기를 잼(1.9 / 57.5 / 219.8 / 14.5 KB) → 시안 M22. Claude는 Svelte를 추천
4. 메인테이너: **"배포 유형이 매우 다양합니다. IDE까지 고려한 것인가요?"** → 붙이는 것은 모두 되지만, Obsidian · VSCode · IntelliJ에는 그 프로그램의 메뉴와 설정 화면이 있다는 것을 빠뜨렸음. M22에 대상 표와 새 물음 U1을 더함. U1 1번(편집기가 명령과 설정의 목록을 내놓음) → [[0033-command-list-for-shells|ADR-0033]]
5. 메인테이너: **"Svelte과 React의 개발자 층은 어느 것이 두터운가요?"** → React가 6~20배쯤. 견주지 않았던 개발자 층과 배포 대상의 관례(Confluence Forge, VSCode 웹뷰)를 더해 추천을 React로 바꿈. U2 3번 React → [[0010-ui-framework|ADR-0010]] 승인
6. **상세 설계 `01-model` 시작.** 타입, 보기 상태, 불변 조건 일곱, 편집 명령, 규칙 F를 초안으로 씀. 사용자에게 보이는 물음 셋을 시안 M23으로
	- MD1 1번: 접기 영역 끝에 넣으면 고른 것을 따름
	- MD2: 메인테이너가 **"칸을 열고 고치는 도중 (아직 엔터를 입력하기 전)에 crtl+z는 어떻게 동작하나요?"** → 칸 안의 `Ctrl`+`Z`는 칸만, 칸을 연 때까지. 1번(칸을 열고 닫을 때까지 실행 취소 한 번)
	- MD3: 메인테이너 **"1번으로 하되, if처럼 보이게 될 것이라면 if블록으로 변환할지 물어보게 해주세요. 또, if블록에서 `+`를 누르면 case블록으로 변환할지 물어보게 해주세요."** 이어서 **"코드 리버스엔지니어링 할 때, default만 있는 코드는 문제가 되지 않을까요?"** → 모델은 넓게(default 없음 · default만 허용), 편집 명령은 좁게
7. **inbox 다섯 항목**(위 원문). 1 · 2는 바로 반영, 3~5는 시안 M24에서 모두 1번: 빈 갈래 `∅`, 머리 모양 "제목처럼"은 이름 + 딱지, 두 키 조합은 0.4초 뒤 화면 아래 안내 상자
8. 메인테이너: **"오늘은 여기까지. 안녕히"** → 마무리하고 push
9. 메인테이너: **"inbox에 추가한게 더 있어요. 이거까지 합시다."** → 아래 "inbox 원문 (마무리 뒤)"의 물음. 05가 DR로 옮겨지지 않은 까닭(DR-0001의 범위 밖, 같은 날 Claude가 적은 규칙)을 답하고, 결정이 흩어진 모습과 모으는 안 셋을 시안 M25로. D1 1번 → [[dr-0012-decisions-in-atelier|DR-0012]]. `05-ux-decisions`를 [[ux-decisions|UX 결정 모음]]으로 옮기고, 열린 물음은 [[02-interaction-rules#9. 미결정 사항]]으로, 오늘의 날짜 꼬리표는 결정 모음 링크로 바꿈

## 발견한 위험

- **Claude의 추천이 빠뜨린 기준 위에 서 있었다.** UI 프레임워크를 "세 셸"과 "읽기 쉬움"만 보고 추천했다가, 메인테이너의 물음 둘(IDE, 개발자 층)로 범위와 추천이 모두 바뀜. 배포 대상이 여섯을 넘으므로, 앞으로 구조를 정할 때는 [[03-architecture#6. 배포 구성]]의 표 전체를 대 본다
- 모델의 불변 조건을 편집 규칙에서 바로 옮기면 코드에서 가져온 것을 담지 못한다(Case의 default). 모델은 "담을 수 있는 것", 명령은 "만들 수 있는 것"으로 나눠 본다
- 웹에서는 다른 문서를 부르는 호출 블록이 사용자가 그 파일을 고르지 않으면 늘 끊겨 보임(ADR-0031)
- sed 패턴의 `\|`가 GNU sed에서 "또는"으로 읽혀 상태 문서의 두 줄이 망가졌다가 바로잡음. 위키링크의 `\|`가 든 줄은 파이썬으로 고친다
