# 2026-11-03 시작의 CPU를 프로파일로, 예제 썸네일을 WebP로

메인테이너: "진도 나갑시다" (`/clear` 뒤). inbox는 비어 있었다. Claude가 혼자 할 수 있는 다음 일로 [[backlog#MVP 개발]]의 "시작의 CPU 시간 더 줄이기"를 골랐다.

## 프로파일

- 시작의 CPU를 함수별로 보는 스크립트 `src/apps/web/scripts/profile-startup.mjs`를 만듦(CPU 6배 느림, 내비게이션부터 블록 글꼴 준비까지, 자기 시간 · 전체 시간 상위). 압축하지 않은 빌드(`vite build --minify false`)로 돌려야 이름이 읽힌다
- 다시 방문(CPU 6배 느림, 약 1초): 브라우저 내부(파싱 · 레이아웃 · 그리기) 약 350ms, 모듈 실행 약 180ms(그 가운데 `createEditor` 약 50 ~ 100ms), React 그리기 약 250ms
- 찾아 고친 작은 것 둘: 명령을 하나 등록할 때마다 모든 명령을 다시 계산함(등록 수의 제곱, 51 → 27ms) → 등록 · 해제 알림을 마이크로태스크 하나로 모음. 툴바 구분선 검사가 구분선마다 툴바를 다시 훑음 → 한 번 훑고 뺀 구분선만 목록에서 지움. 둘 다 측정의 흔들림(±0.3초)보다 작아 시계로는 보이지 않음
- 첫 방문의 첫 레이아웃 한 번이 687ms(CPU 6배)였고, 대부분이 글자 모양 계산(text shaping). 글꼴 목록의 순서를 바꿔 따로 재 봐도 같았고 영어 화면도 비슷해, OS가 글꼴을 처음 다루는 몫으로 보고 손대지 않음

## 예제 썸네일을 WebP로

- 트레이스에서 썸네일 SVG 10장(이미지마다 따로 된 문서, 안에 서브셋 글꼴)을 레이아웃하고 그리는 데 메인 스레드가 약 1초(CPU 6배)를 씀. 휴대폰 화면에도 썸네일이 거의 다 보여 `loading="lazy"`로는 줄지 않음
- 실험 빌드로 견줌(CPU 6배, 다섯 번 중앙값): 모달 → 썸네일 다 보임 1.6 ~ 1.8초 → 0.1 ~ 0.7초, slow 4G 썸네일 다 보임 5.0 ~ 6.4초 → 3.2 ~ 3.3초, slow 4G 글꼴 준비 3.1 ~ 6.3초 → 2.7 ~ 2.9초. 크기는 같음(한 언어 열 개에 약 84 KB)
- 만드는 법: 렌더러의 SVG를 Playwright의 Chromium 캔버스로 WebP(품질 0.9, 최대 440 × 248)로. 저장소에는 WebP 20개와 `sources.json`(그림마다 SVG의 해시). T-0529는 브라우저 없이 해시로 낡음을 검사
- 첫 E2E에서 시간 기준 테스트 셋(T-0002 · T-0007 · T-0287)이 실패했으나, 혼자 돌리면 통과하고 전체를 두 번 더 돌려 55개 모두 통과. 기계가 바빴던 때의 흔들림(1.1분 대 31초)
- 문서: [[06-web]] 5장의 표와 7장

## 발견한 위험

- 시작 시간은 같은 코드도 ±0.3초 흔들리고, 기계가 바쁘면 E2E의 시간 기준 테스트가 실패한다
- 남은 JS 실행은 하나하나가 작아 측정으로 잡기 어렵다. 더 줄이려면 코드 분할(모듈 실행을 나눔) 같은 큰 손질이 필요하다
