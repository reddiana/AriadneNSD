# ADR-0026: 글꼴을 번들하고, 글자 폭은 그 글꼴 파일로 셈한다

> [!info] 제안됨인 까닭
> "글꼴 번들"은 메인테이너가 정했다(2026-10-13). 폭을 **브라우저에 묻지 않고 셈한다**는 것과 아래 "남은 물음"은 Claude의 제안이다. 스파이크를 다른 브라우저에서 확인하고 남은 물음에 답이 나면 승인으로 바꾼다.

## 배경

블록의 폭은 글자의 폭으로 정해진다. 글자의 폭은 실행 환경(브라우저, OS에 깔린 글꼴)마다 조금씩 다르다. 그러면 같은 모델이 환경마다 다른 그림으로 저장되어 [[01-requirements#^nfr-compat]]와 [[01-requirements#^fmt-deterministic]]을 지키지 못한다. [[03-architecture#7. 위험과 검증이 필요한 사항]]에 위험으로 적어 두었던 것이다.

아키텍처를 짜기 전에 정할 것으로 Claude가 물었고, 메인테이너가 답했다.

> 3: 글꼴 번들
> 3번 스파이크 합시다

## 결정 기준

- 같은 모델은 어느 배포 대상에서 저장해도 같은 SVG가 된다
- `core`는 DOM과 브라우저 API에 기대지 않는다 ([[03-architecture#3. 구성 요소]])
- 설치 파일과 첫 내려받기가 지나치게 커지지 않는다

## 검토한 대안

### 대안 A. 글꼴을 번들한다

- 장점: 기기에 무슨 글꼴이 깔려 있든 같은 글꼴로 그린다. 글꼴 파일에 글자마다의 폭이 적혀 있어, 브라우저에 묻지 않고도 폭을 셈할 수 있다
- 단점: 글꼴 파일만큼 커진다. 글꼴에 없는 글자는 여전히 기기의 글꼴로 그려진다. 저장된 그림을 글꼴이 없는 곳에서 열면 다른 글꼴로 보인다

### 대안 B. 기기의 글꼴로 재고 값을 반올림한다

- 장점: 더 실을 것이 없다
- 단점: 기기마다 깔린 글꼴이 다르면 폭이 몇 px씩 달라 반올림으로 가려지지 않는다

### 대안 C. 요구사항을 "같은 환경에서 같은 SVG"로 낮춘다

- 장점: 할 일이 없다
- 단점: Obsidian에서 만든 파일을 웹에서 저장하면 그림 전체가 바뀌어 git에 큰 변경으로 남는다

## 결정

**글꼴을 번들한다(대안 A).** 그리고 글자 폭은 번들한 글꼴 파일의 글자 폭 표로 `core`가 직접 셈한다. 셸이 측정 함수를 주입하지 않아도 된다.

스파이크(2026-10-13, [[status#바로 가기]]의 "글자 폭 스파이크")에서 이 컴퓨터의 Chrome 155와 Edge 155로 견본 14줄을 쟀다.

| 견준 것 | 가장 큰 차이 |
| --- | --- |
| 번들 글꼴(커닝 끔)을 브라우저가 잰 값과 글꼴 파일로 셈한 값 | 0.015px (Chrome이 폭을 1/64px 단위로 맞추는 만큼) |
| 위 두 값을 위로 올림한 값 | 다른 줄 없음 |
| 커닝을 켠 값과 끈 값 | 줄에 따라 0~8px (`AVATAR To WAVE` 같은 낱말) |
| 기기의 글꼴(맑은 고딕)로 잰 값과 번들 글꼴로 잰 값 | 줄에 따라 2~32px |

여기서 정해지는 것:

- 그릴 때 커닝과 합자를 끈다(`font-kerning: none`). 켜 두면 글자 폭을 더한 값과 브라우저가 그린 폭이 어긋난다. 커닝까지 셈하려면 글꼴의 짝 표를 읽는 코드가 더 든다
- 셈한 폭은 정수 px로 올려 쓴다. 브라우저마다의 소수점 아래 차이가 그림에 들어가지 않는다
- 번들 글꼴에 없는 글자(견본에서는 `▾`)는 편집기가 그림에 적지 않는다. 사용자가 적은 글자가 글꼴에 없을 때의 폭은 따로 정한다

## 결과

- 좋아지는 점: 레이아웃이 순수한 셈이 되어 Node에서 그대로 시험할 수 있다. 측정 함수를 주입하는 인터페이스가 없어진다
- 감수하는 점: Pretendard Regular를 통째로 실으면 woff2로 762 KB, 자주 쓰는 한글 2,350자로 추리면 187 KB가 는다. 굵은 글자나 고정폭 글꼴을 더 실으면 그만큼 더해진다
- 확인하지 못한 것: Firefox(Gecko)와 Safari(WebKit)에서 번들 글꼴을 잰 값. 이 컴퓨터에 없어서 재지 못했다. 스파이크 페이지를 그 브라우저로 열면 바로 견줄 수 있다
- 남은 물음
	- 어느 글꼴을 싣는가. 스파이크는 Pretendard Regular(OFL 1.1)를 임시로 썼다. 코드를 적는 블록에 고정폭 글꼴을 쓸지도 함께 정한다
	- 번들한 글꼴을 저장되는 그림에도 넣는가(스파이크 페이지의 F1). 넣지 않으면 글꼴이 없는 곳에서 글자가 칸을 넘거나 못 미친다 → [[01-requirements#^fmt-text]], [[01-requirements#^fmt-outline]]
	- 사용자가 테마에서 글꼴을 바꾸는 것([[01-requirements#^lay-theme]])을 어디까지 허용하는가. 번들하지 않은 글꼴은 폭을 셈할 수 없다
	- 한글을 모두(11,172자) 싣는가, 추려 싣는가
- 후속 작업: [[02-layout#2. 텍스트 폭 측정]], [[03-architecture]]의 의존 규칙과 4.1의 흐름 그림(측정 함수 주입)을 고친다
