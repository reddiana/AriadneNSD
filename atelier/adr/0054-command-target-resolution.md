# ADR-0054: 명령의 대상과 삽입 위치는 editor의 컨테이너 트리에서 한 번에 정한다

## 배경

조작 규칙은 명령의 동작을 요소와 컨테이너의 규칙 T1 ~ T4, 모든 명령의 규칙 C1 ~ C5, 명령마다 받는 대상과 삽입 위치의 표로 추상화했다([[02-interaction-rules#공통 규칙]], [[ux-decisions#CR2. 공통 규칙에 컨테이너 · 블록 종류 · 필드 · 받는 대상 · 삽입 위치의 표|CR2]]). 아키텍처는 조작 규칙의 개념 하나에 구성 요소 하나를 대응시키는 것을 방침으로 한다([[01-architecture#4.6 조작 규칙과 구성 요소의 대응]]). 조작 규칙 전체와 설계 · 코드를 함께 검토한 결과([[interaction-abstraction-review]]):

- C4(실행 취소 단위)와 C5(읽기 전용)는 코드의 요소 하나이고, C1(대상 결정)과 C2(삽입 위치)는 명령마다 구현된다. 선택의 종류를 구분하는 분기가 `editor`의 21개 파일에 약 200곳, 상위 컨테이너를 찾는 구현이 넷, 삽입 위치의 구현이 키보드와 드롭에 따로 있다.
- 조작 규칙의 컨테이너(다이어그램, 반복 블록, 분기 블록, 분기, 접기 영역, 펴 보인 호출 블록)를 한 구조로 표현하는 것은 방향키가 쓰는 보이는 나무([[03-editor#2.2 이동]])뿐이다. 이동 명령, 드롭, 접기 대상, 풀기는 컨테이너의 종류마다 평행한 코드를 가진다.
- "화면에 보이지 않는 컨테이너는 없는 것과 같다"(T4)의 구현이 넷이고, 그 하나는 core의 인자(`hiddenFolds`)다. core가 화면의 개념에 의존한다.
- "접기 영역의 안인가 밖인가"를 core에 전달하는 방법이 다섯이다: `Range.join`, `Range.keepOut`, 인자 `outsideFolds`, 인자 `outsideFold`, `Target`의 종류(`fold` · `diagramEnd`).

관련 요구사항: [[01-requirements#^r-nfr|R-NFR-05]](키보드 접근성: 모든 진입점이 같은 명령), 원칙 ② "직접 조작" · ③ "선택 후 명령"([[02-interaction-rules#디자인 원칙]]).

## 결정 기준

- 조작 규칙의 개념(요소와 컨테이너, 대표 요소, C1, C2, 표 1 · 표 2)이 코드의 요소 하나씩에 대응한다.
- 매트릭스의 칸 하나를 바꿀 때, 선택의 종류 하나를 추가할 때 수정하는 `commands/` 파일이 하나다([[03-quality-attribute-scenarios#QA-22 조작 규칙의 변경 (제안)|QA-22]]).
- 키보드와 드롭이 같은 삽입 위치를 쓴다.
- `core`는 화면의 개념(선택, 펴 보기, 이름 띠, 빈 default 칸)에 의존하지 않는다([[01-architecture#4.3 의존 규칙]]).
- 편집 반응 시간을 해치지 않는다([[03-quality-attribute-scenarios#QA-07 편집 반응 시간|QA-07]]).
- 지금의 동작을 바꾸지 않고 명령 묶음마다 이전할 수 있다.

## 검토한 대안

### 대안 A: 구조는 그대로, 규칙의 표를 테스트로 대조

- 장점: 비용이 작다. 규칙의 표와 앱이 달라지면 테스트가 검출한다. 이미 있다(T-1700 ~ T-1721).
- 단점: 수정할 곳의 수는 그대로다. C1 · C2는 계속 명령마다 구현된다.

### 대안 B: editor에 컨테이너 트리, 선택의 사슬, 위치의 타입

`editor`가 문서(내용과 뷰 상태)에서 컨테이너 트리를 만들고, 그 위에 셋을 둔다.

1. **컨테이너 트리:** 노드는 다이어그램, 블록, 분기, 접기 영역이다. 노드는 모델의 id, 화면 id, 호출 경로, 줄 안의 범위, 보이는지(`isShown`), 접혔는지, 읽기 전용인지를 가진다. 보이지 않는 접기 영역(이름 띠를 끈 펴진 영역)도 노드다. 방향키의 보이는 나무는 이 트리의 뷰가 된다.
2. **선택의 사슬(C1, 표 1):** 선택한 것과 그것을 포함하는 컨테이너를 가까운 것부터 반환하는 함수 하나. 명령은 받는 대상의 종류와 상위로 올라가는지(표 2)를 기술하고, 사슬에서 첫 대상을 가져온다. 펴 보인 호출 블록 안에서도 같은 함수다.
3. **위치의 타입(C2):** 컨테이너와 그 안의 순서. core에는 `{ to, side, inside }`(어느 블록의 어느 쪽, 그 블록을 받는 가장 안쪽 접기 영역)로 전달한다. 키보드(요소 + 방향), 드롭(히트 + 구역), 이동(한 걸음의 목적지)이 같은 타입을 만든다.

- 장점: 규칙의 표 하나에 코드의 요소 하나가 대응한다. 상위 컨테이너 찾기 4개가 1개, 펴 보인 곳을 위한 사본이 0, T4의 구현이 1개(`isShown`), core의 안 · 밖 표현 다섯이 하나가 된다.
- 단점: 명령 묶음 여섯과 드롭을 이전하는 리팩터링이다. 접기 영역이 얽힌 경우에서 동작이 바뀔 위험이 있다.

트리를 두는 방법은 셋을 견주었다.

| 방법 | 평가 |
| --- | --- |
| B-1. 컨테이너 트리를 새로 두고, 보이는 나무는 그 뷰로 만든다 | 선택. 노드가 "무엇인지"를 가진다(지금의 보이는 나무는 접기 영역을 가짜 While 블록으로 변환해 종류를 잃는다). 보이지 않는 영역을 노드로 둘 수 있다. 스파이크에서 트리로 만든 보이는 나무가 지금 것과 같았다 |
| B-2. 보이는 나무에 필드를 추가한다 | 보이는 나무는 `Content` 타입(블록의 트리)이라 보이지 않는 영역을 넣을 수 없다. 넣으면 `navigate`가 그것을 건너뛰는 분기를 가져야 한다 |
| B-3. 트리 없이 줄마다의 접기 영역을 조회하는 함수를 공유한다 | 접기 영역만 통일된다. 분기 · 본문 · 펴 보인 호출 블록은 계속 종류마다 다룬다 |

### 대안 C: 명령의 표에서 조작 규칙의 매트릭스를 생성

- 장점: 문서와 코드의 원본이 하나다.
- 단점: 생성 스크립트와 문서 형식의 약속이 필요하다. 규칙을 먼저 기술하고 코드를 맞추는 순서와 반대다. B를 마친 뒤 다시 검토한다.

### 대안 D: C1 · T4를 core로 옮기고 `Target`을 확장

- 장점: `core`의 단위 테스트만으로 검증된다.
- 단점: 선택, 펴 보기, 이름 띠, 빈 default 칸은 화면의 개념이라 의존 규칙에 어긋난다. 지금의 `hiddenFolds`가 그 예다.

### 이동 명령(위 · 아래)의 구현

| 방법 | 평가 |
| --- | --- |
| core `move`를 유지한다(접기 영역의 경로와 `hiddenFolds`) | T4의 구현이 core에 하나 더 남는다. 접기 영역의 경로와 제어 블록의 경로가 평행하다 |
| `editor`가 트리에서 한 걸음의 목적지를 구하고 core `moveTo`가 실행한다 | 선택. 스파이크에서 임의 문서와 임의 명령으로 견주어 core `move`와 결과가 같았다. 한 걸음의 규칙이 "가장 가까운 보이는 컨테이너 안에서: 옆 항목을 지나거나, 그 컨테이너의 밖으로"로 한 문장이 된다 |
| 트리를 core에 둔다 | 뷰 상태(접힘, 펴 보기, 이름 띠)가 core의 편집 명령에 들어간다. 의존 규칙에 어긋난다 |

## 결정

(제안) **대안 A 위에 대안 B(B-1)로 간다.** 이동 명령(위 · 아래)은 `editor`가 컨테이너 트리에서 목적지를 구해 `moveTo`로 실행한다. 스파이크([[container-tree-spike]])로 확인한 설계다.

- `editor`의 `model/`에 컨테이너 트리, 선택의 사슬, 위치를 둔다. DOM을 쓰지 않는 순수 함수이고 Node에서 테스트한다.
- core의 편집 명령은 위치를 `{ to, side, inside }` 하나로 받는다. `Range.join` · `Range.keepOut`, 인자 `outsideFolds` · `outsideFold` · `hiddenFolds`, core `move`의 위 · 아래 경로를 제거한다. 같은 줄 안의 이동은 한 번에 계산한다(빼고 넣는 두 단계의 중간 상태에서 접기 영역이 사라지는 결함을 함께 해결).
- "빈 블록은 교체"는 위치가 아니라 명령의 성질이다(삽입 위치의 표의 한 줄). 위치와 따로 전달한다.
- 이전의 순서: core의 위치 → 컨테이너 트리와 보이는 나무 → 이동 → 대상 해석(접기 · 펴기, 접기 영역 풀기, 풀기, 분기 명령) → 삽입 · 붙여넣기 → 드롭 → 명령의 표. 묶음마다 기존 구현을 기준으로 결과를 견준 뒤 기존 구현을 제거한다([[container-tree-spike#6. 단계와 순서]]).
- 지금의 동작은 바꾸지 않는다. 트리로 표현하면 한 규칙인데 지금 다르게 동작하는 칸(U10 · U11)은 조작 규칙에서 따로 정한다([[interaction-abstraction-review#6. 추상화가 드러낸 칸]]).

방향은 메인테이너가 정했다(2026-11-28: 규칙과 설계를 함께, 0 → 1 → 2 → 3). 이 ADR은 스파이크의 결과로 승인을 요청한다.

> [!question] 미결정
> - 드롭의 구역 판정을 트리의 노드로 옮기는 방법과, 명령의 표(표 2에서 `when` · 컨텍스트 메뉴 · 알림을 생성)의 타입은 스파이크하지 않았다. 그 묶음을 시작할 때 작은 스파이크로 정하고 이 ADR의 "이후 변경"이나 새 ADR로 기록한다.

## 결과

- 좋아지는 점: 조작 규칙의 컨테이너 · T4 · C1 · C2가 코드의 요소 하나씩이 되어, 규칙을 바꾸면 수정할 곳이 정해진 한 곳이다. 키보드, 드롭, 이동의 결과가 같은 위치의 타입에서 나온다. core가 화면의 개념에 의존하지 않는다. 펴 보인 곳을 위한 사본 함수가 없어진다.
- 감수하는 점: 리팩터링의 비용(새 코드 약 1,000줄, 제거 약 1,050줄)과 회귀 위험. 이동(위 · 아래)의 규칙이 core에서 `editor`로 옮겨 가 그 테스트도 옮긴다. 문서가 바뀔 때마다 트리를 만든다(블록 500개에서 약 3ms). 표의 칸으로 표현되지 않는 처리(If에 분기를 삽입하면 Case로 변환)는 명령의 처리 함수에 남는다.
- 후속 작업: [[01-architecture]] 3.3 · 4.6과 [[03-editor]] 2 · 3 · 5장, [[01-model]] 4장(`moveTo`와 위치)에 기술. [[03-quality-attribute-scenarios#QA-22 조작 규칙의 변경 (제안)|QA-22]]의 응답 측정을 확정. 영향받는 승인 ADR에 "이후 변경"을 추가([[0017-fold-name-in-model|ADR-0017]]의 접기 영역 편집 규칙, [[0046-site-folding-in-view|ADR-0046]] · [[0047-copy-method-folds-at-first-open|ADR-0047]]의 펴 보인 곳의 접기 대상). 블록 종류의 기술자와 필드의 기술자([[interaction-abstraction-review#5.2 단계]]의 2 · 3단계)는 정하면 별도의 ADR로 기록한다.
