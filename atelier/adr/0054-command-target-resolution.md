# ADR-0054: 명령의 대상과 삽입 위치는 editor의 컨테이너 트리에서 한 번에 정한다

## 배경

조작 규칙은 명령의 동작을 모든 명령의 규칙 C1 ~ C5와 명령 × 대상 매트릭스로 추상화했다([[02-interaction-rules#공통 규칙]], [[ux-decisions#CR1. 공통 규칙은 바탕 규칙 넷과 명령 × 대상 표|CR1]]). 조작 규칙 전체와 설계 · 코드를 함께 검토한 결과([[interaction-abstraction-review]]):

- C4(실행 취소 단위)와 C5(읽기 전용)는 코드의 요소 하나이고, C1(대상 결정)과 C2(삽입 위치)는 명령마다 구현된다. 선택의 종류를 구분하는 분기가 `editor`의 21개 파일에 약 200곳, 상위 컨테이너를 찾는 구현이 넷, 삽입 위치의 구현이 키보드와 드롭에 따로 있다.
- 조작 규칙의 컨테이너(다이어그램, 제어 블록, 분기, 접기 영역, 펴 보인 호출 블록)를 한 구조로 표현하는 것은 방향키가 쓰는 보이는 나무([[03-editor#2.2 이동]])뿐이다. 이동 명령, 드롭, 접기 대상, 풀기는 컨테이너의 종류마다 평행한 코드를 가진다.
- "화면에 보이지 않는 요소는 조작에 영향을 주지 않는다"(원칙 ②)의 구현이 넷이다.

관련 요구사항: [[01-requirements#^r-nfr|R-NFR-05]](키보드 접근성: 모든 진입점이 같은 명령), 원칙 ② "직접 조작" · ③ "선택 후 명령"([[02-interaction-rules#디자인 원칙]]).

## 결정 기준

- 조작 규칙의 개념(요소와 컨테이너, 대표 요소, C1, C2, 매트릭스)이 코드의 요소 하나씩에 대응한다.
- 매트릭스의 칸 하나를 바꿀 때, 선택의 종류 하나를 추가할 때 수정하는 `commands/` 파일이 하나다.
- 키보드와 드롭이 같은 삽입 위치를 쓴다.
- `core`는 화면의 개념(선택, 펴 보기, 빈 default 칸)에 의존하지 않는다([[01-architecture#4.3 의존 규칙]]).
- 편집 반응 시간을 해치지 않는다([[03-quality-attribute-scenarios#QA-07 편집 반응 시간|QA-07]]).
- 지금의 동작을 바꾸지 않고 명령 묶음마다 이전할 수 있다.

## 검토한 대안

### 대안 A: 구조는 그대로, 규칙의 표를 테스트로 대조

- 장점: 비용이 작다. 규칙의 표와 앱이 달라지면 테스트가 검출한다.
- 단점: 수정할 곳의 수는 그대로다. C1 · C2는 계속 명령마다 구현된다.

### 대안 B: editor에 컨테이너 트리, 대상 해석기, 삽입 위치의 타입

보이는 나무를 컨테이너 트리로 확장한다(노드: 대신하는 모델 요소, 대표 요소, 읽기 전용 여부, 보이는지 여부). 그 위에 둘을 둔다.

1. 대상 해석기(C1): 선택한 요소에서 컨테이너를 차례로 올라가는 함수 하나. 명령은 "받는 대상의 종류, 올라가는지, 처리"의 표만 기술한다. `when`, 컨텍스트 메뉴의 항목, "어디에 적용했는지"의 알림을 이 표에서 생성한다.
2. 삽입 위치의 타입(C2): 줄의 사이, 분기의 사이, 다이어그램의 사이와 접기 영역의 안 · 밖. 키보드(요소 + 방향)와 드롭(히트 + 구역)이 같은 타입을 만들고, 삽입 · 붙여넣기 · 이동 · 드롭이 그것을 받는다. 드롭은 명령 레지스트리의 명령으로 실행한다.

대안 A의 테스트를 먼저 둔다.

- 장점: 규칙의 표 하나에 코드의 요소 하나가 대응한다. 상위 컨테이너 찾기 4곳과 삽입 위치 2곳이 하나씩이 되고, 펴 보인 곳을 위한 사본 함수가 없어진다. `core`의 편집 명령은 그대로다.
- 단점: 명령 묶음 여섯과 드롭을 이전하는 리팩터링이다. 미묘한 경우(이름 띠를 끈 접기 영역, 빈 default 칸을 채우며 삽입, 펴 보인 곳의 접기 영역, 접기 대상의 순서)에서 동작이 바뀔 위험이 있다.

### 대안 C: 명령의 표에서 조작 규칙의 매트릭스를 생성

- 장점: 문서와 코드의 원본이 하나다.
- 단점: 생성 스크립트와 문서 형식의 약속이 필요하다. 규칙을 먼저 기술하고 코드를 맞추는 순서와 반대다. B를 마친 뒤 다시 검토한다.

### 대안 D: C1을 core로 옮기고 `Target`을 확장

- 장점: `core`의 단위 테스트만으로 검증된다.
- 단점: 선택, 펴 보기, 빈 default 칸은 화면의 개념이라 의존 규칙에 어긋난다.

## 결정

(제안) **대안 A를 먼저 하고 대안 B로 간다.** 조작 규칙에 요소와 컨테이너, 명령마다 받는 대상, 삽입 위치의 표를 먼저 세우고([[interaction-abstraction-review#5.2 단계]]의 0단계), 그 표를 대조하는 테스트를 둔 뒤, 컨테이너 트리 · 대상 해석기 · 삽입 위치의 타입을 `editor`에 둔다. `core`의 편집 명령은 유지한다. 명령 묶음마다 이전한다: 삽입 · 붙여넣기 · 분기 삽입 → 복사 · 잘라내기 · 삭제 · 감싸기 → 풀기 · 접기 · 펴기 → 텍스트 편집 · 새 Method로 빼기 → 드롭.

이동 명령을 컨테이너 트리에서 목적지를 구해 `moveTo`로 실행하는 것(core `move`의 접기 영역 경로와 `hiddenFolds` 인자의 제거)은 스파이크로 확인한 뒤 따로 정한다.

메인테이너의 답을 기다린다 → [[interaction-abstraction-review#8. 정할 것]]

## 결과

- 좋아지는 점: 조작 규칙의 컨테이너 · C1 · C2 · 매트릭스가 코드의 요소가 되어, 규칙을 바꾸면 수정할 곳이 정해진 한 곳이다. 키보드와 드롭의 결과가 같은 규칙에서 나온다.
- 감수하는 점: 리팩터링의 비용과 회귀 위험. 표의 칸으로 표현되지 않는 처리(If에 분기를 삽입하면 Case로 변환)는 명령의 처리 함수에 남는다.
- 후속 작업: 규칙의 표를 대조하는 테스트, 변경 용이성 시나리오("새 명령 · 새 대상")를 [[03-quality-attribute-scenarios]]에 추가, [[01-architecture]] 3.3과 [[03-editor]] 2 · 3 · 5장에 기술. 블록 종류의 기술자와 필드의 기술자([[interaction-abstraction-review#5.2 단계]]의 2 · 3단계)는 정하면 별도의 ADR로 기록한다.
