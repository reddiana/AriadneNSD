# 요구사항 문서 검토

> [!abstract] 이 문서는
> UX 설계를 하려고 [[01-requirements]]를 처음부터 다시 읽으면서 찾은 **요구사항 문서 자체의 문제**를 모은 작업 목록입니다. 문서의 짜임새, 서로 어긋나는 문장, 빠져 있는 규칙이 들어 있습니다. 요구사항을 다시 짤 때 이 목록을 따라 고치고, 다 고치면 이 문서는 할 일을 다한 것입니다.
> - 사용자의 조작 규칙에 대한 설계(공통 규칙 일곱 개, Q1~Q17, Q19~Q21)는 [[ux-decisions]]에 있습니다.
> - 같은 날 요구사항의 세부 규칙(블록, 편집, 접기 등)을 [[02-interaction-rules]]로 옮겼습니다. 아래에서 "요구사항의 `^edit-extract` 아래에 …"처럼 짚은 문장 가운데 많은 것이 지금은 그 문서에 있습니다. 문장은 그대로 옮겼으므로 짚은 문제도 그대로 남아 있습니다.
> - 2026-10-12까지는 두 내용이 `plan/ux-review.md` 한 문서에 있었습니다. 메인테이너가 "내용을 보니 ux 설계입니다. ux 설계를 위한 입력은 요구사항에 있습니다"라고 짚어, 설계(출력)는 `docs/`로 옮기고 입력에 되돌려 줄 것만 여기 남겼습니다. 물음의 번호는 그대로입니다.

메인테이너의 요청(2026-10-11)에서 시작했습니다.

> 지금까지의 요구사항과 UX규칙을 검토해봅시다. 사용자 경험이 일관성이 있다면 단순하게 정리가 될 것 같아요.

> `docs/01-requirements`도 우리의 작품입니다. 단순하고 합리적이며 우리가 원하는 결과를 만들고 평가하기에 부족함이 없어야합니다.

**독립 검토.** Claude가 쓴 글을 Claude가 검토하면 같은 곳을 놓칩니다. 그래서 요구사항 문서와 용어집만 건네받은 다른 Claude에게 따로 읽혔습니다. 검토 문서의 내용(물음과 추천)은 건네지 않았습니다. 아래에서 "독립 검토"는 이것을 가리킵니다.

## 1. 문서의 짜임새 (Q18)

지금 [[01-requirements]]는 결정이 날 때마다 그 자리에 문장을 덧붙여 왔습니다. 그래서 규칙을 찾기 어렵고, 시험을 쓰려면 여러 곳을 맞춰 읽어야 합니다.

**보이는 문제.**

- **규칙이 엉뚱한 항목 아래에 있다.** "새 Method로 빼기"(`^edit-extract`) 아래에 새 빈 다이어그램 만들기, 머리 달기, 종류 바꾸기, `E` · `M` 키가 달려 있다. Event 머리(`^blk-event`) 아래에 Method의 이름 규칙이 있다
- **키가 규칙 문장에 섞여 있다.** 어떤 명령은 키가 적혀 있고(`F`, `U`, `E`, `M`, `Tab`, `Ctrl`+방향키), 어떤 명령은 없다(블록 넣기, 호출, 감싸기, 갈래). 키를 다시 설계하면 문서 곳곳을 고쳐야 한다
- **명령이 어떻게 실행되는지가 감싸기에만 적혀 있다.** "단축키, 우클릭 메뉴, 도구 모음 모두 지원"
- **블록 종류 표의 블록 가운데 규칙이 없는 것이 있다.** For, 탈출, 병렬, 주석
- **평가할 기준이 없는 문장.** "편집을 방해하지 않는 자리", "옆으로 긴 띠가 되지 않도록", "16 : 10에 가까워지게"

**제안하는 짜임.** 3장 "기능 요구사항"의 3.1과 3.2를 아래 순서로 다시 짭니다. 2장(배포 대상), 3.3 뒤(레이아웃, 파일 형식, 내보내기), 4장 뒤는 손대지 않습니다.

| 절 | 담는 것 |
| --- | --- |
| 개념 | 문서 · 다이어그램 · 머리 · 블록 · 갈래 · 빈 블록. 고를 수 있는 것의 표 ([[ux-decisions#Q10. 고를 수 있는 것의 목록\|Q10]]) |
| 공통 규칙 | R1~R7([[01-ux-overview#3. 공통 규칙]]). 규칙마다 블록 ID. 예외는 그 규칙 아래에 모두 적는다 |
| 블록 | 블록 종류마다 "모양, 글자, 이 블록에만 있는 규칙". 공통 규칙과 같은 것은 적지 않는다 |
| 명령 | 명령마다 "무엇을 골랐을 때 듣는가 → 무슨 일이 일어나는가 → 끝난 뒤 무엇이 골라져 있는가". 표로 |
| 이동과 선택 | 방향키, 여러 블록 선택 |
| 단축키 | 명령과 키의 표 **하나**. 키는 여기에만 적는다 |

- **기존 블록 ID(`^edit-wrap` 등)는 그대로 둡니다.** 승인된 ADR이 이 ID로 가리키고 있고, 승인된 ADR의 본문은 고치지 않기 때문입니다. 같은 까닭으로 파일을 여럿으로 쪼개지 않고 `01-requirements.md` 하나로 둡니다
- **까다로운 규칙에는 장면을 하나씩 붙입니다** ("이것을 고르고 → 이 명령을 하면 → 이렇게 된다"). 시험 설계가 이 장면에서 바로 시작할 수 있습니다

**고를 것 (Q18).** 1. 이 짜임으로 다시 짠다 / 2. 지금 짜임을 두고 문장만 고친다. **추천: 1.**

## 2. 우선순위 태그와 MVP 범위 (Q22)

"#P0 = MVP 필수"이고 5장은 MVP의 배포 대상을 웹으로만 적습니다. 그런데 Obsidian 항목 일곱 개와 데스크톱의 파일 열기가 #P0입니다. 또 #P0인 "키보드만으로 편집" 아래에 #P1 기능(Case, 머리, 여러 다이어그램)의 규칙이 달려 있고, #P0인 "여러 블록 선택"은 #P1인 복사와 이동을 말합니다.

1. **태그의 뜻을 "기능의 우선순위"로만 쓰고, 배포 대상의 순서는 DR-0002(웹 → Obsidian → 데스크톱)이 정한다고 적는다.** MVP = 웹에서의 #P0. Obsidian의 #P0은 "Obsidian 판을 낼 때의 필수"로 읽는다. #P0 항목 아래에 섞인 #P1 규칙은 다시 짜면서 제 항목으로 옮긴다
2. Obsidian과 데스크톱의 #P0을 #P1로 내린다

**추천: 1.**

이것과 따로, 5장 MVP 범위가 "#P0 항목만"인데 그 뒤 #P1로 들어온 것(Case, 호출, 여러 다이어그램, 접기)이 프로토타입의 중심이 됐습니다. 범위를 넓힐지는 메인테이너가 정할 일이라 [[debt]]에 적어 두었습니다.

## 3. 낱말 둘 (Q23)

한 낱말이 두 가지를 가리킵니다.

- **"머리"**: 다이어그램의 Event · Method 머리와, 제어 블록의 조건이 적힌 윗부분("머리는 남고", "Case의 머리"). → 추천: 제어 블록 쪽을 **"조건 칸"**으로 바꾼다. "머리"는 다이어그램의 것만 가리킨다
- **"선택 블록"**: 용어집에서는 If 블록인데, 요구사항 여러 곳에서 "고른 블록"의 뜻으로 쓴다. → 추천: If 블록은 **"If 블록"**이라고만 부르고, 고른 것은 "고른 블록"으로 적는다. 용어집의 "선택 블록"을 "If 블록"으로 바꾼다

`Q23: 추천대로` 또는 다른 말을 적어 주세요.

## 4. 묻지 않고 고칠 것

메인테이너가 정한 것을 바꾸지 않는, 문서의 잘못입니다. 다시 짤 때 함께 고칩니다.

- `^obs-theme`가 "저장되는 SVG의 색상은 테마 설정을 따름"이라고 적는데, 6장에는 저장된 SVG의 색이 미결정으로 남아 있다 → `^obs-theme`에서 그 말을 빼고 미결정을 가리킨다
- 접기 영역 풀기 설명이 제어 블록 풀기를 `^edit-wrap`으로 가리킨다 → `^edit-unwrap`
- `^edit-basic`의 "텍스트 수정(더블클릭 또는 F2)"에 `Enter`가 빠져 있다 ([[02-interaction-rules#Q1. 고치기를 시작하는 방법 (R1)|Q1]]의 답에 따라)
- 2장 첫 문장 "세 가지 형태로 배포한다"와 표: Google Drive, Confluence, Claude skill이 그 뒤에 더 있다 → "무료 배포 대상 셋과 그 밖"으로 적는다
- 5장 MVP 범위가 "#P0 항목만"이라고 하는데, 그 뒤 #P1로 들어온 것이 프로토타입의 중심이 됐다 → 범위는 그대로 두고, 그 사실을 한 줄 적는다
- "이벤트 머리"와 "Event 머리", "선택한 블록"과 "고른 블록"이 섞여 있다 → 하나로 맞춘다 ("Event 머리", "고른 블록". 용어집의 "선택 영역"은 그대로)
- frontmatter의 `updated`가 2026-10-10이다

독립 검토가 찾은 모순도 함께 고칩니다.

- `^edit-basic`의 "추가(선택 블록의 앞/뒤/안쪽)": "안쪽에 넣기"는 2026-10-10에 없앴다 → "안쪽"을 뺀다
- "한 갈래의 블록을 모두 고르고 접으면 그 갈래만 접는다"가 접기 · 펴기의 대상 목록에 빠져 있다 → [[02-interaction-rules#Q20. 접기 · 펴기가 듣는 곳을 한 문장으로 (R6)|Q20]]의 답에 맞춰 적는다
- 끊긴 호출 블록은 "고칠 수 없다"고 하고 바로 "부를 Method를 다시 고르면"이라고 한다 → 막는 것은 인자와 결과 고치기뿐이라고 적는다
- "DIN 66261 / 원 논문 기준" 바로 아래에 표준에 없는 Event · Method 머리가 있다 → 표준의 블록과 AriadneNSD가 더한 것을 나눠 적는다
- 감싸기 표의 "For 블록(#P1) 구현 후"는 일정 메모다 → 뺀다
- "같은 모델이면 같은 파일": 저장되는 그림은 접힘 상태에 따라 달라진다 → "같은 내용과 같은 보기 상태이면"으로 고친다
- Obsidian의 "탭을 닫으면" · "저장하면" · "편집을 마치면"이 섞여 있다 → 저장 시점이 미결정이라는 것을 6장에 올리고, 낱말을 하나로 맞춘다
- 까닭을 적은 문장("…하려는 것이다")과 방법을 적은 문장(빗금의 좌표)이 요구사항에 섞여 있다 → 까닭은 ADR이 있으면 그리로 링크하고, 없으면 짧게 남긴다. **승인된 ADR에 없는 까닭을 지우지는 않습니다** (지우면 어디에도 남지 않으므로)
- 키 `M` · `E`의 조건이 겹친다: 머리 없는 다이어그램에서 블록을 고르고 `M`을 누르면 "새 Method로 빼기"와 "머리 달기"가 둘 다 맞다 → 단축키를 다시 설계할 때 풉니다

## 5. 요구사항에 빠져 있는 것

프로토타입에는 있고 메인테이너가 써 보셨지만 요구사항에는 적히지 않은 것입니다. 다시 짤 때 프로토타입의 동작대로 적고, 적은 것을 목록으로 보여 드려 확인받겠습니다.

- **지우기.** 블록을 지운 뒤 무엇이 골라지는지. 갈래의 마지막 블록을 지우면 빈 블록이 남는 것. 머리를 고르고 지우면 머리 떼기, 다이어그램 지우기는 따로(지금 `Shift`+`Delete`)
- **글자 고치기 중의 줄바꿈** (지금 `Shift`+`Enter`)
- **빈 블록**이 무엇인지 (4장의 정합성 문장에만 나옴)
- **호출 블록에서 부르는 Method로 가기** (지금 `G`), **부를 Method 바꾸기** (지금 `R`)의 명령 이름
- **목록에서 고르기** (부를 Method 목록, 감싸기 목록): 방향키와 `Enter`, 숫자 키
- **감싸기가 두 번 누르기**라는 것 (지금 `S` 다음 글자)
- **머리를 골랐을 때** 각 명령이 어떻게 듣는지 (블록 넣기는 본문 맨 앞? 붙여넣기만 적혀 있음)
- **오른쪽 클릭 메뉴와 도구 모음**에 무엇이 있는지

### 독립 검토가 찾은, 답이 없는 곳

"이 문서만 보고 만들고 평가할 수 있는가"에 걸리는 곳입니다. 80개쯤이고, 하나하나 여쭙지 않겠습니다. 다시 짤 때 **프로토타입의 동작이 있으면 그대로 적고, 없으면 공통 규칙에서 끌어내 적은 뒤**, 새로 적은 문장에 표시를 붙여 한꺼번에 확인받겠습니다. 큰 묶음만 적습니다.

- **지우기 규칙이 통째로 없음.** 제어 블록을 지우면 안쪽도 지워지는지, 머리와 다이어그램을 지우는 명령, 지운 뒤에 골라지는 것
- **"빈 블록"의 정의.** 글자가 빈 처리 블록인지 따로 있는 자리 표시인지
- **`↑` `↓`의 "그림에 보이는 순서".** If의 조건 칸에서 `↓`가 어느 갈래로 가는지, 참 갈래의 끝에서 `↓`가 어디로 가는지, Do-While은 조건이 아래에 있는데 어디서 골라지는지
- **방향키의 끝.** 다음 블록이 없을 때, 다이어그램 순서의 끝에서 멈추는지 도는지
- **여러 블록 선택과 키보드.** `Shift`+`↑` `↓`가 줄의 끝을 넘으면 부모로 넓히는지, 범위를 고른 채 방향키를 누르면 어디서 출발하는지
- **접기 영역과 편집.** 영역의 끝 블록 뒤에 넣으면 안인지 밖인지, 블록을 지워 하나만 남으면, 영역의 경계를 걸친 선택으로 감싸거나 빼면, 복사할 때 영역과 이름이 따라가는지
- **"블록 n개"의 n.** 바로 아래 블록 수인지 모든 후손인지
- **머리 이름의 끝 경우.** 닫는 괄호가 없을 때, 괄호 뒤에 글자가 있을 때, 종류를 바꾸면서 이름이 겹치게 될 때(프로토타입의 알려진 구멍)
- **호출 블록을 넣는 흐름.** 목록에서 `Esc`, Method가 하나도 없을 때의 목록, 결과가 비었을 때 기호를 감추는지
- **Case.** default 갈래에서 "갈래 넣기"를 하면 어디에 들어가는지, 갈래의 최소 수, If의 "참" · "거짓"을 고칠 수 있는지
- **빈 다이어그램.** "머리도 내용도 없는 다이어그램은 저절로 사라진다"는데 새 문서의 첫 다이어그램이 바로 그 상태다. 언제 사라지는지
- **P0 블록 넷(처리, If, While, Do-While)에 블록 ID와 규칙이 없음.** Do-While과 Repeat-Until은 조건의 뜻이 반대인데 블록 하나에서 어떻게 가르는지
- **평가할 수 없는 문장.** "편집 반응 100ms"(무엇을, 어떤 기기에서), "편집을 방해하지 않는 자리", "옅은"
