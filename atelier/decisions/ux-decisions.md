## 2. 고치기 · 넣기 · 옮기기

### Q3. `Esc`의 뜻 (R1)

**정함 (2026-10-13): 3. `Enter`와 `Esc` 모두 적은 대로 받아들인다.** 고치기 전으로 되돌리려면 실행 취소를 한다. 받아들일 수 없어 다시 연 칸(겹친 머리 이름)에서만 `Esc`가 고치기 전으로 되돌린다.

- 까닭: Vim에서 `Esc`는 적은 것을 남기고 나가는 키라서, 되돌리기로 두면 Vim에 익은 손이 적은 글자를 매번 잃는다 → [[dr-0009-vim-keys|DR-0009]]. 처음의 추천은 "`Esc`는 되돌리기"(1)였다.
- 지금의 규칙 → [[02-interaction-rules#Event 헤더]]

## 3. 묶기 · 풀기 · 실행 취소

### Q7. 푸는 명령을 하나로 (R5)

**정함 (2026-10-13): 3. 껍데기를 없애고 안의 것을 남기는 "풀기"는 제어 블록과 호출 블록에 듣고, 접기 영역 풀기는 따로 둔다.**

- 까닭: Vim에서 접기(`zd`)와 둘레 지우기(vim-surround의 `ds`)는 서로 다른 가족이다. 메인테이너: "vim 단축키를 도입한 이유는 vim 사용자에게 친숙한 환경을 제공하기 위함입니다. 그점도 고려가 되면 좋겠습니다." 처음의 추천은 "풀기 하나가 셋 모두에 듣는다"(1)였다.
- 안쪽 블록을 고르고 풀면 그것을 담은 가장 가까운 제어 블록이 벗겨진다. Q8의 추천 1과 어긋나는 곳이고, 실행 취소로 되돌린다.
- 지금의 규칙 → [[02-interaction-rules#감싸기 · 풀기]], [[02-interaction-rules#접기 · 펼치기]]

### Q9. 실행 취소의 대상 (R7)

**정함 (2026-10-13): 1. 파일의 내용을 바꾸면 실행 취소의 대상이고, 보기 상태를 바꾸면 대상이 아니다.** 결과 기호(`←` / `=`)는 보기 상태에 넣는다.

- 까닭: 결과 기호는 "같은 내용을 어떻게 보여 주는가"이고 설정 화면에서 바꾸는 것이다. 이 구분은 [[0018-save-as-shown|ADR-0018]]이 파일 안에서 나눠 둔 "내용"과 "보기 상태"와 같다. 접기만 해도 "저장 안 됨" 표시는 뜬다.
- 지금의 규칙 → [[02-interaction-rules#6. 실행 취소]]

## 4. 호출 블록

### 4.1 호출 블록 펴 보기 (R6)

호출 블록 자리에 부르는 Method의 블록을 보기로만 보여 주는 기능이다. 접기 · 펴기 명령이 듣는 것에 호출 블록을 더한다. 지금의 규칙 → [[02-interaction-rules#호출 블록 펴 보기]], [[02-interaction-rules#펴 보인 곳의 접기 영역]]. 정한 과정은 [[2026-10-11-03-ux-review]]에 있다.

- **펴 보인 안쪽에서 접기 · 펴기. → 정함 (2026-10-13): 그것을 담은 가장 가까운 펴 보인 호출 블록이 접힌다.** 이 자리에서 만든 접기 영역 안이면 그 접기 영역이 먼저 접힌다.
- **펴 보인 곳의 접기 영역. → 정함 (2026-10-13).** 그 호출 블록 자리에만 생기고 Method의 원본은 그대로다.
	- **P1. 원본의 접기 영역과 가려 보이는가. → 정함: 똑같이 그린다 (1).**
	- **P2. Method가 바뀌어 묶어 둔 블록이 달라지면. → 정함: 남은 블록으로 줄어든다 (1).**
- **Q13. 펴 보인 블록을 고칠 수 있는가. → 정함 (2026-10-11): 고칠 수 없다 (E1).** 여기서 고치면 그 Method를 부르는 모든 곳이 함께 바뀌는데, 그것이 화면에서 보이지 않는다. 고르면 Method의 원래 블록으로 따라갈 수 있다.
- **Q14. 재귀. → 정함 (2026-10-11): 펴 보인 안쪽의 호출 블록도 펼 수 있다 (D2). 같은 Method가 세 번째로 펴지는 때부터 펼 때마다 알린다.** 다이어그램 자신을 첫 번째로 센다. 서로 다른 Method를 차례로 펴는 것은 재귀가 아니다(이 풀이는 2026-10-25에 확인받음 → [[2026-10-25-04-outbox-cleanup]]).
	- **Q14-a. 알림의 모양. → 정함 (2026-10-11): 먼저 펴고 알림 한 줄 (1).** 편집기에 입력을 막는 자리를 늘리지 않는다.
- **Q15. 펴진 접기 영역과 펴 보인 호출 블록의 모습. → 다시 정함 (2026-10-13): 접기 영역은 굵은 테두리 + 이름 띠, 펴 보인 호출 블록은 가는 점선 테두리 + 띠.** 2026-10-11의 "왼쪽 세로 막대"는 접기 영역이 겹치거나 이어질 때 알아보기 어려웠다. 접기 영역은 강조도 겸하므로 굵은 실선, 펴 보기는 강조가 아니므로 가는 점선.
	- **T1. 겹치거나 이어진 테두리 사이. → 정함 (2026-10-13): 틈을 둔다. 보통 블록은 테두리에 붙인다.** 모든 블록을 들이면 테두리와 블록의 선이 나란히 서서 호출 블록의 이중선처럼 보인다.
	- **T2. 펴 보인 호출 블록. → 정함 (2026-10-13): 가는 점선 테두리.** 띠만 두면 겹쳐 폈을 때 안쪽 호출 블록의 끝이 보이지 않는다.
	- **Q15-a. 둘을 가르는 법. → 다시 정함 (2026-10-13): 선의 모양과 색.** 흑백 인쇄에서도 실선과 점선으로 갈린다. 2026-10-11에는 "똑같이 그리고 색만 다르게"(C1)였다.
	- **Q15-b. While과 가르는 법. → 없어진 물음 (2026-10-13).** 사방을 두른 테두리는 While의 왼쪽 띠와 닮지 않았다.
	- **Q15-c. 이름 띠를 끄면. → 정함 (2026-10-11): 테두리도 함께 사라진다 (2).**
	- **Q15-d. 테두리의 색과 굵기. → 다시 정함 (2026-10-17): 파랑 3px로 두고, 고른 표시를 주황으로.** 같은 파랑이면 고른 상자가 저장되는 테두리처럼 보인다. 한때 접기 영역을 무채색으로 바꿨으나 메인테이너가 원하지 않았다. 견준 안 → M19 접기 영역 색 시안 https://claude.ai/artifact/R6G68CKoUa8aKsj8rhsRW9
	- 굵기 · 색 · 치수의 값 → [[04-visual-design#6. 선]], [[04-visual-design#3.3 밝은 기본 테마|3.3 밝은 기본 테마]]

### 4.2 호출 블록을 Method의 블록들로 바꾸기 (R5)

Q7의 "풀기"가 호출 블록에 듣는 경우다. Method로 빼기의 반대이고, 호출 블록 자리에 Method의 블록들이 복사되어 들어간다. 지금의 규칙 → [[02-interaction-rules#감싸기 · 풀기]]

- **Q16. 인자와 결과. → 정함 (2026-10-13): 글자는 그대로 복사한다.** 편집기는 글자 안을 검사하지 않으므로([[0022-call-name-follows-head|ADR-0022]]) Method 안의 이름(`a, lo, hi`)을 호출 블록의 인자(`a, lo, mid`)로 바꿔 적을 수 없다. 호출 블록에 적혀 있던 인자와 결과는 사라진다.
- **Q17. 이어진 곳이 없는 호출 블록. → 정함 (2026-10-13): 풀 수 없다.** 아무 일도 하지 않고 알린다.

### 4.3 부를 Method가 이 문서에 없을 때

2026-10-17에 메인테이너가 "호출할 서브루틴(다이어그램)이 없거나 다른 문서에 있을 수도 있음"이라고 적었다. 견준 안과 그림 → M18 호출 대상 시안 https://claude.ai/artifact/RXopHw9gKu4hmz5GvFo6Vx, 사본 `journal/assets/2026-10-17-call-target-study.html`. 지금의 규칙 → [[02-interaction-rules#호출 블록]]

- **CB1. 부를 것을 그리지 않았을 때. → 정함 (2026-10-17): 이름을 직접 적는 호출 블록, 보통 모양 (1).** 라이브러리 함수를 부르는 것은 잘못이 아니므로 점선과 `?`로 그리지 않는다. 빈 Method를 만들어야만 부를 수 있게 하면 함수마다 빈 다이어그램이 늘어난다.

## 6. 이미 정한 것 가운데 처음 읽는 눈에 놀라웠던 곳

독립 검토(요구사항 문서와 용어집만 건네받은 다른 검토자)가 다시 물은 것이다. 까닭을 알고 정한 것이므로 **그대로 두는 것이 기본**이고, 사용자가 처음 만났을 때 놀랄 수 있는 곳의 목록으로 남긴다. → [[requirements-rework#독립 검토와 같은 결론에 닿은 것]]

- **머리에서 괄호를 지우면 호출 블록의 인자가 사라지는 것.** 2026-10-13에 "기억하지 않는다"로 정했다. 같은 파일이 기기에 따라 다르게 되살아나지 않게 하려는 것이다.
- **인자 칸을 비울 수 없는 것.** Q4에서 공통 규칙의 한 경우가 되었다(2026-11-01).
- **접고 펴기가 실행 취소의 대상이 아닌 것.** 그림이 바뀌었는데 실행 취소가 듣지 않는다. 대신 "저장 안 됨" 표시는 뜬다(Q9).
- **붙여넣기가 고른 것을 바꿔 놓지 않고 뒤에 붙는 것.** 글자 편집기와 다르다. 구조 편집기에서는 뒤에 붙는 쪽이 안전하다고 보아 그대로 둔다.
- **새 Method가 맨 뒤에 생기고 화면이 그리로 가는 것.** 블록을 뺀 사용자가 보던 자리를 잃는다. → 2026-11-03에 [[#XM1. 새 Method의 자리|XM1]](뺀 Method 바로 뒤)과 [[#XM2. 빼고 난 뒤의 선택과 화면|XM2]](호출 블록으로 돌아옴)로 답했다.
- **머리에서 좌우 이동이 옆 다이어그램으로 가는데, 다이어그램은 위에서 아래로 쌓이는 것.** 키의 방향과 화면의 방향이 맞지 않을 때가 있다.

## 15. 2026-11-03의 결정

### TB1. 툴바에 For를 두지 않는다

**정함 (2026-11-03): For의 툴바 아이콘을 뺀다.** 메인테이너: "툴바에서 While과 For가 혼란스럽네요. 우리가 검토했던 것은 흐릿하게 기억이 나기는 하는데 나도 혼란스러우면 사용자는 많이 혼란스러울 것 같아요. For가 꼭 필요하다면 툴바에서라도 뺍시다." For는 While과 모양이 같고 헤더의 글로만 구분하므로([[#FB1. For 블록의 모양|FB1]]) 아이콘도 같았다. For 블록 자체는 MVP의 블록([[01-requirements#^r-blk|R-BLK-06]])이라 남기고, 넣기와 감싸기는 키(`a` `f`, `s` `f`), 다이어그램 › 삽입, 컨텍스트 메뉴, 커맨드 팔레트, 툴바의 "감싸기 ▾"로 한다.


### KP1. 처리 블록도 `a` + 종류 글자로

**정함 (2026-11-03): `a` `p`를 `o`와 같은 키로 더한다.** 메인테이너: "`ap`를 단축키에 추가해주세요. `o`와 동일하게 처리블록이 추가됩니다." 다른 블록을 `a` + 종류 글자로 넣으므로 처리 블록도 같은 방식으로 넣을 수 있게 했다. 같은 날 메인테이너: "`a`에는 `p`가 있는데 `A`에는 없습니다." 그래서 `A` `p`(= `O`)도 더했다. 감싸기의 `s` `p`는 두지 않는다(처리 블록은 다른 블록을 담지 않는다). 지금의 키 → [[03-keymap]]

### KP2. 빈 블록에서도 o · O는 삽입

**정함 (2026-11-03): 빈 블록을 선택하고 `o` · `O`(`a` `p` · `A` `p`)를 누르면, 빈 블록에 적지 않고 다른 블록처럼 뒤 · 앞에 새 처리 블록을 넣는다.** 메인테이너: "빈 처리블록에서 `O`하면 앞에 블록이 삽입되지 않고 포커스 블록 편집이 됩니다." 2026-10-10에 넣을 위치 모드(뒤 · 앞 · 안쪽)를 없애며 "빈 블록은 그 자리"로 정했는데([[2026-10-10-04-prototype-feedback]]), 왜 그렇게 했는지 묻고 나서 메인테이너: "oO는 편집이 아니라 삽입으로 해주세요." 제어 블록(`a i` 등)과 끌어 놓기는 그대로 빈 블록을 그 블록으로 바꾼다. Case의 빈 default 칸(`∅`, 아직 블록이 없는 자리)에서는 default 분기를 만들고 그 안에 블록 하나만 생긴다. 빈 갈래(`∅`)에 적으려면 `Enter` · `i`나 더블클릭으로 편집한다. 툴바의 처리 블록 아이콘을 누르는 것도 같은 명령이라 같다. 지금의 규칙 → [[02-interaction-rules#키보드로 이동하고 삽입하기]]

### CF1. 캔버스에는 포커스 테두리를 그리지 않는다

**정함 (2026-11-03): 선택한 것이 없을 때 캔버스 안쪽에 그리던 2px 포커스 테두리(`ui.accent`)를 없앤다.** 메인테이너: "포커스가 사라지면 전체 캔버스가 굵게 셀렉트되는데, 내 기억이 이렇게 캔버스가 셀렉트 되지 않게 하기로 한 것 같아요." 2026-10-10에 "캔버스에 들어오면 첫 블록을 고른다(캔버스 포커스 선 대신)"로 정했으나, 2026-10-16 시각 디자인에서 WCAG 2.4.7(포커스가 보여야 함)을 따라 다시 들어왔고([[2026-10-16-01-visual-design]]), "열면 고른 것이 없다"([[#OP1. 열면 고른 것이 없다|OP1]]) 뒤로 자주 보였다. Claude는 1px로 줄이기를 추천했고 메인테이너는 없애기를 골랐다. 선택한 것이 없는 동안에는 키가 캔버스로 가는지 화면으로 알 수 없다(WCAG 2.4.7에 모자람). 이동 키를 누르면 첫 블록이 선택되어 그 테두리가 보인다. 같은 날 [[#CF2. 캔버스의 포커스는 잠깐 보인다|CF2]]로 바꿨다.

### CF2. 캔버스의 포커스는 잠깐 보인다

**정함 (2026-11-03): 선택한 것이 없을 때 캔버스의 포커스 테두리를 1초만 보인다. 캔버스에 포커스가 올 때, 캔버스의 빈 곳을 클릭할 때, 아무 일도 하지 않은 키를 누를 때다. 환경 설정 "캔버스 포커스 테두리 늘 보이기"(기본은 꺼짐)를 켜면 늘 보인다.** [[#CF1. 캔버스에는 포커스 테두리를 그리지 않는다|CF1]]로 테두리를 없앤 뒤, Claude가 "선택한 것이 없는 동안에는 키가 어디로 가는지 알 수 없다"고 알렸고 메인테이너: "대안을 제안해주세요. 나는 사용자가 다이어그램을 검토하면서 다이어그램 자체에 집중할 수 있게 하고 싶었습니다." Claude가 시안 M53(https://claude.ai/artifact/BrHSHnwUmVXn9MuG4hYSni, 사본 `journal/assets/2026-11-03-canvas-focus-study.html`)에 다섯 안을 그렸고 1번(키보드로 들어오면 첫 블록 선택)을 추천했다. 메인테이너: "4번 1초 뒤 사라짐으로 하고, 캔버스에 포커스 있는 동안 의미 없는 키보드 입력이 있을 때마다 1초간 테두리 하면 어떨까요?" 이어서 "아 마우스 클릭도요". 잠깐만 보이는 표시는 WCAG 2.4.7을 채우지 못한다고 Claude가 짚고 늘 보이기 설정을 추천해 메인테이너가 골랐다. "아무 일도 하지 않은 키"는 누른 뒤에도 선택한 것이 없고 편집도 두 키 대기도 아닌 키다(Claude). 지금의 규칙 → [[02-interaction-rules#키보드로 이동하고 삽입하기]], [[04-visual-design#7.1 상태 표]]

### K4. 클릭하면 기다리던 키를 버린다

### CM1. 빈 캔버스의 컨텍스트 메뉴

### US1. 저장하지 않은 새 문서를 두고 다른 문서를 열 때

**정함 (2026-11-03): 한 번도 저장하지 않은 새 문서가 저장 안 된 채로 있을 때, 예제 · 새 문서 · 다른 파일을 열기 전에 묻는다(저장 · 버리고 열기 · 취소). 파일로 연 문서는 지금처럼 묻지 않는다.** 웹은 임시 보관이 있어 묻지 않기로 했으나, 임시 보관은 문서마다 남고 페이지를 다시 열 때는 가장 최근의 것 하나만 복원을 묻는다. 파일로 연 문서는 그 파일을 다시 열면 복원을 묻지만, 저장하지 않은 새 문서는 다른 문서를 열어 고친 뒤에는 다시 꺼낼 길이 없다(Claude가 코드에서 확인). 고르는 창의 세 안(새 문서일 때만 묻기, 언제나 묻기, 묻지 않고 최근 파일에 남기기) 가운데 메인테이너가 추천안을 골랐다. 예제 모달의 문구도 "파일로 연 문서는 그 파일을 다시 열면 복원할 수 있습니다"로 바꾼다.

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 8 KB까지는 조용히 복사하고, 8 KB를 넘으면 복사하되 "긴 링크를 자르는 앱이 있어 파일로 공유하는 것을 추천합니다"를 `warn`으로 알리고, 1 MB를 넘으면 복사하지 않고 파일로 공유하라고 알린다. 클립보드가 거절하면 링크를 모달에 넣어 손으로 복사하게 한다.** 8 KB는 메신저 · 메일 · 이슈 트래커가 링크를 자르기 시작하는 길이보다 넉넉히 짧고, 블록 150개쯤의 다이어그램이 든다. 막지 않고 알린다([[01-ux-overview]]의 원칙). 견준 것: 2 KB(옛 IE의 한도, 너무 일찍 경고), 경고 없이 늘 복사.

#### SH3. 보기 모드의 모습

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 메뉴 바 · 툴바 · 상태 표시줄 대신 한 줄의 막대(제품 이름 · 문서 이름 · 알림 · "보기 모드" · 파란 "편집하기" 버튼)만 둔다. 확대 · 스크롤 · 선택 이동 · 접기 · 펴기는 되고, 편집 키는 이유를 알리며, 컨텍스트 메뉴는 열지 않는다.** SequenceDiagram.org의 보기 모드처럼 그림이 화면을 다 쓰되, 알림이 보일 자리와 "이것이 무엇인지"(제품 이름)를 남긴다. 견준 것: 막대 없이 떠 있는 버튼 하나(알림을 보일 곳이 없음), 툴바만 숨기기(편집 화면과 다르지 않음).

#### SH4. 편집하기

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): "편집하기"는 같은 문서를 다시 열지 않고 읽기 전용만 푼다. 그 문서는 한 번도 저장하지 않은 새 문서(이름은 링크의 이름)라 [[#US1. 저장하지 않은 새 문서를 두고 다른 문서를 열 때|US1]]을 따른다. 보기 모드가 끝나면 주소창의 링크를 지워, 새로 고치면 링크가 아니라 로컬 백업을 복원한다.** 견준 것: 링크를 주소창에 남김(새로 고치면 편집한 것이 링크의 원본으로 되돌아간 듯 보임), 편집하기를 누르면 바로 저장 창.

#### SH5. 링크를 열 때

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 공유 링크로 연 페이지는 처음 온 사람의 예제 모달을 띄우지 않고, 로컬 백업의 "복원할까요?"도 묻지 않는다(백업은 남겨 다음에 묻는다). 열 수 없는 링크는 까닭(손상 · 너무 큼 · 더 새 버전 · 이 브라우저가 풀 수 없음)을 알리고 평소처럼 시작한다. 열린 탭에 붙여 넣은 링크도 열되, 저장하지 않은 새 문서는 US1대로 먼저 묻는다.** 링크를 누른 사람은 그 그림을 보러 왔다.

#### SH6. 메뉴의 자리

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 파일 메뉴의 내보내기 바로 아래 "공유 링크 복사"(영어 "Copy Share Link") 하나만 두고, 키와 툴바 버튼은 두지 않는다.** 자주 쓰는 명령이 아니고, 커맨드 팔레트로도 찾는다. 견준 것: 툴바 버튼, 내보내기 ▸ 안의 항목(내보내기는 파일을 만드는 것이라 다름).

### 2026-11-03 레인 3 (테마 · 고대비, 메인테이너가 추천안을 받아들임)

메인테이너(2026-11-03): "모두 지금 개발해주세요. 나의 선택이 필요한 부분은 일단 달님의 추천안을 수용하겠습니다." 아래는 테마([[01-requirements#^r-lay|R-LAY-08]])와 고대비 화면([[01-requirements#^r-nfr|R-NFR-07]])을 구현하며 Claude가 추천안으로 정한 것이다. 시안 없이 구현으로 바로 갔으므로, 써 보고 바꿀 수 있다.

#### TM1. 테마는 넷 (밝은 · 어두운 · 고대비 · 흑백 인쇄)

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 테마는 밝은 테마(`default`) · 어두운 테마(`dark`) · 고대비(`high-contrast`) · 흑백 인쇄(`print`)의 넷이고, 문서 설정에 이 차례로 나온다. 영어 화면의 이름은 Light · Dark · High contrast · Black and white print.** 어두운 테마는 M17 테마 시안의 초안을 바탕으로 밝은 테마와 같은 색상을 어두운 종이에 옮기고, 텍스트 4.5:1 · 선 3:1을 맞췄다. 고대비는 검은 종이에 흰 선과 흰 글자이고 텍스트와 선이 모두 7:1이다. 고대비를 어두운 쪽으로 한 것은 Windows 대비 테마의 관례(검은 바탕)를 따르고, 흰 종이에 검정은 흑백 인쇄(21:1)가 이미 맡기 때문이다. 밝은 테마의 파일 이름은 이미 저장된 파일과 맞도록 `default` 그대로 둔다. 견준 것: 밝은 · 어두운 둘만(고대비와 흑백 인쇄는 뒤로), 흰 종이의 고대비(흑백 인쇄와 거의 같아짐). 값 → [[04-visual-design#8. 테마]]

#### TM2. 테마는 문서 설정의 한 줄

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 테마는 다이어그램 › 문서 설정… 모달의 마지막 줄 "테마"(Theme)에서 고른다. 고르는 칸은 다른 줄과 같은 드롭다운이고, 이름 아래에 흐린 한 줄 "그림의 색. 저장되는 그림도 이 색"(The colors of the drawing, saved with it)을 둔다. 고르면 모달을 닫지 않아도 그림이 바로 바뀐다.** [[04-visual-design#12. 미결정 사항|시각 디자인의 미결정]] "테마를 선택하는 자리"의 답. 견준 것: 보기 메뉴의 하위 메뉴(파일에 저장되는 것이 보기 메뉴에 섞임), 툴바의 테마 버튼(자주 바꾸지 않는 것에 자리를 씀), 미리 보기 그림이 있는 카드(넷뿐이라 드롭다운으로 충분). → [[05-screen-layout]]

#### TM3. 테마를 바꾸는 것은 실행 취소의 대상

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 테마는 문서 설정이라 바꾸면 실행 취소의 대상이고 저장하지 않은 표시가 붙는다. 저장되는 그림, PNG, 인쇄는 고른 테마의 색 그대로다.** 다른 문서 설정(헤더 모양 · 그림 문구의 언어)과 같다([[#Q9. 실행 취소의 대상 (R7)|Q9]]). 읽기 전용에서는 바꿀 수 없다.

#### TM4. 편집 레이어는 종이의 종류를 따른다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 선택 · 호버 · 드롭 위치 · 오류 표시와 인라인 에디터의 색은 화면 색이 아니라 테마의 종류(종이가 밝은가 어두운가)를 따른다. 어두운 종이(어두운 테마 · 고대비)에는 더 밝은 주황 `#f08a4b`과 빨강 `#ff7b72`, 인라인 에디터는 그 테마의 종이 색 바탕에 `text.primary` 글자다.** 편집 레이어는 종이 위에 그려지므로, 화면 색을 따르면 밝은 화면의 어두운 종이에서 선택이 묻힌다. 네 테마 모두에서 편집 레이어의 표시가 3:1을 넘는다. 견준 것: 테마마다 편집 레이어 색을 따로(넷뿐이라 둘로 충분), 늘 같은 주황(어두운 종이 위 대비는 넘지만 인라인 에디터가 흰 칸으로 튐). → [[04-visual-design#3.4 화면 색]]

#### TM5. 고대비는 화면 색과 테마로 나눈다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 운영체제가 더 높은 대비를 요청하면(`prefers-contrast: more`) 편집 화면은 고대비 화면 색(텍스트 7:1)으로 바뀐다. 그림은 문서의 테마로 고대비를 고르고, 운영체제의 설정이 문서의 테마를 바꾸지는 않는다. 화면에서만 그림을 고대비로 보는 "보기 전용" 선택은 지금 두지 않는다.** 전에 시각 디자인 8장은 "그림은 흑백 인쇄 팔레트를 화면에서도 선택할 수 있게 하고, 화면에서만 바꾸는 보기 전용 선택을 따로 둔다"고 적었다. 보기 전용 선택은 화면의 그림과 저장되는 그림을 다르게 그려야 해서 화면 그대로 저장([[0018-save-as-shown|ADR-0018]])과 한 렌더러([[0030-swappable-drawing|ADR-0030]])에 예외를 만든다. 그래서 먼저 문서의 테마로 고대비를 두고, 보기 전용은 필요가 보이면 정하도록 미결정으로 남겼다([[04-visual-design#12. 미결정 사항]]). 편집 화면의 밝은 · 어두운 화면 색은 이미 기기의 밝기(`prefers-color-scheme`)를 따르므로 바꾸지 않았다. 견준 것: 운영체제가 고대비를 요청하면 그림도 화면에서 고대비로(보기 전용), 고대비 화면 색만 두고 그림의 고대비는 흑백 인쇄로.

메인테이너: "모두 지금 개발해주세요. 나의 선택이 필요한 부분은 일단 달님의 추천안을 수용하겠습니다." 아래는 Claude가 추천안으로 정하고 구현한 것이다. 시안 없이 정했으므로 써 보고 바꿀 수 있다. 구조의 선택(PDF 작성기, 외곽선, 그림 지문)은 [[0045-export-pipeline|ADR-0045]]에 있다.

#### XS1. 순수 SVG는 저장 파일에서 모델만 뺀 것

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 파일 › 내보내기 ▸ "SVG로 내보내기(그림만)…"는 저장 파일에서 `<metadata>`(모델)만 뺀 SVG를 `이름.svg`로 저장한다. 그림 · 서브셋 글꼴 · 종이 · 클래스 이름은 그대로 둔다.** 견준 것: 글꼴도 빼고 대체 글꼴에 맡기기(어디서나 같게 보이지 않음), 늘 외곽선으로(파일이 커지고, 외곽선은 문서 설정 [[#OL1. 텍스트 외곽선은 문서 설정|OL1]]이 이미 맡음). 문서가 외곽선 설정을 켰으면 순수 SVG도 외곽선이다. 이름에 "(그림만)"을 붙여 저장 파일(`.ns.svg`도 SVG)과 헷갈리지 않게 했다. 지금의 규칙 → [[06-web#1.4 SVG 내보내기 (그림만)]], [[01-file-format#4.2 순수 SVG]]

#### PD1. PDF는 앱이 바로 만든다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 파일 › 내보내기 ▸ "PDF로 내보내기…"는 앱 안에서 벡터 PDF를 만들어 `이름.pdf`로 저장한다(인쇄 창을 거치지 않음). 텍스트는 번들 글꼴의 외곽선이라 선택 · 검색은 되지 않고, 번들 글꼴에 없는 문자는 빈 상자다.** 견준 것: 브라우저의 "PDF로 저장"에 맡기기(명령이 아니라 인쇄 창의 한 선택이 되고 브라우저마다 다름), PDF 라이브러리(번들에 수백 KB). 한자 · 이모지가 든 문서는 인쇄([[#PT1. 인쇄는 인쇄 전용 보기로|PT1]])에서 "PDF로 저장"을 쓰면 대체 글꼴로 나온다(사용법에 적음). 지금의 규칙 → [[06-web#1.5 PDF 내보내기]]

#### PD2. 종이와 방향은 묻지 않는다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): PDF와 인쇄의 종이는 브라우저 언어의 지역으로 고른다: Letter를 쓰는 지역(미국 · 캐나다 · 멕시코 등, CLDR)은 Letter, 그 밖은 A4. 방향은 세로와 가로 가운데 페이지가 적게 나오는 쪽(같으면 세로). 여백은 네 쪽 36pt(12.7mm). 정하는 창은 두지 않는다.** 견준 것: 내보낼 때마다 묻는 창(한 번 더 누름), 환경 설정에 종이 크기(써 보고 필요하면 더함). 지금의 규칙 → [[02-layout#5. 인쇄와 PDF의 페이지]]

#### PD3. 줄이지 않고 블록 사이에서 자른다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 그림을 줄이지 않고(1px = 0.75pt) 여러 페이지로 나눈다. 텍스트가 든 칸(처리 · 호출 블록, 제어 블록의 헤더, 다이어그램의 헤더)을 가로지르지 않는 가장 먼 경계에서 자르고, 그런 경계가 없으면 페이지 끝에서 자른다. 폭이 넘치면 열로 나누고 아래로 먼저 읽는다. 종이만 있는 페이지는 뺀다. 페이지가 둘 이상이면 아래 가운데에 "n / N"을 적는다.** 견준 것: 페이지 폭에 맞춰 줄이기(가장 작은 글자 9pt · 가장 가는 선 0.75pt를 지키지 못함 → [[04-visual-design#9.2 배율과 출력]]), 쪽 번호를 늘 적기(한 장짜리에는 군더더기). 지금의 규칙 → [[02-layout#5. 인쇄와 PDF의 페이지]]

#### PT1. 인쇄는 인쇄 전용 보기로

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 파일 › 인쇄…와 `Ctrl`+`P`는 PDF와 같은 페이지를 인쇄 전용 보기에 넣고 브라우저의 인쇄 창을 연다. 브라우저의 메뉴로 인쇄해도 같은 보기가 인쇄된다(편집 화면이 인쇄되지 않음).** 브라우저가 `Ctrl`+`P`를 이미 인쇄로 쓰므로 같은 키를 둔다. 지금의 규칙 → [[06-web#1.6 인쇄]], [[03-keymap]]

#### DC1. 다른 도구로 고친 그림은 열 때 상태 표시줄에 경고

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 그림 부분이 앱이 저장한 것과 다르면(그림 지문이 다름), 파일을 열고 상태 표시줄에 경고한다: "“{이름}”의 그림이 다른 도구로 고쳐져 모델과 다를 수 있습니다. 편집기는 모델을 보여 줍니다. 저장하면 그림을 모델로 다시 그리므로, 그림에서만 고친 것은 사라집니다." 파일은 열고, 문서는 저장 안 됨이 되지 않는다.** 견준 것: 여는 것을 묻는 모달(열지 않을 까닭이 없음: 원본은 저장해야 바뀜), 열 때 모델로 다시 그려 비교(렌더러가 바뀐 판에서 옛 파일을 모두 "고쳐짐"이라 함 → [[0045-export-pipeline|ADR-0045]]). 지문이 없는 파일(이 기능 전에 저장)은 확인하지 않는다. 지금의 규칙 → [[01-file-format#4.1 그림 지문]], [[03-editor#6. 셸과의 연결]]

#### OL1. 텍스트 외곽선은 문서 설정

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 다이어그램 › 문서 설정에 "텍스트를 외곽선으로 저장"(기본은 끔)을 둔다. 켜면 저장 파일과 순수 SVG의 텍스트가 번들 글꼴의 외곽선이 되고, 화면은 그대로 텍스트로 그린다. 번들 글꼴에 없는 문자가 든 줄은 텍스트로 남는다.** 견준 것: 환경 설정(사람마다 파일이 달라짐 → [[0041-drawing-locale-in-document|ADR-0041]]과 같은 까닭), 내보내기에만 두기([[01-requirements#^r-fmt|R-FMT-10]]은 저장의 옵션). 문서 설정이라 파일과 함께 가고 undo 대상이다. 굵은 글자는 화면의 합성 굵게와 같은 두께로 그린다. 지금의 규칙 → [[01-file-format#4.3 텍스트 외곽선]], [[02-layout#3. SVG 렌더링]]

### 2026-11-03 레인 1 (접기 · 호출 블록, 메인테이너가 추천안을 받아들임)

접기([[01-requirements#^r-edit|R-EDIT-13]], [[01-requirements#^r-edit|R-EDIT-14]], [[01-requirements#^r-edit|R-EDIT-23]], [[01-requirements#^r-fmt|R-FMT-11]])와 호출 블록([[01-requirements#^r-edit|R-EDIT-15]], [[01-requirements#^r-edit|R-EDIT-16]], [[01-requirements#^r-edit|R-EDIT-08]], [[01-requirements#^r-blk|R-BLK-08]])을 만들면서 Claude가 정한 것이다. FD는 접기, CB3부터는 호출 블록이다(CB1 · CB2는 [[#4.3 부를 Method가 이 문서에 없을 때|4.3]]). 메인테이너(2026-11-03): "모두 지금 개발해주세요. 나의 선택이 필요한 부분은 일단 달님의 추천안을 수용하겠습니다." 그래서 시안 없이 지금의 규칙 · UX 결정 · 흔한 편집기의 관례에 가장 맞는 안을 골랐고, 메인테이너가 써 보고 다시 정한다.

#### FD1. 접기 · 펴기가 적용되는 곳 (Q20)

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 선택한 것이 접을 수 있는 것이면 그것에, 아니면 그것을 담는 가장 가까운 접을 수 있는 것에 적용된다.** 2026-10-11 M09의 Q20 추천 1이다. 제어 블록의 안쪽은 이름 없는 접기 영역처럼 보고, "블록이 하나뿐이면 접지 않는다"는 처리 블록이나 호출 블록 하나일 때만 남긴다(제어 블록 하나뿐인 분기는 접는다). 그 전의 규칙("선택한 것을 온전히 담는 가장 작은 접기 영역")은 깊은 곳의 블록을 선택하고 접으면 먼 바깥의 접기 영역이 접혔고, 큰 If 하나만 든 반복문은 접을 수 없었다. 지금의 규칙 → [[02-interaction-rules#접기 · 펼치기]]

#### FD2. 기본 이름을 고른 접기 영역

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 만들 때 아무것도 적지 않으면 그 접기 영역은 이름 없이 저장하고, 다시 묻지 않는다.** 기본 이름("첫 블록의 텍스트 외 n개")은 블록을 따라 바뀐다. 이름은 만들 때만 묻기로 했으므로(2026-10-13) 프로토타입처럼 "이미 물어봤음"을 따로 저장하지 않아도 된다. 2026-10-10 프로토타입 세션의 질문 2에 답한 것이다 → [[2026-10-10-02-prototype#만들며 생긴 질문 (메인테이너의 답을 기다림)]]

#### FD3. 펼친 뒤에도 보이는 접기 영역

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 펼친 접기 영역은 이름 띠를 켜 둔 동안 늘 테두리와 이름 띠로 보인다. 새 문서는 이름 띠가 켜져 있고, 보기 › 접기 영역 보기로 끈다.** 2026-10-13의 Q15와 Q15-c로 이미 그렇게 정해 둔 것을 2026-10-10 프로토타입 세션의 질문 1("평소에도 보여야 하나?")의 답으로 확인한 것이다.

#### FD4. 만들 때 적은 이름은 만들기와 한 단계

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 접기 영역을 만들자마자 접힌 칸에서 적은 이름은 만들기와 실행 취소 한 단계다.** 새 Method로 빼기와 바로 이어 적은 이름([[#XM2. 빼고 난 뒤의 선택과 화면|XM2]])과 같은 방식이다. 나중에 이름을 바꾸는 것은 따로 한 단계다.

#### FD5. 키보드로 지나가는 접힌 것과 이름 띠

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 접힌 줄과 접힌 칸은 방향키에서 블록 하나다. 펴진 접기 영역의 이름 띠는 분기 라벨([[#Q10. 고를 수 있는 것의 목록|Q10]])처럼 한 칸이라, 영역의 첫 블록에서 `↑`가 이름 띠에 선다. 이름 띠를 끄면 서지 않는다.** 이름 띠에 서야 키보드만으로 접기 영역을 선택해 이름을 바꾸거나 풀 수 있다. 견준 것: 이름 띠에는 서지 않고 마우스로만 선택.

#### FD6. 분기 라벨에서 접기

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 분기 라벨을 선택하고 접기 · 펴기를 쓰면 그 분기를 접고 편다.** FD1의 "선택한 것이 접을 수 있는 것이면 그것에"를 분기 라벨에 적용한 것이다. 미결정이던 "분기 라벨을 선택했을 때의 복사 · 감싸기 · 접기" 가운데 접기만 정했다 → [[02-interaction-rules#분기 라벨을 선택했을 때의 복사 · 감싸기]]

#### FD7. 접고 편 뒤의 선택

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 접으면 그 자리에 보이는 접힌 줄이나 접힌 칸이 선택된다. 제어 블록을 선택하고 그 안쪽을 접으면 제어 블록이 그대로 선택된다. 펴면 선택한 것이 그대로 남고, 이름 띠를 끈 채 접기 영역을 펴면 그 블록들이 선택된다.** 접혀서 보이지 않게 된 블록이 선택된 채로 남지 않게 하려는 것이다([[#Q19. 명령 뒤에 고르는 것|Q19]]의 "바뀐 것을 선택한다").

#### FD8. 이름 띠의 텍스트 자리

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 이름 띠와 펴 보기의 띠에서 텍스트는 왼쪽 끝에서 20px(접힌 칸과 같은 자리)에서 시작한다. 그 앞의 10px(`size.band-icon-room`)은 편집할 때만 보이는 펼침 삼각형(`▾`)의 자리다.** 접힌 칸의 `size.fold-icon-room`(20px)과 같은 방식이고, 화면과 파일의 기하가 같으므로 저장되는 그림에도 그 자리가 남는다([[0018-save-as-shown|ADR-0018]]). 견준 것: 삼각형을 `size.band-text-x`(10px) 안에 넣음(텍스트와 1px밖에 떨어지지 않음). → [[04-visual-design#5. 기하와 해부도]]

#### FD9. 접기만 · 펴기만

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): `zc`(접기만)와 `zo`(펴기만)는 FD1의 차례에서 펴진 것 · 접힌 것 가운데 가장 가까운 것에 적용되고, 없으면 알린다.** Vim에서 `zo`는 커서를 담은 닫힌 접기를, `zc`는 열린 접기를 찾는다.

#### FD10. 접기 영역 풀기 뒤의 선택

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 접기 영역(이름 띠, 접힌 칸)을 선택하고 풀면 그 블록들이 선택되고, 안의 블록을 선택하고 풀면 선택한 것이 그대로 남는다. 상태 표시줄에 푼 접기 영역의 이름을 알린다.** 제어 블록 풀기의 선택([[#Q19. 명령 뒤에 고르는 것|Q19]]: 남은 안의 블록들, 안쪽에서 풀었으면 그대로)과 같은 방식이다.

#### CB3. 펴 보인 블록의 화면 id

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 펴 보인 호출 블록 안에 그린 것의 화면 id는 호출 블록의 경로를 `/`로 이은 뒤에 모델의 id를 붙인 문자열이다(`b4/b17`). 선택에는 화면 id 대신 경로와 모델의 id를 따로 적는다.** 레이아웃의 상자와 클릭 영역은 문자열 하나로 찾는 것이 쉽고, 모델의 id에는 `/`가 없어 섞이지 않는다. 선택을 경로와 id로 두면 복사 · `gd`가 Method의 블록을 바로 찾는다. [[03-editor#미결정 사항]]에 있던 물음("문자열로 이을지, 배열로 둘지")에 답한 것이다 → [[03-editor#2. 상태와 선택]]

#### CB4. 호출 블록의 접기 · 펴기는 펴 보기

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 호출 블록 하나를 선택하고 접기 · 펴기(`f` `za`)를 쓰면 그 호출 블록을 펴 보고, 펴 보인 것을 선택하고 다시 쓰면 접는다.** 펴 보기를 접기 · 펴기 명령으로 한다는 규칙(R6, [[#4.1 호출 블록 펴 보기 (R6)|4.1]])과 FD1의 "선택한 것이 접을 수 있는 것이면 그것에"를 호출 블록에 적용한 것이다. 같은 문서의 Method를 부르는 호출 블록만 펴진다. 펴 보인 안쪽에서 쓰면 그 자리의 접기 영역, 없으면 담은 펴 보인 호출 블록이 접힌다(2026-10-13).

#### CB5. 펴 보인 호출 블록 안을 지나가는 키

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 펴 보인 호출 블록은 방향키에서 반복 블록처럼 다룬다. 띠가 한 칸(호출 블록)이고, `↓`로 안의 첫 블록에 들어가고 안의 첫 블록에서 `↑`로 띠에 돌아온다.** 펴진 접기 영역의 이름 띠(FD5)와 같은 방식이라 익힐 것이 없다. 견준 것: 펴 보인 블록은 마우스로만 선택.

#### CB6. 이름을 적어 호출하기

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 호출할 Method를 고르는 목록의 맨 끝, "새 Method를 만들고 호출" 다음에 "이름을 적어 호출하기"를 둔다. 고르면 이름을 적는 호출 블록을 넣고 바로 이름 칸을 연다. 호출할 Method 바꾸기에서 고르면 지금 보이는 이름이 칸에 든 채로 열린다. 칸 이동(`Tab`)은 인자 → 결과 → 이름 → 인자로 돈다.** 편집은 언제나 인자 칸에서 시작한다는 규칙([[02-interaction-rules#호출 블록]])을 지키고, 이름은 넣을 때와 바꿀 때만 먼저 연다. 견준 것: 모달로 이름을 묻기(입력을 막는 자리를 늘림, [[#4.1 호출 블록 펴 보기 (R6)|Q14-a]]와 같은 까닭으로 고르지 않음).

#### CB7. 이름을 적는 호출 블록의 빈 이름

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 한 번 적은 이름은 비울 수 없다(비우면 편집 전 이름으로 돌아가고 알린다, [[#Q4. 비울 수 없는 칸 (R2)|Q4]]). 새로 넣고 아무것도 적지 않고 닫으면 이름 없이 남고 "(이름 없음)"이 보인다.** 넣자마자 모달 없이 칸을 열기 때문에, 빈 채로 닫는 것을 막지는 않는다. 나중에 이름을 적으면 된다.

#### CB8. 호출 블록 풀기 뒤의 모습

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 호출 블록을 풀면 들어온 블록들이 선택되고, 펴 보였을 때의 모습 그대로 들어온다: Method에서 접혀 있던 접기 영역 · 분기는 접힌 채로, 이 자리의 접기 영역은 보통 접기 영역이 되어 접힘도 그대로, 안쪽에서 펴 보인 호출 블록은 펴 보인 채로.** 풀기의 선택([[#Q19. 명령 뒤에 고르는 것|Q19]]: 남은 안의 블록들)과 같고, 보던 모습이 풀기로 바뀌지 않게 하려는 것이다. Method의 접기 영역과 걸치거나 같은 범위인 이 자리의 접기 영역은 펴 보인 곳에서도 그려지지 않던 것이라 버린다.

#### CB9. 호출하는 Method로 가기

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): `gd`는 호출 블록에서는 그 Method의 헤더로, 펴 보인 블록에서는 Method의 원래 블록으로, 펴 보인 곳에서 본 Method의 접기 영역에서는 Method의 그 접기 영역으로 간다. 이름을 적는 호출 블록, 참조 대상이 없는 호출 블록에서는 가지 않고 알린다. 다이어그램 메뉴와 컨텍스트 메뉴에도 둔다.** Vim의 `gd`(정의로 가기)와 같은 뜻이다. 다른 문서의 Method로 가기([[01-requirements#^r-blk|R-BLK-09]], `P2`)는 그때 정한다.

#### CB10. 펴 보인 곳의 접기 영역이 걸칠 때

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 펴 보인 곳에서 Method의 접기 영역이나 그 자리의 다른 접기 영역과 범위가 같거나 끝에 걸치는 접기 영역은 만들지 않고 알린다.** 레이아웃은 그런 영역을 그리지 않으므로(Method가 바뀌어 그렇게 된 것은 그리지 않는다, P2), 만들어도 보이지 않기 때문이다. 보통 접기 영역의 규칙(같은 범위 · 걸침 거절)과 같다.

#### CB11. 다른 문서에 붙인 호출 블록

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 복사한 호출 블록은 부르던 Method의 이름을 클립에 담는다. 붙이면 그 문서에서 이름이 같은 Method를 부르고, 없으면 그 이름을 간직한 채 참조 대상 없음(점선과 `?`)이 된다.** 그 전에는 클립에 이름이 없어, 다른 문서에 붙이면 "(이름 없음)"이 되거나 우연히 같은 id의 다른 Method를 불렀다(backlog). 이름은 헤더를 따르므로([[0022-call-name-follows-head|ADR-0022]]) 이름이 같은 Method가 사용자가 기대하는 것이다. 감수하는 점: 같은 문서에서 복사한 뒤 Method의 이름을 바꾸고 붙이면 그 호출 블록은 참조 대상 없음이 된다(호출할 Method 바꾸기로 다시 잇는다).

#### CB12. 펴 보인 곳에서 Method의 접힘을 바꾸면

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 펴 보인 곳에 보이는 Method의 접기 영역 · 분기도 접고 펼 수 있고, 그것은 Method의 접힘이라 Method 자신과 그 Method를 펴 보인 모든 곳이 함께 바뀐다.** 모델은 펴 보인 블록의 접힘을 Method에 저장된 접힘으로 두었다([[01-model#2. 뷰 상태]]). 그 자리에만 접고 싶으면 그 자리의 접기 영역을 만든다([[01-requirements#^r-edit|R-EDIT-16]]).

### 2026-11-10 LLM · 에이전트 안내서 (M56, 메인테이너가 추천안을 받아들임)

메인테이너가 ChatGPT에게 "https://ariadnensd.com 으로 버블소트 알고리즘을 nsd로 그려주세요"라고 하자, ChatGPT는 첫 화면 HTML만 읽고 앱을 조작하려 하다가 "요청하신 AriadneNSD는 현재 페이지가 로딩 화면으로만 확인되어 제가 직접 다이어그램을 입력하거나 저장하지는 못했습니다."라고 답했다. 그래서 다른 AI가 공유 링크를 만들어 주고 사용자가 준 공유 링크를 읽게 하는 안내서를 시안 M56에서 물었다(안내서 초안 v1 ~ v3, haiku · sonnet · opus로 23번 실험). 메인테이너(2026-11-10): "모두 추천을 수용합니다." 또 "다른 에이전트에게 안내할 때, '공유 링크 복사' 기능을 추천해주세요."라고 했다. 견준 안과 실험 → 시안 M56 https://claude.ai/artifact/RruS69wvMC5iyCkoWW6Erm · 사본 `journal/assets/2026-11-09-llm-guide-study.html`. 지금의 규칙 → [[06-web#3.1 LLM · 에이전트를 위한 안내서]], [[06-web#3. 공유 URL과 보기 모드]], 요구사항 [[01-requirements#^r-web|R-WEB-10]]

#### LG1. 안내서의 자리와 언어

**정함 (2026-11-10, 4번): 영어 `/llms.txt` 하나를 사이트 루트에 두고, 첫 화면 `index.html`이 그것을 가리킨다(`<link rel="alternate" type="text/markdown">`, 메타 설명). 그리고 첫 화면 HTML 안에 사람에게는 보이지 않는 짧은 안내(`<section id="for-ai" hidden>`: 조작하지 말고 공유 링크를 주라, 링크 만드는 법의 요약, 규칙 넷, 아주 작은 예제 하나, `/llms.txt`를 가리킴)를 둔다. 사용법에 "AI에게 그려 달라고 하기" 한 꼭지를 둔다.** ChatGPT의 사례처럼 첫 화면만 읽고 링크를 따라가지 않는 도구에게는 가리키는 것만으로 모자라다. 자세한 것은 `/llms.txt` 하나에만 둔다. 영어는 모든 LLM이 가장 정확히 따르는 말이고 필드 이름 · 예제가 이미 영어다. 견준 것: 1 `/llms.txt`와 가리키기만, 2 영어와 한국어 두 벌(맞춰 둘 것이 둘), 3 사용법 안의 HTML 페이지만(관례를 아는 도구가 찾지 못함).

#### LG2. LLM이 만드는 링크의 꾸림

**정함 (2026-11-10, 1번): 공유 링크에 꾸림 `u`(`#ns1.u.<encodeURIComponent(봉투 JSON)>`)를 더하되 앱은 읽기만 한다. 길이 한도 · 크기 한도 · `parseModel`의 검증은 다른 꾸림과 같다.** `u`는 압축이 없어 코드 없이 손으로 만들 수 있고(실험에서 18번 열림), 사람과 LLM이 그대로 읽는다. 사람에게 추천하는 길(공유 링크 복사)과 AI에게 추천하는 길(공유 링크)이 같은 "누르면 열리는 링크"가 된다. 견준 것: 2 지금의 `j`(base64를 손으로 하면 한 글자만 틀려도 뒤가 깨짐), 3 `d`만(코드 도구가 없으면 만들 수 없음), 4 파일만, 5 짧은 글 DSL(문법 · 파서를 하나 더 지켜야 함). 구조의 결정 → [[0043-share-link-in-fragment|ADR-0043]]

#### LG3. 모델 JSON의 JSON Schema

**정함 (2026-11-10, 1번): `/model.schema.json`을 따로 두고 안내서에서 한 줄로 가리킨다. core의 테스트가 골든 파일들을 이 스키마로 검사해 파서와 어긋나지 않게 한다.** 도구 호출 · 구조화 출력을 쓰는 에이전트가 가져다 쓰고, 안내서는 가볍게 남는다. 스키마는 모양만 검사하고 불변식은 앱이 검사한다고 적는다. 견준 것: 2 안내서 안에 넣기(안내서가 두 배 가까이), 3 두지 않음.

#### LG4. 요구사항 ID

**정함 (2026-11-10, 1번): 새 요구사항 [[01-requirements#^r-web|R-WEB-10]](`P1`)으로 둔다. `u` 꾸림은 [[01-requirements#^r-web|R-WEB-05]]의 상세(웹 설계)에 적는다.** 웹이 내놓는 정적 파일이고 비용이 작으며, "AI에게 그려 달라 하면 링크가 온다"는 것이 처음 온 사람에게 쉬운 입구가 될 수 있다. 견준 것: 2 [[01-requirements#^r-web|R-WEB-05]]에 덧붙임(안내서와 링크 형식이 한 줄에 섞임), 3 R-SKILL 영역에(그것은 Claude skill, 이 안내서는 skill 없이 아무 LLM에게나 듣는 웹의 것).

#### LG5. 사용자가 준 링크를 LLM이 읽는 길

**정함 (2026-11-10, 1번): 공유 링크 복사는 지금처럼 `d` 하나를 만든다(앱의 코드는 바꾸지 않음). 안내서에 "코드를 못 돌리면 `d`의 내용을 짐작하지 말고 저장 파일이나 모델 JSON을 청하라"를 둔다.** 메인테이너의 기준("공유 링크 복사를 추천")과 가장 잘 맞고, 실험에서 코드 없는 모델도 지어내지 않고 파일을 청했다. 견준 것: 2 공유 링크 복사가 `u`나 `j`를 만듦(링크가 2 ~ 3배 길어져 사람끼리의 공유가 나빠짐), 3 "AI에게 줄 링크 복사" 메뉴를 하나 더([[#SH6. 메뉴의 자리|SH6]]과 어긋남). 써 보고 불편하면 3번을 다시 본다.

#### LG6. 열지 못한 링크의 까닭

**정함 (2026-11-10, 1번): 공유 링크를 열지 못하면 모달에 그 까닭(파서의 detail, 영어)을 보이고 "까닭 복사" 버튼을 둔다. 안내서에도 사용자가 그 글을 붙이면 고쳐서 다시 주라고 적는다.** LLM이 만든 링크가 깨지면 사용자는 무엇이 틀렸는지 그 LLM에게 말할 수 있어야 한다. 검증은 그대로 두고 고칠 길만 연다. 견준 것: 2 `u`에서 끝의 괄호만 맞춰 열기(파일과 같은 검증 QA-02에 예외가 생김, 1번을 써 본 뒤에 다시 봄), 3 지금처럼 한 줄 알림만.

- 만들며 Claude가 정한 것(메인테이너가 써 보고 정함): 상태 표시줄의 한 줄 대신 `editor`의 모달(`confirm`)로 보인다. 버튼이 있어야 하고, 페이지를 처음 열 때는 그 뒤의 "복원할까요?"보다 먼저 읽혀야 하기 때문이다. 모달의 제목은 시안의 그림대로 "AriadneNSD"(`confirm`에 제목을 줄 수 있게 더함). 버튼은 "닫기" / "까닭 복사"(기본). 모든 실패(손상 · 너무 큼 · 더 새 버전 · 풀 수 없음)에 같은 모달을 쓴다. 복사하는 글은 `AriadneNSD could not open the share link (<reason>): <detail>`과 안내서의 주소 한 줄.
