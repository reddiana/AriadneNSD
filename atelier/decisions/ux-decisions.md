## 2. 고치기 · 넣기 · 옮기기

### Q3. `Esc`의 뜻 (R1)

**정함 (2026-10-13): 3. `Enter`와 `Esc` 모두 적은 대로 받아들인다.** 고치기 전으로 되돌리려면 실행 취소를 한다. 받아들일 수 없어 다시 연 칸(겹친 머리 이름)에서만 `Esc`가 고치기 전으로 되돌린다.

- 까닭: Vim에서 `Esc`는 적은 것을 남기고 나가는 키라서, 되돌리기로 두면 Vim에 익은 손이 적은 글자를 매번 잃는다 → [[dr-0009-vim-keys|DR-0009]]. 처음의 추천은 "`Esc`는 되돌리기"(1)였다.
- 지금의 규칙 → [[02-interaction-rules#Event 헤더]]

## 3. 묶기 · 풀기 · 실행 취소

### Q7. 푸는 명령을 하나로 (R5)

**정함 (2026-10-13): 3. 껍데기를 없애고 안의 것을 남기는 "풀기"는 제어 블록과 호출 블록에 듣고, 접기 영역 풀기는 따로 둔다.**

- 까닭: Vim에서 접기(`zd`)와 둘레 지우기(vim-surround의 `ds`)는 서로 다른 가족이다. 메인테이너: "vim 단축키를 도입한 이유는 vim 사용자에게 친숙한 환경을 제공하기 위함입니다. 그점도 고려가 되면 좋겠습니다." 처음의 추천은 "풀기 하나가 셋 모두에 듣는다"(1)였다.
- 안쪽 블록을 고르고 풀면 그것을 담은 가장 가까운 제어 블록이 벗겨진다. Q8의 추천 1과 어긋나는 곳이고, 실행 취소로 되돌린다.
- 지금의 규칙 → [[02-interaction-rules#감싸기 · 풀기]], [[02-interaction-rules#접기 · 펼치기]]

### Q9. 실행 취소의 대상 (R7)

**정함 (2026-10-13): 1. 파일의 내용을 바꾸면 실행 취소의 대상이고, 보기 상태를 바꾸면 대상이 아니다.** 결과 기호(`←` / `=`)는 보기 상태에 넣는다.

- 까닭: 결과 기호는 "같은 내용을 어떻게 보여 주는가"이고 설정 화면에서 바꾸는 것이다. 이 구분은 [[0018-save-as-shown|ADR-0018]]이 파일 안에서 나눠 둔 "내용"과 "보기 상태"와 같다. 접기만 해도 "저장 안 됨" 표시는 뜬다.
- 지금의 규칙 → [[02-interaction-rules#6. 실행 취소]]

## 4. 호출 블록

### 4.1 호출 블록 펴 보기 (R6)

호출 블록 자리에 부르는 Method의 블록을 보기로만 보여 주는 기능이다. 접기 · 펴기 명령이 듣는 것에 호출 블록을 더한다. 지금의 규칙 → [[02-interaction-rules#호출 블록 펴 보기]], [[02-interaction-rules#펴 보인 곳의 접기 영역]]. 정한 과정은 [[2026-10-11-03-ux-review]]에 있다.

- **펴 보인 안쪽에서 접기 · 펴기. → 정함 (2026-10-13): 그것을 담은 가장 가까운 펴 보인 호출 블록이 접힌다.** 이 자리에서 만든 접기 영역 안이면 그 접기 영역이 먼저 접힌다.
- **펴 보인 곳의 접기 영역. → 정함 (2026-10-13).** 그 호출 블록 자리에만 생기고 Method의 원본은 그대로다.
	- **P1. 원본의 접기 영역과 가려 보이는가. → 정함: 똑같이 그린다 (1).**
	- **P2. Method가 바뀌어 묶어 둔 블록이 달라지면. → 정함: 남은 블록으로 줄어든다 (1).**
- **Q13. 펴 보인 블록을 고칠 수 있는가. → 정함 (2026-10-11): 고칠 수 없다 (E1).** 여기서 고치면 그 Method를 부르는 모든 곳이 함께 바뀌는데, 그것이 화면에서 보이지 않는다. 고르면 Method의 원래 블록으로 따라갈 수 있다.
- **Q14. 재귀. → 정함 (2026-10-11): 펴 보인 안쪽의 호출 블록도 펼 수 있다 (D2). 같은 Method가 세 번째로 펴지는 때부터 펼 때마다 알린다.** 다이어그램 자신을 첫 번째로 센다. 서로 다른 Method를 차례로 펴는 것은 재귀가 아니다(이 풀이는 2026-10-25에 확인받음 → [[2026-10-25-04-outbox-cleanup]]).
	- **Q14-a. 알림의 모양. → 정함 (2026-10-11): 먼저 펴고 알림 한 줄 (1).** 편집기에 입력을 막는 자리를 늘리지 않는다.
- **Q15. 펴진 접기 영역과 펴 보인 호출 블록의 모습. → 다시 정함 (2026-10-13): 접기 영역은 굵은 테두리 + 이름 띠, 펴 보인 호출 블록은 가는 점선 테두리 + 띠.** 2026-10-11의 "왼쪽 세로 막대"는 접기 영역이 겹치거나 이어질 때 알아보기 어려웠다. 접기 영역은 강조도 겸하므로 굵은 실선, 펴 보기는 강조가 아니므로 가는 점선.
	- **T1. 겹치거나 이어진 테두리 사이. → 정함 (2026-10-13): 틈을 둔다. 보통 블록은 테두리에 붙인다.** 모든 블록을 들이면 테두리와 블록의 선이 나란히 서서 호출 블록의 이중선처럼 보인다.
	- **T2. 펴 보인 호출 블록. → 정함 (2026-10-13): 가는 점선 테두리.** 띠만 두면 겹쳐 폈을 때 안쪽 호출 블록의 끝이 보이지 않는다.
	- **Q15-a. 둘을 가르는 법. → 다시 정함 (2026-10-13): 선의 모양과 색.** 흑백 인쇄에서도 실선과 점선으로 갈린다. 2026-10-11에는 "똑같이 그리고 색만 다르게"(C1)였다.
	- **Q15-b. While과 가르는 법. → 없어진 물음 (2026-10-13).** 사방을 두른 테두리는 While의 왼쪽 띠와 닮지 않았다.
	- **Q15-c. 이름 띠를 끄면. → 정함 (2026-10-11): 테두리도 함께 사라진다 (2).**
	- **Q15-d. 테두리의 색과 굵기. → 다시 정함 (2026-10-17): 파랑 3px로 두고, 고른 표시를 주황으로.** 같은 파랑이면 고른 상자가 저장되는 테두리처럼 보인다. 한때 접기 영역을 무채색으로 바꿨으나 메인테이너가 원하지 않았다. 견준 안 → M19 접기 영역 색 시안 https://claude.ai/artifact/R6G68CKoUa8aKsj8rhsRW9
	- 굵기 · 색 · 치수의 값 → [[04-visual-design#6. 선]], [[04-visual-design#3.3 밝은 기본 테마|3.3 밝은 기본 테마]]

### 4.2 호출 블록을 Method의 블록들로 바꾸기 (R5)

Q7의 "풀기"가 호출 블록에 듣는 경우다. Method로 빼기의 반대이고, 호출 블록 자리에 Method의 블록들이 복사되어 들어간다. 지금의 규칙 → [[02-interaction-rules#감싸기 · 풀기]]

- **Q16. 인자와 결과. → 정함 (2026-10-13): 글자는 그대로 복사한다.** 편집기는 글자 안을 검사하지 않으므로([[0022-call-name-follows-head|ADR-0022]]) Method 안의 이름(`a, lo, hi`)을 호출 블록의 인자(`a, lo, mid`)로 바꿔 적을 수 없다. 호출 블록에 적혀 있던 인자와 결과는 사라진다.
- **Q17. 이어진 곳이 없는 호출 블록. → 정함 (2026-10-13): 풀 수 없다.** 아무 일도 하지 않고 알린다.

### 4.3 부를 Method가 이 문서에 없을 때

2026-10-17에 메인테이너가 "호출할 서브루틴(다이어그램)이 없거나 다른 문서에 있을 수도 있음"이라고 적었다. 견준 안과 그림 → M18 호출 대상 시안 https://claude.ai/artifact/RXopHw9gKu4hmz5GvFo6Vx, 사본 `journal/assets/2026-10-17-call-target-study.html`. 지금의 규칙 → [[02-interaction-rules#호출 블록]]

- **CB1. 부를 것을 그리지 않았을 때. → 정함 (2026-10-17): 이름을 직접 적는 호출 블록, 보통 모양 (1).** 라이브러리 함수를 부르는 것은 잘못이 아니므로 점선과 `?`로 그리지 않는다. 빈 Method를 만들어야만 부를 수 있게 하면 함수마다 빈 다이어그램이 늘어난다.
- **CB2. 다른 문서의 Method. → 정함 (2026-10-17): 파일과 Method를 가리켜 둔다 (1).** 우선순위는 `P2`. 그 전에는 CB1의 이름을 적는 블록으로 부를 수 있다.

## 5. 고르기 · 이동 · 접기 · Method

### Q10. 고를 수 있는 것의 목록

**정함 (2026-10-13): 2. 갈래의 이름도 고를 수 있다.** 갈래 전용 키를 줄이고, 지우기 · 옮기기가 갈래에도 듣게 하려는 것이다. 처음의 추천은 "갈래는 고를 수 없게 두고 지금 갈래로 대신한다"(1)였다(방향키가 멈추는 곳이 늘어 If · Case를 지나가기 번거로워진다는 까닭).

- 정하지 않은 것 → [[02-interaction-rules#9. 미결정 사항]], [[02-interaction-rules#분기 라벨 선택]]

독립 검토(요구사항 문서와 용어집만 건네받은 다른 검토자)가 다시 물은 것이다. 까닭을 알고 정한 것이므로 **그대로 두는 것이 기본**이고, 사용자가 처음 만났을 때 놀랄 수 있는 곳의 목록으로 남긴다. → [[requirements-rework#독립 검토와 같은 결론에 닿은 것]]

**정함 (2026-10-31): 화면이 처음 열리거나 파일을 열면 아무 블록도 골라져 있지 않다.** 메인테이너(inbox): "화면이 열리면 선택된 블록 없을 것". 처음 보는 그림이 고른 테두리 없이 보이게 한다. 이동 키를 누르면 첫 블록을 고르는 규칙은 그대로다. "새로"(빈 문서)는 바로 적을 수 있게 빈 블록을 고른 채로 둔다(Claude). 명령 뒤에 무엇이 골라지는가(Q19의 남은 물음)는 그대로 열려 있다(Q19는 2026-11-01에 정함). 지금의 규칙 → [[02-interaction-rules#키보드로 이동하고 삽입하기]]

### MB1. 좁은 화면

**정함 (2026-10-31): 좁은 화면에서는 도구 모음 · 설정 · 안내를 접어 두고 다이어그램에 화면을 준다.** 메인테이너(inbox): "모바일에서 메뉴랑 옵션 선택 부분이 고정되어있어서 다이어그램을 보여줄 공간이 없음". 원칙만 정했다(→ [[01-ux-overview#2. UX 원칙]]). 펴는 단추의 자리와 모양은 편집기 설계([[03-editor#1. 화면 구성]])에서 정한다 (그 뒤 [[05-screen-layout|화면 배치]]의 "좁은 화면"에서 정함, 2026-11-01). 프로토타입 64번째 판은 폭 860px 이하에서 머리 줄의 "메뉴" · "안내" 단추로 편다(Claude).

### MB2. 좁은 화면의 툴바

**정함 (2026-11-01): 좁은 화면에 아래 줄을 두지 않는다. 되돌리기 · 다시 · 감싸기 · 도움말도 툴바에 둔다.** 처음엔 툴바를 두 줄로 지키려고 이 넷을 화면 아래 줄에 내렸다(Claude, [[05-screen-layout|화면 배치]]). 메인테이너(S26에서 써 보고): "감싸기가 화면 아래에 있어요. 이럴 필요가 있나요?" MVP를 폰 크기로 띄워 셋을 견줌(그림 `journal/assets/2026-11-01-narrow-wrap-options.png`): 1 지금(아래 줄), 2 감싸기만 툴바로, 3 아래 줄 없앰. 3을 고름(Claude의 추천). 툴바가 한 줄 늘어도 아래 줄이 없어져 다이어그램의 자리는 1과 같고, 버튼이 노트북과 같은 자리에 모인다. 2는 툴바도 늘고 아래 줄도 남아 가장 좁다

## 10. 2026-11-01의 결정

MVP에 드는 조작의 미결정을 한 번에 정했다(메인테이너: "mvp 전에 결정해야할 것들을 결정합시다"). 2026-10-11의 M09에서 물었던 것을 프로토타입 64번째 판의 그림으로 다시 그려 시안 M43 https://claude.ai/artifact/N7GhRyH47c5qs98V1N9uqH (사본 `journal/assets/2026-10-31-mvp-ux-questions-study.html`)에서 하나씩 물었다. 모두 Claude의 추천대로다. 접기 · 펴기가 듣는 곳(Q20)과 If ↔ Case로 바꾸는 모양은 MVP 뒤로 남겼다.

### Q1 · Q2. 고치기를 시작하는 방법과 더블클릭

**정함: Q1 1번 어디서나 같은 명령, Q2 1번 더블클릭은 어디서나 글자 고치기.** 키(`i` · `cc` · `Enter` · `F2`)는 64번째 판에서 이미 하나였고(Q1은 확인), 남은 것은 접힌 칸과 이름 띠의 더블클릭(펴기 · 접기)이었다. 메인테이너가 "1번이면 접고 펴는 것은 어떻게 하나요?"라고 물었고, Claude가 답했다: 접힌 칸과 이름 띠 앞에 이미 그려진 세모(`▸` `▾`)를 단추로 쓰고, 키(`za` `f` `zo` `zc`)와 오른쪽 클릭 메뉴는 그대로다. 고칠 글자가 없는 접힌 줄("⋯ 블록 n개")의 더블클릭은 펼치기로 남긴 것은 Claude가 정했다. 세모를 저장되는 그림에 넣지 않는 것도 Claude가 정했다(처음 M09의 추천 그대로). 지금의 규칙 → [[02-interaction-rules#텍스트 편집]], [[02-interaction-rules#접기 · 펼치기]]

### Q4. 비울 수 없는 칸 (R2)

**정함: 1번 머리의 이름을 비우면 고치기 전의 이름으로 돌아가고 칸이 닫힌다.** 비울 수 없는 칸은 어디서나 기본 글자로 돌아간다. 칸을 다시 여는 것은 이름이 겹칠 때뿐이다. 지금의 규칙 → [[02-interaction-rules#텍스트 편집]]

### Q6. 옮기기 명령 하나

**정함: 1번 "옮기기" 하나, `Alt`+방향키(`Alt`+`h` `j` `k` `l`도).** 블록은 위 · 아래, 갈래는 왼쪽 · 오른쪽, 머리를 골랐으면 다이어그램의 순서. 키는 VS Code의 줄 옮기기를 본떴다(Claude). If의 참 · 거짓을 맞바꿀 때 조건 글자를 뒤집지 않고 알리기만 하는 것, 줄 끝에서 제어 블록 밖으로 나오고 안으로는 들어가지 않는 것은 Claude가 정했다(M43에 적어 보인 대로). 지금의 규칙 → [[02-interaction-rules#이동]]

### Q10의 세부와 Q5. 갈래 이름 고르기, 갈래 넣기와 지우기

**정함: a 1번 If의 "참" · "거짓"도 고를 수 있다. b 1번 갈래의 첫 블록에서 `k`(↑)로 갈래 이름에 간다(내려갈 때는 멈추지 않음). c 1번 갈래 이름을 고르고 블록과 같은 키 `o` · `O` · `x`로 갈래를 넣고 지운다. `+` `-`는 없앤다.** c가 Q5(갈래를 앞에 넣는 방법)의 답이다. 메인테이너가 c에서 "갈래 안의 블록을 선택하고 oOx하면 어떻게 되나요?"라고 물었고, Claude가 답했다: 고른 것이 블록이면 블록에, 갈래 이름이면 갈래에 듣는다. 갈래 이름에서 `h` `l`은 옆 갈래 이름, `j`는 그 갈래의 첫 블록으로 가는 것, 다른 블록 넣기(`a` + 종류)는 갈래 이름에서 듣지 않는 것, `Shift`+`L`을 갈래 안 블록에서 바로 이름을 고치는 지름길로 남기는 것은 Claude가 정했다. 지금의 규칙 → [[02-interaction-rules#분기 라벨 선택]], [[02-interaction-rules#Case 블록]]

### Q8. 고른 것을 담은 것에 듣는 명령

**정함: 1번 지금대로. 풀기(`ds`) · 접기 영역 풀기(`zd`) · 접기 · 펴기(`za`)는 고른 것, 아니면 그것을 담은 가장 가까운 것에 듣고, 무엇에 들었는지 알린다.** 처음(2026-10-11)의 추천은 "내용을 바꾸는 명령은 고른 것에만"이었으나, 45번째 판에서 Vim의 `ds(`에 맞춰 `ds`가 안쪽에서도 듣게 바꾼 뒤라 추천을 바꿨다. 지금의 규칙 → [[02-interaction-rules#감싸기 · 풀기]]

### Q11. 좌우 이동의 겹

**정함: 2번 세 겹 그대로(`Ctrl`+`←` `→`를 남김).** 처음 추천은 1번(없앰)이었다. 이미 들어 있고 시험도 있어 MVP의 일이 늘지 않으므로 추천을 2번으로 바꿨다. 지금의 규칙 → [[02-interaction-rules#키보드로 이동하고 삽입하기]]

## 11. 웹 화면 (2026-11-01)

웹 버전(MVP)의 화면을 시안 M44 https://claude.ai/artifact/VpocjhpW3vtPJ8UHvoyFgX (사본 `journal/assets/2026-11-01-web-screen-study.html`)에서 하나씩 물어 W1 ~ W6을 모두 정했다(2026-11-01).

### W1. 웹 화면의 배치

**정함 (2026-11-01): 메뉴 막대 + 블록 아이콘의 도구 모음 (Structorizer처럼).** 첫 판은 SequenceDiagram.org를 본보기로 왼쪽 아이콘 막대를 추천했다. 메인테이너가 되물었다: "structorizer를 참고하고 싶습니다. 물론 웹버전은 아니지만 우리의 웹버전은 데스크톱버전과 거의 유사하니까요. structorizer의 아이콘바에 블록들이 있는 것이 편해보입니다." 둘째 판에서 모든 안의 도구 모음에 블록 모양 아이콘을 넣고 Structorizer식을 1번(추천)으로 두었고, 메인테이너가 1번을 골랐다. 견준 것: 도구 모음 한 줄과 ☰, 왼쪽 세로 막대, 리본. Structorizer와 SequenceDiagram.org의 화면은 Claude의 기억이고 안내서에서 확인하지 못했다. 지금의 규칙 → [[05-screen-layout|화면 배치]]

### W2. 블록 아이콘을 쓰는 법

**정함 (2026-11-01): 누르기는 언제나 넣기(뒤에, `Shift`는 앞에), 감싸기는 `Ctrl`+클릭 · 블록 위에 끌어 놓기 · `s` + 종류.** 메인테이너가 놓는 자리의 규칙을 제안했다: "끌어 놓을 때는 마우스 위치가 블록 위일 때는, 다른 블록을 포함할 수 있는 블록유형(루프라든지)이라면 그 불록을 포함. if블록이라면 참으로 포함, case라면 첫번째 브랜치로 포함. 포함할 수 없는 블록이라면 뒤에 추가. 블록 사이일 때는 그 위치에 추가." 누르기는 "현재 선택한 블록이 한개라면 뒤에 추가, 여러 블록을 영역으로 선택한 상태이면 블록 위일 때처럼"이었다. Claude는 끌어 놓기 규칙은 파일 탐색기의 관례와 같고 감싸기 규칙과도 맞아 일관된다고 보았고, 누르기는 고른 수에 따라 뜻이 바뀌어 블록 하나를 아이콘으로 감쌀 수 없고 같은 대상에 누르기와 끌기가 달리 움직인다고 짚어 "누르기는 언제나 넣기, `Ctrl`+클릭은 감싸기"를 추천했다. 메인테이너: "추천을 수용합니다". 세부는 Claude가 정했다: 빈 블록 위에 놓으면 그 빈 블록을 바꿈, 고른 블록 가운데 하나 위에 놓으면 고른 것 전체를 감쌈, 이미 있는 블록을 옮길 때는 블록 위에 놓아도 가까운 사이로, 고른 것이 없을 때 누르면 다이어그램의 맨 끝에. 지금의 규칙 → [[02-interaction-rules#블록 아이콘으로 삽입 · 감싸기]], [[02-interaction-rules#7. 드래그 앤 드롭]]

### W3. 파일 이름과 저장 상태

**정함 (2026-11-01): 파일이 하나면 탭 줄을 숨기고 메뉴 막대 오른쪽에 이름과 `●`, 둘 이상이면 탭 줄이 나타나 탭으로 옮김.** M44 넷째 판의 추천은 VS Code · IntelliJ처럼 "편집기 탭"이었다. 메인테이너: "w3도 다른 ide를 참고해서 의견 주세요". Claude가 VS Code · Sublime · IntelliJ · Eclipse · Visual Studio · Xcode · draw.io · Google Docs의 모습을 표로 견주었다(Claude의 지식, 이번에 확인하지 않음): IDE는 편집기 탭에 이름과 표시(`●` 또는 `*`), 웹 도구는 왼쪽 위 제목과 "저장됨" 글. 메인테이너: "탭이 하나 뿐일 때는 탭을 안보이게 하는 UI도 쓰이는 사례가 있나요?" macOS의 탭 창(Finder · TextEdit · 터미널), 예전 Safari, Windows Terminal의 설정이 그렇고 그때는 창 제목이 그 일을 맡는다고 답했다. 웹 MVP는 늘 문서 하나라 탭이 자리만 차지하므로 섞은 안을 추천했고 메인테이너가 골랐다. 표시는 `●`, 브라우저 탭 제목에도, 닫을 때 묻기는 Claude가 정했다. 지금의 규칙 → [[05-screen-layout|화면 배치]]

### W3-b. 임시 보관과 자동 저장

## 15. 2026-11-03의 결정

### TB1. 툴바에 For를 두지 않는다

**정함 (2026-11-03): For의 툴바 아이콘을 뺀다.** 메인테이너: "툴바에서 While과 For가 혼란스럽네요. 우리가 검토했던 것은 흐릿하게 기억이 나기는 하는데 나도 혼란스러우면 사용자는 많이 혼란스러울 것 같아요. For가 꼭 필요하다면 툴바에서라도 뺍시다." For는 While과 모양이 같고 헤더의 글로만 구분하므로([[#FB1. For 블록의 모양|FB1]]) 아이콘도 같았다. For 블록 자체는 MVP의 블록([[01-requirements#^r-blk|R-BLK-06]])이라 남기고, 넣기와 감싸기는 키(`a` `f`, `s` `f`), 다이어그램 › 삽입, 컨텍스트 메뉴, 커맨드 팔레트, 툴바의 "감싸기 ▾"로 한다.


### KP1. 처리 블록도 `a` + 종류 글자로

**정함 (2026-11-03): `a` `p`를 `o`와 같은 키로 더한다.** 메인테이너: "`ap`를 단축키에 추가해주세요. `o`와 동일하게 처리블록이 추가됩니다." 다른 블록을 `a` + 종류 글자로 넣으므로 처리 블록도 같은 방식으로 넣을 수 있게 했다. 같은 날 메인테이너: "`a`에는 `p`가 있는데 `A`에는 없습니다." 그래서 `A` `p`(= `O`)도 더했다. 감싸기의 `s` `p`는 두지 않는다(처리 블록은 다른 블록을 담지 않는다). 지금의 키 → [[03-keymap]]

### KP2. 빈 블록에서도 o · O는 삽입

**정함 (2026-11-03): 빈 블록을 선택하고 `o` · `O`(`a` `p` · `A` `p`)를 누르면, 빈 블록에 적지 않고 다른 블록처럼 뒤 · 앞에 새 처리 블록을 넣는다.** 메인테이너: "빈 처리블록에서 `O`하면 앞에 블록이 삽입되지 않고 포커스 블록 편집이 됩니다." 2026-10-10에 넣을 위치 모드(뒤 · 앞 · 안쪽)를 없애며 "빈 블록은 그 자리"로 정했는데([[2026-10-10-04-prototype-feedback]]), 왜 그렇게 했는지 묻고 나서 메인테이너: "oO는 편집이 아니라 삽입으로 해주세요." 제어 블록(`a i` 등)과 끌어 놓기는 그대로 빈 블록을 그 블록으로 바꾼다. Case의 빈 default 칸(`∅`, 아직 블록이 없는 자리)에서는 default 분기를 만들고 그 안에 블록 하나만 생긴다. 빈 갈래(`∅`)에 적으려면 `Enter` · `i`나 더블클릭으로 편집한다. 툴바의 처리 블록 아이콘을 누르는 것도 같은 명령이라 같다. 지금의 규칙 → [[02-interaction-rules#키보드로 이동하고 삽입하기]]

### CF1. 캔버스에는 포커스 테두리를 그리지 않는다

**정함 (2026-11-03): 선택한 것이 없을 때 캔버스 안쪽에 그리던 2px 포커스 테두리(`ui.accent`)를 없앤다.** 메인테이너: "포커스가 사라지면 전체 캔버스가 굵게 셀렉트되는데, 내 기억이 이렇게 캔버스가 셀렉트 되지 않게 하기로 한 것 같아요." 2026-10-10에 "캔버스에 들어오면 첫 블록을 고른다(캔버스 포커스 선 대신)"로 정했으나, 2026-10-16 시각 디자인에서 WCAG 2.4.7(포커스가 보여야 함)을 따라 다시 들어왔고([[2026-10-16-01-visual-design]]), "열면 고른 것이 없다"([[#OP1. 열면 고른 것이 없다|OP1]]) 뒤로 자주 보였다. Claude는 1px로 줄이기를 추천했고 메인테이너는 없애기를 골랐다. 선택한 것이 없는 동안에는 키가 캔버스로 가는지 화면으로 알 수 없다(WCAG 2.4.7에 모자람). 이동 키를 누르면 첫 블록이 선택되어 그 테두리가 보인다. 같은 날 [[#CF2. 캔버스의 포커스는 잠깐 보인다|CF2]]로 바꿨다.

### CF2. 캔버스의 포커스는 잠깐 보인다

**정함 (2026-11-03): 선택한 것이 없을 때 캔버스의 포커스 테두리를 1초만 보인다. 캔버스에 포커스가 올 때, 캔버스의 빈 곳을 클릭할 때, 아무 일도 하지 않은 키를 누를 때다. 환경 설정 "캔버스 포커스 테두리 늘 보이기"(기본은 꺼짐)를 켜면 늘 보인다.** [[#CF1. 캔버스에는 포커스 테두리를 그리지 않는다|CF1]]로 테두리를 없앤 뒤, Claude가 "선택한 것이 없는 동안에는 키가 어디로 가는지 알 수 없다"고 알렸고 메인테이너: "대안을 제안해주세요. 나는 사용자가 다이어그램을 검토하면서 다이어그램 자체에 집중할 수 있게 하고 싶었습니다." Claude가 시안 M53(https://claude.ai/artifact/BrHSHnwUmVXn9MuG4hYSni, 사본 `journal/assets/2026-11-03-canvas-focus-study.html`)에 다섯 안을 그렸고 1번(키보드로 들어오면 첫 블록 선택)을 추천했다. 메인테이너: "4번 1초 뒤 사라짐으로 하고, 캔버스에 포커스 있는 동안 의미 없는 키보드 입력이 있을 때마다 1초간 테두리 하면 어떨까요?" 이어서 "아 마우스 클릭도요". 잠깐만 보이는 표시는 WCAG 2.4.7을 채우지 못한다고 Claude가 짚고 늘 보이기 설정을 추천해 메인테이너가 골랐다. ### US1. 저장하지 않은 새 문서를 두고 다른 문서를 열 때

**정함 (2026-11-03): 한 번도 저장하지 않은 새 문서가 저장 안 된 채로 있을 때, 예제 · 새 문서 · 다른 파일을 열기 전에 묻는다(저장 · 버리고 열기 · 취소). 파일로 연 문서는 지금처럼 묻지 않는다.** 웹은 임시 보관이 있어 묻지 않기로 했으나, 임시 보관은 문서마다 남고 페이지를 다시 열 때는 가장 최근의 것 하나만 복원을 묻는다. 파일로 연 문서는 그 파일을 다시 열면 복원을 묻지만, 저장하지 않은 새 문서는 다른 문서를 열어 고친 뒤에는 다시 꺼낼 길이 없다(Claude가 코드에서 확인). 고르는 창의 세 안(새 문서일 때만 묻기, 언제나 묻기, 묻지 않고 최근 파일에 남기기) 가운데 메인테이너가 추천안을 골랐다. 예제 모달의 문구도 "파일로 연 문서는 그 파일을 다시 열면 복원할 수 있습니다"로 바꾼다.

**정함 (2026-11-03): 새 Method로 빼기([[01-requirements#^r-edit|R-EDIT-19]])로 만든 Method는 뺀 블록이 있던 Method 바로 뒤에 둔다. Event나 헤더 없는 다이어그램에서 뺐으면 Method 무리의 맨 뒤다.** "새 다이어그램은 그 종류의 맨 뒤"의 예외다. 견준 것: 언제나 Method 무리의 맨 뒤(지금까지), 뺀 다이어그램 바로 뒤. 이것으로 [[#6. 이미 정한 것 가운데 처음 읽는 눈에 놀라웠던 곳|6절]]의 "새 Method가 맨 뒤에 생기고 화면이 그리로 가는 것"에 답했다([[#XM2. 빼고 난 뒤의 선택과 화면|XM2]]와 함께). → 시안 M54(https://claude.ai/artifact/J11wWw9DVKUZkUP2ubT94n, 사본 `journal/assets/2026-11-03-extract-method-study.html`, 만드는 스크립트 `…-build.py` · `…-figs.test.ts`)

### XM2. 빼고 난 뒤의 선택과 화면

**정함 (2026-11-03): 새 Method의 이름을 적고 `Enter`를 누르면, 그 자리에 남은 호출 블록이 선택되고 화면이 그리로 돌아온다.** 견준 것: 새 Method의 헤더를 선택한 채 그 자리에 머묾, 새 Method의 첫 블록 선택. → 시안 M54(https://claude.ai/artifact/J11wWw9DVKUZkUP2ubT94n, 사본 `journal/assets/2026-11-03-extract-method-study.html`, 만드는 스크립트 `…-build.py` · `…-figs.test.ts`)

### XM3. 헤더 없는 다이어그램에서 블록에 m은 고르는 목록

**정함 (2026-11-03): 헤더 없는 다이어그램에서 블록을 선택하고 `m`을 누르면 키 힌트 자리(선택 바로 아래, K3)에 작은 목록 "1 새 Method로 빼기 · 2 Method 헤더 달기"를 띄운다. `Enter`나 `1`은 빼기, `2`는 Method 헤더 달기, `Esc`는 그만두기. 헤더가 있는 다이어그램에서는 `m`이 바로 빼기다. `e`는 그대로 Event 헤더 달기다. Method 헤더 달기는 메뉴 · 컨텍스트 메뉴 · 커맨드 팔레트에도 둔다.** 시안 M54 EX3의 3번(둘 가운데 고르게 묻는다). 같은 날 처음에는 1번(어디서나 빼기)으로 정했다가 메인테이너가 3번으로 바꿈. 견준 것: 블록에서 `m`은 어디서나 빼기(1번, Claude의 추천), 헤더 없는 다이어그램에서는 `m`이 Method 헤더 달기(지금대로, 2번)이고 빼기는 메뉴로만. → 시안 M54(https://claude.ai/artifact/J11wWw9DVKUZkUP2ubT94n, 사본 `journal/assets/2026-11-03-extract-method-study.html`, 만드는 스크립트 `…-build.py` · `…-figs.test.ts`)

### BS1. 브라우저 안의 문서는 열기 · 저장 창 안에서 고른다

**정함 (2026-11-03): 브라우저 안의 문서([[01-requirements#^r-web|R-WEB-09]])는 따로 된 메뉴 항목을 두지 않는다. 열기… 와 다른 이름으로 저장… 이 먼저 앱의 창을 띄우고, 거기서 "이 컴퓨터의 파일 / 이 브라우저"를 고른다(SequenceDiagram.org · draw.io의 방식). 창은 그 브라우저에서 마지막에 고른 쪽으로 열린다(처음에는 이 컴퓨터의 파일). 이 컴퓨터의 파일에서는 한 번 더 누르면 운영체제의 창이 열린다.** 메인테이너가 Claude의 추천(파일 메뉴에 "브라우저에 저장…" · "브라우저의 문서…" 두 항목)이 아닌 2번을 골랐다. 시안이 적은 2번의 좋은 점: 저장소가 늘어도(Google Drive) 메뉴는 그대로다. 견준 것: 파일 메뉴에 두 항목(추천), 최근 파일에 섞기. 메뉴 이름과 [[#US1. 저장하지 않은 새 문서를 두고 다른 문서를 열 때|US1]] 모달의 버튼은 구현 때 이에 맞춘다. → 시안 M55(https://claude.ai/artifact/CLz2Y1yXLYJfdn6q27Y1PV, 사본 `journal/assets/2026-11-03-browser-storage-study.html`)

### BS2. 브라우저가 그 문서의 자리

#### XS1. 순수 SVG는 저장 파일에서 모델만 뺀 것

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 파일 › 내보내기 ▸ "SVG로 내보내기(그림만)…"는 저장 파일에서 `<metadata>`(모델)만 뺀 SVG를 `이름.svg`로 저장한다. 그림 · 서브셋 글꼴 · 종이 · 클래스 이름은 그대로 둔다.** 견준 것: 글꼴도 빼고 대체 글꼴에 맡기기(어디서나 같게 보이지 않음), 늘 외곽선으로(파일이 커지고, 외곽선은 문서 설정 [[#OL1. 텍스트 외곽선은 문서 설정|OL1]]이 이미 맡음). 문서가 외곽선 설정을 켰으면 순수 SVG도 외곽선이다. 이름에 "(그림만)"을 붙여 저장 파일(`.ns.svg`도 SVG)과 헷갈리지 않게 했다. 지금의 규칙 → [[06-web#1.3 SVG 내보내기 (그림만)]], [[01-file-format#4.2 순수 SVG]]

#### PD1. PDF는 앱이 바로 만든다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 파일 › 내보내기 ▸ "PDF로 내보내기…"는 앱 안에서 벡터 PDF를 만들어 `이름.pdf`로 저장한다(인쇄 창을 거치지 않음). 텍스트는 번들 글꼴의 외곽선이라 선택 · 검색은 되지 않고, 번들 글꼴에 없는 문자는 빈 상자다.** 견준 것: 브라우저의 "PDF로 저장"에 맡기기(명령이 아니라 인쇄 창의 한 선택이 되고 브라우저마다 다름), PDF 라이브러리(번들에 수백 KB). 한자 · 이모지가 든 문서는 인쇄([[#PT1. 인쇄는 인쇄 전용 보기로|PT1]])에서 "PDF로 저장"을 쓰면 대체 글꼴로 나온다(사용법에 적음). 지금의 규칙 → [[06-web#1.4 PDF 내보내기]]

#### PD2. 종이와 방향은 묻지 않는다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): PDF와 인쇄의 종이는 브라우저 언어의 지역으로 고른다: Letter를 쓰는 지역(미국 · 캐나다 · 멕시코 등, CLDR)은 Letter, 그 밖은 A4. 방향은 세로와 가로 가운데 페이지가 적게 나오는 쪽(같으면 세로). 여백은 네 쪽 36pt(12.7mm). 정하는 창은 두지 않는다.** 견준 것: 내보낼 때마다 묻는 창(한 번 더 누름), 환경 설정에 종이 크기(써 보고 필요하면 더함). 지금의 규칙 → [[02-layout#5. 인쇄와 PDF의 페이지]]

#### PD3. 줄이지 않고 블록 사이에서 자른다

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 그림을 줄이지 않고(1px = 0.75pt) 여러 페이지로 나눈다. 텍스트가 든 칸(처리 · 호출 블록, 제어 블록의 헤더, 다이어그램의 헤더)을 가로지르지 않는 가장 먼 경계에서 자르고, 그런 경계가 없으면 페이지 끝에서 자른다. 폭이 넘치면 열로 나누고 아래로 먼저 읽는다. 종이만 있는 페이지는 뺀다. 페이지가 둘 이상이면 아래 가운데에 "n / N"을 적는다.** 견준 것: 페이지 폭에 맞춰 줄이기(가장 작은 글자 9pt · 가장 가는 선 0.75pt를 지키지 못함 → [[04-visual-design#9.2 배율과 출력]]), 쪽 번호를 늘 적기(한 장짜리에는 군더더기). 지금의 규칙 → [[02-layout#5. 인쇄와 PDF의 페이지]]

#### DC1. 다른 도구로 고친 그림은 열 때 상태 표시줄에 경고

**정함 (2026-11-03, Claude의 추천안 — 메인테이너가 써 보고 정함): 그림 부분이 앱이 저장한 것과 다르면(그림 지문이 다름), 파일을 열고 상태 표시줄에 경고한다: "“{이름}”의 그림이 다른 도구로 고쳐져 모델과 다를 수 있습니다. 편집기는 모델을 보여 줍니다. 저장하면 그림을 모델로 다시 그리므로, 그림에서만 고친 것은 사라집니다." 파일은 열고, 문서는 저장 안 됨이 되지 않는다.** 견준 것: 여는 것을 묻는 모달(열지 않을 까닭이 없음: 원본은 저장해야 바뀜), 열 때 모델로 다시 그려 비교(렌더러가 바뀐 판에서 옛 파일을 모두 "고쳐짐"이라 함 → [[0042-export-pipeline|ADR-0042]]). 지문이 없는 파일(이 기능 전에 저장)은 확인하지 않는다. 지금의 규칙 → [[01-file-format#4.1 그림 지문]], [[03-editor#6. 셸과의 연결]]
