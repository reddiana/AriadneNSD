# DR-0023: 서브 세션은 허브 하나가 주제마다 열고, 긴 작업은 허브가 허락한다

> [!NOTE] 이후 변경
> - 2026-11-28: 허브는 서브 세션 관리에만 집중하고, 주제 일(코드 · 시안 · 문서 정리)은 작아도 서브 세션에 맡김 → [[how-we-work#허브와 서브 세션]]
> - 2026-11-28: 시간 테스트는 긴 작업에서 뺌. T-1126은 로컬에서 `SKIP_TIMING=1`로 skip하고 판정은 CI, T-0171은 시간 제한만 늘림 → [[how-we-work#2. 세션의 리듬]]
> - 2026-11-28: 서브 세션은 턴마다 보고 첫 줄에 상태 한 줄(에이전트 도는 중 / 답 기다림 / 끝), 허브는 넘기기 전에 먼저 확인 → [[how-we-work#허브와 서브 세션]]
> - 2026-11-28: 허브는 서브 세션이 살아 있는 동안 비우거나 넘기지 않음, 서브 세션 지시문에 허브의 세션 id, 작은 일은 서브 세션 대신 허브의 에이전트로 → [[how-we-work#허브와 서브 세션]]

## 배경

Claude Code 데스크톱 앱에서는 세션이 다른 세션을 열 수 있다(`start_session`). 연 세션(서브 세션)이 한 턴을 마치면 연 세션에 보고가 간다. 2026-11-28에 이것을 처음 여럿 써 보며 세 가지가 드러났다.

- **매듭을 지을 수 없음:** 백그라운드 에이전트가 도는 세션은 매듭지을 수 없다(그 커밋이 정리에 들어가야 한다). 기다리기 아까워 계속 진도를 나가면 한 세션에 여러 주제가 뒤섞인다. 메인테이너: "에이전트가 돌고있는 세션을 매듭지을 수 없고, 시간이 아까워 계속 진도 나가면 세션이 여러 주제로 뒤죽박죽되는 것 때문에 서브 세션을 쓰려는 것입니다."
- **3단 구조:** 허브가 연 M86 세션이 "UX 점검은 큰 일이니 새 세션에서"라며 스스로 세션을 열었다. 마무리 10번("다음 할 일이 분명하면 새 세션")이 어느 세션이 여는지 말하지 않아서였다. 손자 세션의 보고는 허브에 닿지 않았고, 세 세션이 worktree 없이 한 폴더를 나눠 썼다. 메인테이너: "지금 세션의 서브세션에서 다시 서브세션이 실행됐습니다. 구조가 이건 좀 아니다 싶네요."
- **겹치는 긴 작업:** 나란히 돈 검사가 CPU를 다투어 시간 테스트 T-0171이 거짓으로 실패했다. 세션마다 E2E를 돌리면 같은 검사를 여러 번 한다.

## 결정 기준

- 메인테이너가 대화하는 세션은 언제든 매듭지을 수 있어야 한다.
- 보고가 한 곳에 모여, 누가 무엇을 하는지 한눈에 보여야 한다.
- 같은 파일을 두 세션이 덮어쓰지 않아야 한다.
- push · E2E 같은 긴 작업은 겹치지 않고, 묶어서 한 번에.

## 검토한 대안

### 대안 A: 허브 하나만 세션을 연다

- 장점: 보고가 모두 허브로 온다. 단이 하나라 구조가 늘 보인다. 업계의 orchestrator-workers(supervisor, hub-and-spoke) 구조와 같다 → [[orchestrator-and-sub-sessions]]
- 단점: 서브 세션이 새 세션을 원하면 허브를 거쳐야 한다.

### 대안 B: 이어달리기만(새 세션을 연 세션은 바로 자신을 보관)

- 장점: 살아 있는 세션이 늘 하나라 단순하다.
- 단점: 나란히 돌릴 수 없어, 에이전트를 기다리는 동안의 문제가 그대로다.

### 대안 C: 지금처럼 아무 데서나 열고, 같은 파일을 쓰는 세션에만 worktree

- 장점: 손이 덜 간다.
- 단점: 계층이 깊어져 보고가 중간에서 막힌다.

## 결정

대안 A. 메인테이너가 고름(2026-11-28).

- **허브:** 메인테이너와 대화하며 `atelier/`를 맡는 세션 하나. 서브 세션은 허브만 연다(`start_session`). 서브 세션은 세션을 열지 않고, 필요하면 보고에 "새 세션 추천: …"만 적는다.
- **주제 하나에 서브 세션 하나.** 코드를 쓰는 서브 세션은 worktree로 연다.
- **기록:** 서브 세션은 매듭 · 마무리 때 자기 주제의 세션 기록을 직접 쓰고, 허브에 "기록 파일 · status에 반영할 것"을 보낸다. 함께 고치는 문서(`status` · `outbox` · `sessions/README` · `usage` · `journal/timeline`)는 허브만 쓴다.
- **긴 작업은 허브가 허락한다:** push, E2E, 전체 `pnpm check`, 커버리지, 사이트 빌드, 시간 테스트는 서브 세션이 "긴 작업 요청"을 보내 허락받고 돌린다. 허브는 시간과 토큰이 덜 드는 쪽으로 "지금 하세요" · "기다리세요" · "하지 마세요(○○가 합쳐서 함)"로 답하고, [[status#긴 작업 대기열]]에 적는다. 메인테이너: "실제 푸시나 e2e 테스트는 각 세션에서 수행하지만 허브 세션의 허락을 받고, 허브 세션은 시간과 토큰을 절약하는 방향으로 어느 세션이 언제 할지를 결정합니다."
- **허브를 넘길 때:** 마무리 10번에서 새 세션을 열면, 그 세션을 맨 위로 떼어(`detach_session`) 새 허브로 삼고 지금 허브는 보관한다.

## 결과

- 좋아지는 점: 허브는 대화와 조율만 해서 언제든 매듭지을 수 있다. 주제마다 세션 기록이 하나씩 남는다. 긴 작업이 겹치지 않는다.
- 감수하는 점: 서브 세션의 400자 보고만으로는 허브가 자세한 것을 모르므로, 필요하면 서브 세션의 대화를 읽어야 한다. worktree마다 `pnpm install`이 든다. 떼어 낸 세션(맨 위로 옮긴 세션)의 보고는 허브에 오지 않으므로, 그런 세션은 중요한 결정을 허브에 직접 보낸다.
- 후속 작업: 운영 방식의 설명은 [[how-we-work#허브와 서브 세션]], 지시는 `CLAUDE.md`의 "세션은 허브 하나가 연다".
