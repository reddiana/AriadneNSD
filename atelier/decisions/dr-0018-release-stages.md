# DR-0018: MVP 다음은 웹 베타와 웹 1.0이고, 파일 형식은 웹 1.0부터 약속한다

## 배경

메인테이너가 물었다: "MVP 다음은 무엇인가요? Beta버전인가요?"(2026-11-02).

MVP 다음에 무엇이 오는지는 두 갈래만 정해져 있었다. 웹에서는 MVP에서 미룬 기능을 다음 판들에 넣고([[01-requirements#5. MVP 범위]], [[dr-0015-mvp-scope|DR-0015]]), 배포 대상은 웹 → Obsidian → 데스크톱 순서다([[dr-0002-development-order|DR-0002]]). 둘 사이의 순서와 단계의 이름은 정하지 않았다.

그런데 문서 곳곳에 정의 없는 단계 이름이 쓰이고 있었다.

- "웹 베타": 후원 버튼을 README에 다는 때([[01-requirements#^r-all|R-ALL-01]], 2026-10-10 메인테이너: "웹버전 베타버전 출시하면 합시다"), 비공개 문제 알리기 채널을 정하는 때([[01-requirements#^r-rep|R-REP-01]]) → [[backlog#출시 무렵과 그 뒤]]
- "공개 출시 전": 상표 검색 → [[names-and-registries#확인하지 않은 것]]
- "출시 뒤": 우선순위 `P3`의 뜻 → [[01-requirements]]의 읽는 법
- "첫 출시 전까지는 버전을 올리지 않고 고칠 수 있다": 파일 형식 → [[01-file-format]]. 그런데 CLAUDE.md와 README는 MVP를 "첫 출시"라고 부른다. MVP는 이미 펴냈으므로, 이 문장대로라면 형식을 더는 버전 없이 고칠 수 없다.

견준 안과 그림은 시안 M47에 있다: https://claude.ai/artifact/UR5XBcsn55ZpgMAZZeqvFN (저장소의 사본 `journal/assets/2026-11-02-release-stages-study.html`).

## 결정 기준

- 단계마다 사용자에게 하는 약속(파일이 열리는가, 키가 바뀌는가)이 다르고, 그 약속이 이름에서 보인다.
- 지금 "베타 무렵" · "출시 전"으로 흩어진 일이 어느 문턱에 드는지 하나로 정해진다.
- 혼자 만드는 제품이 감당할 수 있는 문턱의 수다.
- 메인테이너가 주로 쓰는 Obsidian에서 쓸 날이 너무 늦지 않다.

## 검토한 대안

물음은 다섯이다. 선택지마다의 그림은 M47에 있다.

### S1. 단계의 틀 (웹)

1. MVP → 베타 → 1.0: (고름) 베타는 널리 알리기 시작하는 때, 1.0은 기능과 키가 굳는 때. (Claude의 추천)
2. MVP → 1.0: 가장 단순하다. 알리는 때와 굳는 때가 하나라, 1.0 전에는 알릴 수 없다.
3. MVP → 알파 → 베타 → RC → 1.0: 익숙한 나눔이지만 혼자 만드는 제품에는 문턱이 많고, MVP와 알파가 하는 일이 겹친다.

### S2. 저장한 파일이 뒤의 판에서도 열린다고 약속하는 때

약속한 뒤에는 형식을 바꿀 때마다 버전을 올리고 마이그레이션을 둔다([[01-file-format#5. 버전 관리]]).

1. 지금(MVP)부터: MVP로 저장한 파일도 지킨다. outbox에 남은 글꼴 이름 · 고정 문구의 언어를 바꾸는 것도 마이그레이션이 된다.
2. 웹 베타부터: 널리 알린 뒤부터 지킨다. MVP로 저장한 파일은 뒤에 열리지 않을 수 있으므로 MVP 화면과 README에 그렇게 적는다. (Claude의 추천)
3. 웹 1.0부터: (고름) 형식을 고칠 여유가 가장 길지만, 베타를 알린 뒤 저장한 파일이 열리지 않을 수 있다. 모델은 이미 미룬 기능까지 담도록 설계해([[01-model]]) 그 여유가 그렇게 필요하지 않다.

### S3. Obsidian 플러그인을 시작하는 때

1. 웹 베타 전(MVP 바로 다음): 가장 빨리 쓰지만, 베타의 문턱과 Obsidian 셸을 함께 하게 된다.
2. 웹 베타 동안: (고름) BRAT 플러그인으로 GitHub에서 바로 설치하는 Obsidian 베타. 커뮤니티 플러그인 목록에 올리는 것(Obsidian 1.0)은 웹 1.0 뒤. 웹 1.0으로 굳히기 전에 두 곳이 같은 파일을 읽고 써 본다. (Claude의 추천)
3. 웹 1.0 뒤: 형식과 키가 굳은 뒤라 셸만 만들면 되지만, Obsidian에서 쓰는 날이 가장 늦고 Obsidian에서만 드러나는 문제가 1.0 뒤에 나온다.

### S4. 웹 1.0의 기능

다른 문서의 Method를 부르는 호출(`P2`)은 어느 안에서도 1.0 뒤다.

1. MVP 기능 그대로 굳히기: 1.0이 가장 빠르다. 접기와 펴 보기가 1.0에 없다.
2. MVP에서 미룬 편집 기능까지: 접기 · 접기 영역, Method로 빼기, 호출 펴 보기 · 풀기, 이름을 적는 호출, 블록 글자의 언어 · 구문 강조, 테마. DR-0015가 "MVP 다음 판들"로 미룬 목록 그대로다. 펴 보기의 성능([[03-architecture#7. 위험과 검증이 필요한 사항]])과 접기가 듣는 곳(Q20)을 베타 동안 푼다. (Claude의 추천)
3. 웹의 `P1` 모두: (고름) 2에 더해 공유 URL · 보기 모드, 순수 SVG · PDF · 인쇄, 그림만 고친 파일 알림, 글자를 외곽선으로, 고대비 화면. 1.0이 가장 늦다. 이것들은 1.0 뒤에 더해도 파일에 영향이 없다.

### S5. 버전 번호

앱의 버전이고, 파일 형식의 버전(`v1`)과는 따로 간다.

1. SemVer: (고름) MVP는 `0.1.0`, 판을 낼 때마다 `0.y`를 올리고, 웹 1.0은 `1.0.0`. 단계는 번호가 아니라 이름으로 알린다. npm과 Obsidian 플러그인(manifest의 `version`)이 쓰는 방식이다. (Claude의 추천)
2. 날짜(CalVer, `2026.11`): 언제 낸 판인지 보이지만, 1.0이라는 약속이 번호에 드러나지 않는다.
3. 번호 없이 단계 이름만: 할 일이 없지만, 결함을 알릴 때 커밋 해시로만 판을 말할 수 있고 Obsidian 플러그인에는 번호가 꼭 있어야 한다.

## 결정

메인테이너가 M47에서 고르는 창으로 정했다(2026-11-02): **S1 1번**, **S2 3번**, **S3 2번**, **S4 3번**, **S5 1번**. S1 · S3 · S5는 Claude의 추천이고, S2(추천은 2번 웹 베타부터)와 S4(추천은 2번 미룬 편집 기능까지)는 추천과 다르다. 파일 형식을 웹 1.0까지 열어 두고, 웹 1.0은 웹의 `P1`을 모두 갖춘 판으로 한다.

| 단계 | 버전 | 누구에게 | 파일 형식 |
| --- | --- | --- | --- |
| MVP (지금) | `0.1.0`부터 | 링크를 아는 사람. 널리 알리지 않는다 | 버전을 올리지 않고 고칠 수 있다 |
| 웹 베타 | `0.y` | 널리 알린다 | 같음. 1.0 전에 저장한 파일은 뒤에 열리지 않을 수 있다고 알린다 |
| 웹 1.0 | `1.0.0` | 모두 | 저장한 파일은 뒤의 모든 판이 연다. 형식을 바꾸면 버전을 올리고 마이그레이션을 둔다 |

웹 베타의 문턱:

- 메인테이너가 MVP를 실제 일에 써 보고, 데이터를 잃는 결함이 없다([[defects]]).
- 주소를 정한다: `ariadnensd.com`으로 옮길지. 알린 뒤에 바꾸면 링크가 깨진다.
- 상표 검색(KIPRIS · USPTO · EUIPO)
- 사용법 `/manual/`
- 비공개 문제 알리기 채널([[01-requirements#^r-rep|R-REP-01]]), README의 후원 버튼([[01-requirements#^r-all|R-ALL-01]])
- Firefox · Safari · 휴대폰에서 써 본다.
- 앱과 README에 "1.0 전에 저장한 파일은 뒤의 판에서 열리지 않을 수 있습니다"를 알린다.

웹 베타 동안: 웹의 `P1` 기능을 판마다 더한다. Obsidian 베타를 BRAT(GitHub 저장소에서 바로 설치하는 Obsidian 플러그인)로 시작한다.

웹 1.0의 문턱:

- 웹의 `P1` 기능 모두: MVP에서 미룬 편집 기능(접기 · 접기 영역, Method로 빼기, 호출 펴 보기 · 풀기, 이름을 적는 호출, 블록 글자의 언어 · 구문 강조, 테마)과 공유 URL · 보기 모드, 순수 SVG · PDF · 인쇄, 그림만 고친 파일 알림, 글자를 외곽선으로, 고대비 화면. 다른 문서의 Method를 부르는 호출(`P2`)은 1.0 뒤다.
- 파일에 남는 것을 확정한다: 글꼴 이름(`AriadneNSD Mono`로 정함 → [[dr-0019-bundled-font-name|DR-0019]]), 저장할 때 고정 문구의 언어 → [[outbox#확인해 주세요]]
- 키 표를 굳힌다([[03-keymap]]의 미결정을 닫음). 1.0 뒤에 키를 바꾸면 알린다.
- 사용법이 모든 기능을 다룬다.
- Obsidian 베타가 웹과 같은 파일을 읽고 써 본다.

Obsidian은 웹 베타 동안 베타로 시작하고, 커뮤니티 플러그인 목록에 올리는 것(Obsidian 1.0)은 웹 1.0 뒤다. 데스크톱은 그 뒤에 베타 → 1.0을 거친다. MVP는 웹에만 있다. 앱의 버전은 SemVer이고 파일 형식의 버전(`v1`)과는 따로 간다.

## 결과

- 좋아지는 점: "베타 무렵" · "출시 전"으로 흩어진 일이 한 문턱에 모인다. 사용자가 단계 이름만 보고 무엇을 기대할지 안다. 웹 1.0까지 형식을 마이그레이션 없이 고칠 수 있다.
- 감수하는 점: 웹 베타와 Obsidian 베타에서 저장한 파일이 웹 1.0 뒤에 열리지 않을 수 있다. 웹 1.0이 가장 늦게 온다(웹의 `P1` 모두).
- 후속 작업:
	- 요구사항에 단계를 적음 → [[01-requirements#5.1 MVP 다음의 단계]]. `P3`의 "출시 뒤"는 "웹 베타 뒤"로 고침
	- 파일 형식 명세의 "첫 출시 전까지"를 "웹 1.0 전까지"로 고침 → [[01-file-format]]
	- [[dr-0002-development-order|DR-0002]] · [[dr-0015-mvp-scope|DR-0015]]의 "이후 변경"에 이 DR을 담
	- backlog의 "웹 베타를 출시할 때" · "웹 베타 무렵" · "공개 출시 전"을 베타의 문턱으로 모음, 앱의 버전 `0.1.0`과 "1.0 전 파일" 알림은 할 일로 → [[backlog#웹 베타의 문턱]]
