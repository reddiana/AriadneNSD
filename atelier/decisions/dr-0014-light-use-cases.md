# DR-0014: 요구사항에 유즈케이스를 두고, 실패가 비싼 흐름만 자세히 쓴다

## 배경

메인테이너가 inbox에 적었다: "유즈케이스나 사용자스토리를 도입하는 것을 검토하고 의견 주세요." (2026-10-22)

[[01-requirements]]는 블록 ID가 붙은 기능의 목록이다(약 120개). 사용자가 무엇을 이루려고 그 기능들을 잇달아 쓰는지는 보이지 않는다. 예를 들어 "노트에 다이어그램을 넣어 보인다"는 `OBS-01`, 편집, 저장, `OBS-07`에 흩어져 있다. 그래서 인수 시험의 시나리오를 쓰거나, MVP를 "어느 흐름까지 되면"으로 자르기 어렵다.

## 결정 기준

- 흩어진 요구사항이 사용자의 목표 하나로 이어져 보인다
- 흐름이 인수 시험의 시나리오로 바로 옮겨진다
- 요구사항이 바뀔 때 고칠 곳이 적다. 메인테이너 혼자 유지할 수 있는 무게다

## 검토한 대안

그림은 시안 M26에 있다(같은 유즈케이스 하나를 세 형식으로): https://claude.ai/artifact/WK5QVcxxd27tEKEYs8uwYF , 저장소의 사본 `journal/assets/2026-10-22-use-case-forms-study.html`

### 대안 A: 가벼운 유즈케이스

기본 흐름과 예외 흐름 몇 줄, 요구사항 ID. 유즈케이스 하나에 15줄 안팎.

- 장점: 흐름이 그대로 시험 시나리오. 10개를 한 세션에 쓴다. 요구사항이 바뀌어도 고칠 곳이 적다
- 단점: "실패하면 무엇이 지켜지나"를 묻지 않아 빈 곳이 덜 드러난다

### 대안 B: 자세한 유즈케이스 (Cockburn의 fully dressed)

- 장점: 최소 보장과 확장을 빠짐없이 물어 요구사항의 빈 곳이 드러난다(UC-07 하나에서 넷)
- 단점: 유즈케이스 하나에 40줄 안팎. 쓰는 데도 고치는 데도 품이 많이 든다

### 대안 C: 사용자 스토리

- 장점: Given / When / Then 인수 기준이 자동 시험으로 옮기기 쉽다
- 단점: 일을 쪼개는 단위라 흐름이 여러 스토리로 흩어진다. 팀의 백로그가 아닌 지금은 얻을 것이 적다

### 대안 D: A와 B를 섞기

실패가 비싼 흐름(열기, 저장, 노트에 넣기)만 B로.

## 결정

**대안 D.** 메인테이너는 처음에 시안 M26에서 1번(추천, 대안 A)을 골랐다가, 같은 세션에서 "1과 2를 섞기"로 바꿨다: "이걸 선택할걸!!!" (2026-10-22)

- 유즈케이스는 [[02-use-cases]]에 둔다. 사용자 목표 수준으로 10개 안팎이며, 유즈케이스 다이어그램 하나를 함께 둔다.
- 모두 가벼운 형식(액터, 사전 조건, 기본 흐름, 예외 흐름, 요구사항 블록 ID)으로 쓴다.
- **실패가 비싼 흐름**은 자세한 형식(범위, 수준, 이해관계자와 관심, 최소 보장, 성공 보장, 트리거, 확장, 기술 변형, 빈도)으로 쓴다. 처음에는 UC-02 열기, UC-06 저장, UC-07 노트에 넣어 보이기다. 실패하면 사용자의 파일이나 글이 상하는 흐름이 새로 생기면 그것도 자세히 쓴다.
- 세부 규칙(키, 모습)은 UX 설계에 두고 되풀이하지 않는다.
- 유즈케이스를 쓰다가 드러난 빈 곳은 [[02-use-cases#6. 미결정 사항]]에 둔다.

## 결과

- 좋아지는 점: 기능의 목록 위에 흐름이 생긴다. 파일이 상할 수 있는 흐름에서는 최소 보장을 묻게 되어 빈 곳이 드러난다(세 유즈케이스에서 아홉). MVP를 유즈케이스로 셀 수 있다([[02-use-cases#3. 목록]]의 MVP 열).
- 감수하는 점: 자세히 쓴 셋은 요구사항이 바뀔 때 고칠 칸이 많다. 가볍게 쓴 일곱에서는 빈 곳이 덜 드러난다.
- 후속 작업: 품질 속성 시나리오(QAS)를 쓸 때 유즈케이스를 자극의 출처로 쓴다. 인수 시험은 유즈케이스의 기본 흐름과 예외 흐름에서 시작한다.
