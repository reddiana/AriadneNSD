# SVG 이미지와 WebP 그림, 메인 스레드

## 한 줄 요약

`<img>`로 넣어도 **SVG는 작은 문서**라서, 브라우저가 페이지와 같은 메인 스레드에서 그 안의 글자를 배치하고 그린다. PNG · WebP 같은 **래스터 그림은 픽셀 덩어리**라 메인 스레드 밖에서 풀린다(`decoding="async"`).

## 왜 문제가 되었나

예제 모달의 썸네일 열 개를 SVG로 미리 그려 두었다. 안에 글자가 많고 서브셋 글꼴(`@font-face`)도 들어 있었다. 브라우저는 SVG마다 글꼴을 읽고, 글자 모양을 계산하고(text shaping), 레이아웃하고, 그린다. CPU를 6배 느리게 하면 열 개에 약 1초가 들었다. 그동안 메인 스레드가 바빠서 탭이 늦게 반응했고 화면 글꼴 조각도 늦게 왔다.

## 바꾼 것

같은 SVG를 빌드할 때 Chromium의 캔버스에 그려 WebP로 저장한다(`canvas.toDataURL('image/webp', 0.9)`). 크기는 비슷했고(한 언어 열 개에 약 84 KB), 모달 뒤 썸네일이 다 보이기까지가 1.6초에서 0.7초 이하로 줄었다.

| | SVG 이미지 | WebP · PNG |
| --- | --- | --- |
| 확대 | 얼마든지 또렷 | 만든 크기까지(그래서 화면 칸의 두 배로 만듦) |
| 브라우저의 일 | 문서처럼 레이아웃 · 글자 배치 · 그리기, 메인 스레드 | 압축 풀기, 메인 스레드 밖 |
| 글자 | 글꼴이 필요 | 이미 픽셀 |

## 어떻게 찾았나

- 함수별 CPU: Chrome DevTools 프로토콜의 `Profiler`(→ `src/apps/web/scripts/profile-startup.mjs`). 압축하지 않은 빌드여야 함수 이름이 보인다
- 브라우저 내부의 일(레이아웃, 그리기, 글자 모양 계산): Chrome 트레이스(`devtools.timeline`). SVG 이미지마다 따로 된 "frame"의 레이아웃이 보였다
- 시간 측정은 매번 흔들려(±0.3초), 고치기 전과 후를 번갈아 여러 번 재어 중앙값을 견줬다
