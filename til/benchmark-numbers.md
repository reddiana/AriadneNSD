# 속도를 잰 숫자 읽기

(← [[til/README|TIL]])

메인테이너가 레이아웃 속도 스파이크(M39)를 돌리다 물었다: "할 때 마다 결과다 다른데 몇번 수행하고 평균을 내나요?" (2026-10-25)

## 한 줄 요약

같은 일을 여러 번 돌려 **중앙값**으로 보통의 속도를, **느린 5%**(p95)로 가끔 겪는 느림을 본다. 앞의 몇 번은 버린다(워밍업). 누를 때마다 숫자가 조금씩 다른 것은 정상이다.

## 백엔드로 비유하면

API 응답 시간을 볼 때와 같다. 평균은 몇 번의 느린 요청(GC, 다른 프로세스)에 끌려가서, 모니터링 대시보드는 p50(중앙값) · p95 · p99를 따로 보인다. 서비스 수준 목표(SLO)도 대개 "p95가 200ms 아래"처럼 적는다. JVM의 JIT처럼 브라우저의 JavaScript 엔진도 처음 몇 번은 느리게 돌다 코드를 최적화하므로, JMH가 워밍업 반복을 버리듯 앞의 몇 번을 뺀다.

| 숫자 | 뜻 | 왜 쓰나 |
| --- | --- | --- |
| 평균 | 모두 더해 나눔 | 한 번 크게 튄 값에 끌려간다 |
| 중앙값 (p50) | 줄 세웠을 때 가운데 | 보통의 속도. 튀는 값에 덜 흔들린다 |
| 느린 5% (p95) | 줄 세웠을 때 느린 쪽에서 5% 지점 | 사용자가 가끔 겪는 느림. 목표는 대개 이것으로 적는다 |

## 누를 때마다 다른 까닭

- 다른 탭, 백신, 운영체제의 일이 같은 CPU를 쓴다
- 노트북은 절전 때문에 CPU 속도가 오르내린다
- 브라우저가 쓰레기 수거(GC)를 하는 순간이 매번 다르다

그래서 한 번만 재지 않고 여러 번(M39는 한 번에 30번) 돌리고, 그것을 다시 몇 번(세 번) 눌러 **가장 느린 값**을 기준으로 본다. 목표는 느린 때에도 지켜져야 하기 때문이다.

## AriadneNSD에서는

- M39에서 블록 500개 문서를 다시 세고 그리는 데 중앙값 약 10ms, 느린 5%는 16 ~ 29ms였다. 목표(100ms)의 3분의 1 아래라, 바뀐 곳만 다시 세는 복잡한 방법(증분 레이아웃)은 하지 않기로 했다 → [[02-layout#4. 성능]]
- 시간의 대부분은 계산이 아니라 만든 SVG를 화면(DOM)에 넣는 단계였다. 빨라져야 할 때 손볼 곳이 어디인지도 숫자가 알려 준다
- 개발에 들어가면 같은 재기를 자동 시험(성능 벤치마크)으로 돌린다 → [[03-quality-attribute-scenarios#QA-07 편집 반응 시간|QA-07]]
