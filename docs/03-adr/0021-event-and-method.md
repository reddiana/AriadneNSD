# ADR-0021: Event와 Method를 구분한다

## 배경

한 문서에 다이어그램을 여러 개 두고 호출 블록으로 서로를 부르게 된 뒤([[01-requirements#^edit-multi-diagram]], [[01-requirements#^blk-call]]), 머리가 있는 다이어그램은 모두 같은 모자 모양 머리([[01-requirements#^blk-event]])를 달았다. 이벤트 처리기와, 호출 블록이 부르는 Method(Sub process)를 따로 둘지는 미결정으로 남아 있었다.

메인테이너가 프로토타입에 넣을 예제 둘(퀵소트, Raft 프로토콜)을 요청했고, 그 예제를 만들면서 두 가지가 드러났다.

- **Raft:** 다이어그램 열 개가 모두 같은 머리를 쓴다. 밖에서 시작되는 것 일곱(타이머, 받은 메시지)과 불려서만 도는 것 셋이 한눈에 갈리지 않는다.
- **퀵소트:** 호출 블록이 부르는 다이어그램의 머리 글자를 그대로 보여 주므로, `quicksort(a, lo, p - 1)`와 `quicksort(a, p + 1, hi)`가 같은 글자가 된다. `p = partition(…)`처럼 결과를 받을 수도 없다. 그래서 호출 블록을 쓰지 못하고 처리 블록으로 적어야 했다.

메인테이너는 "모양을 다르게 하기 전에, 의미가 있는지 살펴봐주세요"라고 했고, 코드 연동([[01-requirements#3.6 코드 연동]])도 함께 보자고 했다.

## 결정 기준

- 다이어그램이 여럿일 때 어디서 일이 시작되는지 한눈에 보일 것
- 인자와 결과가 있는 호출을 그릴 수 있을 것
- 나중에 코드 연동(차트 → 코드, 코드 → 차트)을 할 때 걸림돌이 되지 않을 것
- 사용자가 새로 배울 것이 적을 것

## 검토한 대안

시안은 `journal/assets/2026-10-11-event-method-study.html`에 있다.

### 구분할지

- **구분하지 않는다 (지금대로):** 개념이 하나라 단순하다. 위의 두 문제가 그대로 남는다. 코드를 만들 때 처리기 등록과 함수 정의를 가를 수 없다.
- **모델에서 구분한다:** Event는 문서 밖에서 시작되고, Method는 문서 안의 호출 블록이 부른다. 아무도 부르지 않는 Method는 "쓰이지 않는 것"으로 알려 줄 수 있다. 코드를 읽어 올 때 함수는 기본으로 Method가 된다. 개념이 하나 늘지만 종류는 대부분 상황에서 저절로 정해진다.

### Method의 머리 모양

- **H1 이중선 머리:** 호출 블록과 같은 양옆 이중선. 부르는 블록과 불리는 머리가 같은 표기다. Claude가 권했다.
- **H2 납작한 머리:** 모자 없는 네모. 머리 없는 다이어그램의 첫 처리 블록과 색으로만 갈린다.
- **H3 낮은 아치 머리:** Scratch의 "정의하기" 블록처럼 폭 전체에 걸친 낮은 아치. Event의 모자와 한 식구로 보인다. 작게 보면 둘이 비슷하다.

### 인자와 결과를 적는 법

- **A0 지금대로:** 호출 블록은 머리 글자를 그대로 보여 준다. 인자와 결과를 적을 수 없다.
- **A1 호출 블록의 글자를 자유롭게:** 처리 블록처럼 마음대로 적고, 부를 Method는 따로 고른다. 쉽고 코드식·문장식 모두 자연스럽다. 머리 이름을 고쳐도 호출 블록의 글자는 따라 바뀌지 않아 어긋날 수 있다.
- **A2 이름은 따라오고 인자만 적기:** 호출 블록이 "결과 ← 이름(인자)" 꼴이다. 이름, 인자, 결과가 따로 있어 코드 연동에 가장 좋다. 고치는 방법이 하나 더 필요하다. Claude가 권했다.

### 호출 블록으로 Event를 부를 수 있는가

- **C0 지금대로 둘 다:** 자유롭지만 "인터럽트를 함수처럼 부른다"는 어색한 그림이 생긴다.
- **C1 Method만 부른다:** 두 Event가 같은 일을 하면 그 일을 Method로 빼서 둘 다 부른다.
- **C2 Event는 "일으키기" 블록으로:** 뜻은 가장 정확하지만 블록 종류가 하나 는다.

### 단축키

- **S1 지금 키에 하나만 더하기:** `E` 새 다이어그램, `M` 머리 달기는 그대로 두고 종류를 바꾸는 `T`를 더한다.
- **S2 글자가 곧 종류:** `E`는 Event, `M`은 Method. 종류를 바꾸는 키가 따로 없다. `E`와 `M`의 뜻이 지금과 달라진다.

## 결정

**Event와 Method를 모델에서 구분한다.** 메인테이너가 시안을 보고 `H3, A1, C1, S2`를 골랐다.

- **종류:** 머리가 있는 다이어그램은 Event이거나 Method다. Event는 문서 밖에서 시작되고(인터럽트, 타이머, 받은 메시지), Method는 호출 블록이 부른다. 머리가 없는 다이어그램은 종류가 없고 부를 수 없다.
- **머리 모양 (H3):** Event는 지금의 모자 머리, Method는 폭 전체에 걸친 낮은 아치 머리로 그린다.
- **인자와 결과 (A1):** 호출 블록의 글자는 처리 블록처럼 자유롭게 적는다. 어느 Method를 부르는지는 글자와 따로 고른다.
- **호출 (C1):** 호출 블록은 Method만 부른다. Event를 일으키는 블록은 지금 두지 않는다.
- **단축키 (S2):** `E`는 Event, `M`은 Method다. 블록을 고르고 `M`을 누르면 그 블록을 새 Method로 뺀다.

머리 모양과 인자 표기에서는 Claude가 권한 안(H1, A2)과 다른 안을 골랐다. 구분 자체와 C1, S2는 권한 안과 같다.

세부 규칙은 요구사항에 적었다 → [[01-requirements#^blk-event]], [[01-requirements#^blk-method]], [[01-requirements#^blk-call]], [[01-requirements#^edit-extract]]

## 결과

- 좋아지는 점: 다이어그램이 여럿일 때 시작하는 곳(Event)과 불리는 곳(Method)이 머리 모양으로 갈린다. 퀵소트 같은 재귀와 결과를 받는 호출을 호출 블록으로 그릴 수 있다. 코드 연동 때 종류를 알 수 있다.
- 감수하는 점: 호출 블록의 글자가 자유로워서, 머리 이름을 고치면 글자와 이어진 Method가 어긋날 수 있다. 코드를 만들 때 호출 블록의 글자에서 인자와 결과를 가려내야 한다(A2였다면 따로 있었다). 모자와 낮은 아치는 작게 보면 비슷하다. 다른 Event를 일으키는 일은 그릴 수 없다.
- 후속 작업: 파일 형식에 종류를 넣는다([[01-file-format]]). 용어집과 모델 설계에 반영한다. Event를 일으키는 블록이 필요한지는 써 보고 정한다([[01-requirements#6. 미결정 사항]]). 단축키 전체를 정리할 때 `E` · `M` · `R`을 함께 적는다.
