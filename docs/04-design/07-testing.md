# 테스트 전략

AriadneNSD를 어떻게 시험하는지 정합니다: 층마다 무엇을 시험하나, 저장되는 SVG의 골든 파일, MVP의 인수 시험, 도구와 CI. 시험의 종류는 [[03-quality-attribute-scenarios#3. 시험 전략|품질 속성 시나리오 3장]]에서 시나리오마다 정했고, 도구는 [[0038-build-and-test-tools|ADR-0038]]에서 정했습니다. 기능마다의 세부 시험은 그 기능을 개발하기 직전에 씁니다.

코드: 시험 파일은 소스 바로 옆(`*.test.ts`), 골든 파일은 패키지마다 `golden/`, 브라우저 시험은 `src/apps/web/e2e/` (→ [[0036-code-layout|ADR-0036]], [[0038-build-and-test-tools|ADR-0038]])

## 1. 층마다 무엇을 시험하나

아키텍처의 층([[03-architecture#3. 구성 요소]])을 따라, 아래 층일수록 많이, 빠르게 시험합니다.

| 층 | 시험 | 도는 곳 | 무엇을 |
| --- | --- | --- | --- |
| `core` · 모델과 명령 | 단위, 속성 기반 | Node (Vitest + fast-check) | 명령마다 사전 조건 · 결과. 아무 명령열을 해도 불변식을 지킨다(QA-01). 실행 취소로 돌아가면 같은 문서 |
| `core` · 레이아웃 | 단위, 속성 기반 | Node | [[02-layout]]의 규칙: 블록은 맞붙고 겹치지 않는다, 부모가 자식을 담는다, 같은 입력이면 같은 좌표, 갈래 폭과 짧은 갈래의 분배 |
| `core` · 그림과 파일 | 골든 파일, 퍼징 | Node | 저장되는 SVG를 바이트로 비교(QA-03 · 04 · 05, 2장). 깨진 파일을 열어도 죽지 않는다(QA-02) |
| `core` · 속도 | 벤치마크 | Node (Vitest bench) | 블록 500개 문서에서 명령 → 레이아웃 → SVG 글자(QA-07의 `core` 몫, 목표의 절반 50ms) |
| `editor` | 명령 시험 | Node + 가짜 DOM | 키 입력 → 명령 → 문서. 키 표([[03-keymap]])의 두 키 조합, 고르기와 이동, 글자 고치기의 실행 취소 단위 |
| 셸 사이의 약속 | 계약 시험 | Node | 가짜 `DocumentStore` · `SettingsStore`로 `editor`가 셸 없이 돈다(QA-10, QA-17) |
| 웹 셸 | E2E, 시각 회귀 | 브라우저 (Playwright, Chromium) | 인수 시험의 몇 흐름(3장). 키보드만으로(QA-15). 화면과 저장된 그림이 같다(QA-06) |
| 구조 | 정적 분석 | Node | 의존 방향(dependency-cruiser), `core`에 DOM이 없음(`tsconfig`의 `lib`), 화면 글자를 코드에 박지 않음(ESLint 규칙, QA-13), 번들 크기(QA-09) |
| Obsidian · 데스크톱 · 다른 브라우저 | 수동 점검표 | 사람 | 출시 전. MVP(웹)에는 Firefox · Safari에서 열고 저장하기 |

- `core`의 시험이 가장 많고, 모두 Node에서 돕니다. 브라우저 시험은 화면을 지나야만 확인되는 것만 둡니다.
- 프로토타입의 시험(`journal/assets/2026-10-11-ns-prototype-test.mjs`)의 시나리오는 `editor`의 명령 시험으로 옮깁니다. 프로토타입 코드는 옮기지 않습니다.

## 2. 골든 파일

저장되는 그림이 바뀌지 않았는지를 바이트로 확인합니다. "같은 모델이면 같은 파일"([[01-requirements#^r-fmt|R-FMT-03]])의 직접 증거입니다.

- **자리:** `src/packages/core/golden/`. 한 사례가 파일 하나(`이름.ns.svg`)입니다. 모델이 그림 안에 들어 있으므로([[0005-model-embedded-svg|ADR-0005]]) 입력과 기대 출력이 한 파일입니다.
- **시험:** 파일을 열어 모델을 읽고 → 레이아웃 → 저장한 바이트가 원래 파일과 같은가(QA-04: 열고 바로 저장하면 그대로). 같은 시험을 모든 커밋에서 돌립니다.
- **사례:** 블록 종류마다 하나, 오늘 정한 레이아웃 규칙마다 하나(긴 조건과 빗금, 짧은 갈래, default 없는 Case, 여러 다이어그램의 배치, 접기 영역, 펴 보기), 한글 · 영어 섞인 글자, 옛 형식 버전의 파일(QA-05)
- **바꿀 때:** 그림이 바뀌는 것이 의도한 변경이면 갱신 명령으로 기대 파일을 다시 쓰고, 같은 커밋에 넣습니다. GitHub의 Pull Request는 SVG를 그림으로 보여 주므로, 리뷰어는 바뀌기 전과 뒤의 그림을 보고 판단합니다. 의도하지 않은 변경이면 시험이 실패한 것이 맞습니다.
- 갱신 명령의 이름은 개발을 시작할 때 정합니다.

## 3. MVP의 인수 시험

MVP(웹, [[dr-0015-mvp-scope|DR-0015]])를 내놓기 전에 모두 지나야 하는 시험입니다. 유즈케이스의 기본 흐름과 우선이 높은 품질 속성 시나리오에서 골랐습니다.

| ID | 무엇 | 어디서 | 시험 |
| --- | --- | --- | --- |
| AT-01 | 새 다이어그램을 만들고 블록을 넣고 저장한다 (UC-01 · 03 · 06) | 웹 | E2E |
| AT-02 | 저장한 파일을 다시 열면 같은 그림이다 (UC-02, QA-04) | 웹 | E2E + 골든 |
| AT-03 | 블록 6종을 넣고, 감싸고, 풀고, 복사하고, 갈래를 넣고 뺀다 (UC-03) | `editor` | 명령 시험 |
| AT-04 | 키보드만으로 AT-01을 끝낸다 (QA-15) | 웹 | E2E (키 입력만) |
| AT-05 | 블록 500개 문서에서 편집 응답이 100ms 안이다 (QA-07) | 웹 | 성능 (기준 기기) |
| AT-06 | 깨진 파일을 열어도 원본은 그대로이고 편집기는 죽지 않는다 (QA-02) | `core` · 웹 | 퍼징 + E2E |
| AT-07 | 저장에 실패해도 편집한 내용을 잃지 않는다 (UC-06 최소 보장, QA-17) | 웹 | E2E (저장 실패를 흉내) |
| AT-08 | 저장된 그림이 플러그인 없는 뷰어(브라우저, GitHub)에서 같게 보인다 (QA-06) | 웹 · 사람 | 시각 회귀 + 점검표 |
| AT-09 | PNG로 내보낸다 (UC-08) | 웹 | E2E |
| AT-10 | 같은 문서를 Chrome · Firefox · Safari에서 저장하면 같은 바이트다 (QA-03) | 사람 | 점검표 |

## 4. 도구와 CI

도구는 [[0038-build-and-test-tools|ADR-0038]]에 있습니다. CI(GitHub Actions)는 이렇게 돕니다.

| 언제 | 무엇을 | 걸리는 시간(목표) |
| --- | --- | --- |
| Pull Request와 `main`에 push할 때마다 | 코드 검사(ESLint, Prettier) → 타입 검사 → 의존 방향 → `core` · `editor` 시험(단위 · 속성 · 골든 · 계약) → 빌드와 크기 예산 → 웹 E2E(Chromium) | 10분 안 |
| 매일 밤 | 긴 퍼징, 벤치마크 기록(느려지면 알림) | — |
| 출시 전 | 기준 기기에서 성능, 수동 점검표(AT-08 · AT-10) | — |

- 시험이 하나라도 실패하면 `main`에 합치지 않습니다.
- 지금 있는 문서 사이트의 빌드(`.github/workflows/pages.yml`)와는 따로 둡니다.
